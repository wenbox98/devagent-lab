## 0. 这课为什么存在

现在有读、改、跑测试的工具，本课把它们组成修复闭环。模型提出修改不是完成；只有在正确环境、正确代码版本上执行了有效测试，才有资格讨论是否修复。

成品是修复状态机和测试报告分类器，而不是看到“失败”就再让模型改一次的无限循环。

## 1. 一条具体方案：从输入到结果

### 先复现，再修复，再复测

任务：第一页应该从第0个元素开始，当前fixture用 page_no*size。先运行受保护测试获取原始失败，再读取相关代码；模型提出最小补丁，L07校验版本写入，L08运行测试，解析结果后决定停止或下一次尝试。

### 采用有限结果分类

| 测试观测 | 下一步 |
|---|---|
| 已发现并执行测试，断言失败 | 把失败断言和相关代码反馈给模型 |
| 收集失败/导入失败 | 先排查环境、依赖或本次diff，不能直接宣布业务算法错 |
| 发现0个测试 | 验收无效，修测试入口或停止 |
| 超时/输出限额 | 看资源和执行状态，不能当普通assertion failure |
| 目标与回归通过 | 交独立grader确认，不只采信模型文字 |

导入错误并非永远是环境问题：若模型刚把函数名删了，应回看diff。分类器提供事实，修复控制器结合变化和环境证据决策。

### 停止条件

每次尝试记录baseline_hash、patch_hash、test_report和成本。达到修复次数/时间预算、无可行动证据或不可恢复环境错误时返回明确原因。失败结果保留已尝试方案，不把最后一次模型自信总结当成功。

### 用报告而不是日志关键词驱动循环

```python
def next_step(report, remaining_attempts):
    if report.discovered == 0:
        return "fix_test_entry_or_stop"
    if report.kind == "environment_error":
        return "diagnose_environment"
    if report.kind == "assertion_failure" and remaining_attempts > 0:
        return "propose_patch"
    if report.kind == "passed":
        return "independent_grade"
    return "stop_with_evidence"
```

这是教学决策片段，report来源必须是运行器实际结果。模型不能填写report.kind='passed'来绕过测试。

### 每轮反馈保留哪些最小信息

任务约束、当前文件版本、失败测试名、预期与实际、被限制的修改范围、剩余预算。新补丁针对这个版本生成，不能把上轮旧测试报告与本轮新代码混合。

如果收集错误由本次删除模块造成，应回看diff；如果同环境基线也报缺依赖，则优先修环境。分类不是自动归因，它提供了更准确的排查起点。

### 基础演示与独立grader之间

模型声称通过，只表示它生成了声明；运行器报告通过，只表示这批测试在该环境执行成功；grader还要检查目标/回归/约束/快照。这三层结论逐步增强，不允许前一层代替后一层。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 先区分测试结果类型

**读这一段是为了解决：** 红灯是断言失败、零测试还是收集失败？

**原教材的浓缩句：**

> 结果至少有passed、assertion_failed、collection_error、environment_error、timeout、no_tests。

**展开与落地：**

先用机器可解析报告或受控测试运行器获取发现数、执行数、通过数、失败类别和退出码。仅匹配stdout中的OK会被测试打印内容误导。

测试分类器本身也需要样本：零测试、收集失败、业务失败、超时。每种样本说明它会让修复循环选择哪个分支。

### K2. 修复反馈应该足够具体

**读这一段是为了解决：** 给模型什么事实才能指导下一轮修复？

**原教材的浓缩句：**

> 把失败测试名、预期、实际、相关堆栈片段交给模型，比整段上万行日志更可用。

**展开与落地：**

反馈给模型要包含哪条断言失败、实际与预期、相关代码版本和允许修改范围，而不是完整重复整个仓库。

删减输出时保留能反驳当前假设的那一条证据。模型下一步是否变化，可以观察补丁和工具参数，不需要读取隐藏思维。

### K3. 环境问题不要自动变成代码修改

**读这一段是为了解决：** 依赖未安装时改业务代码为何无效？

**原教材的浓缩句：**

> 缺依赖时先报告环境阻塞或执行已授权的配置步骤。

**展开与落地：**

缺依赖时直接改业务函数可能越改越错。先用相同环境复跑基线或检查本次diff区分环境漂移与代码造成的导入错误。

一次只调整一个主要因素。先修测试入口就能发现测试时，不要同时换模型、依赖和提示词，否则无法知道哪项有效。

### K4. 把测试结果转换成有限的下一步

**读这一段是为了解决：** 哪种TestReport应继续、哪种必须blocked？

**原教材的浓缩句：**

> 测试不通过可能是断言失败、导入错误、依赖缺失、无测试或超时。

**展开与落地：**

修复控制器读取TestReport而不是自由文本猜状态。用状态表规定哪些结果可进入下一次模型调用，哪些应阻断。

例如权限拒绝不触发绕过工具；no_tests不允许计成功；stale_patch先重读再生成。这些决策是程序规则，不交给模型无限发挥。

### K5. 修复尝试与任务成功分开记账

**读这一段是为了解决：** 补丁被应用为什么还不叫任务成功？

**原教材的浓缩句：**

> 一次尝试包含读取、提出补丁、执行、验证。

**展开与落地：**

attempt表示一次修改与测试尝试，task表示总体目标。第三次尝试通过不能抹掉前两次成本；第三次失败也不应覆盖初始错误证据。

按任务汇总成功率、调用数、时间和总修改范围。后续成本优化需要这份完整账，而不是只记最后一条模型请求。

### K6. 避免让评判标准跟着答案移动

**读这一段是为了解决：** 为什么不能让Agent同时修改答案和评分标准？

**原教材的浓缩句：**

> 如果Agent可以把失败测试删除或改弱断言，测试全绿不再证明问题解决。

**展开与落地：**

执行者不能修改独立参考测试或放宽期望。测试文件在Agent写权限外，grader绑定验收版本。

可以让模型补候选测试，但不能用自己写的、总是通过的测试作为唯一成功依据。测试被删、发现数降为0、验收配置变动都应使任务无法通过。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 修复顺序 | 失败复现→版本化补丁→测试→独立验收 | 每一步都有输入/输出证据 | 不是模型说修好 |
| 分类 | TestReport区分业务、环境、收集、0测试 | 每种结果对应有限下一步 | 导入错误需结合diff判断 |
| 预算 | 按attempt与task双层记账 | 超限明确停止，保留历史 | 不允许无限改到绿 |
| 验收 | 保护参考测试和发现数 | 篡改验收不能得分 | 新增测试不替代参考测试 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
