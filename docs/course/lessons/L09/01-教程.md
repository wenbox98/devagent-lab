## 先定位阅读目的与对象

**本课要回答：怎样避免在依赖没装好时不停修改正确的业务代码？**

前提是：读取、补丁和运行器已经具备，但红色测试结果有多种根因。 本课把它推进到：用测试数量、收集错误和断言结果控制修复下一步，遇到环境问题停下排障。

本文的知识讲解是为完成上述变化服务，不要求先掌握所有相邻技术。范围边界：不修改裁判标准追求绿灯；分类函数不是完整测试运行器。

**文中代码分两种。** [00-example.py](00-example.py)是包中已经提供的概念示例；本课“工程实现/职责路径”是对你项目的目标要求，除L00起始骨架外不表示应用已经生成。未生成时只研究示例；生成后让Codex把职责映射到实际文件，不照猜函数名找代码。

先读[本课文件导航](00-本课目的与文件导航.md)，练习具体改动位置见[实验与排错](03-实验与排错.md)，源码定位方式见[代码地图](05-过关卡与代码地图.md)。需要代码AI帮助时只给[本课Codex指令](02-交给AI.md)与当前源码，并指定“只分析，不修改”。

### K1. 先区分测试结果类型

**读这一段是为了解决：** 红灯是断言失败、零测试还是收集失败？

结果至少有passed、assertion_failed、collection_error、environment_error、timeout、no_tests。断言失败说明测试执行到某个期待不满足；导入错误可能说明环境或代码加载有问题；没有收集测试不能宣称修复通过。

运行器提供进程事实，测试解析器提供结构化测试事实，Agent使用这些事实做下一步。不要仅根据exit_code=0判定任务成功，某些框架在零测试时也可返回0。

注意：ImportError只说明导入失败，可能是缺依赖，也可能是代码写错导入。先标collection_error，再依据依赖与文件证据分类；不能见到ImportError就断言环境坏了。

### K2. 修复反馈应该足够具体

**读这一段是为了解决：** 给模型什么事实才能指导下一轮修复？

把失败测试名、预期、实际、相关堆栈片段交给模型，比整段上万行日志更可用。同时保存原始日志引用，裁剪后的信息不够时可以回看。

例如page([0,1,2,3],1,2)实际[2,3]、期待[0,1]，指向起始偏移。修正后再检查第二页和非法页码，避免只对一个例子硬编码返回。

### K3. 环境问题不要自动变成代码修改

**读这一段是为了解决：** 依赖未安装时改业务代码为何无效？

缺依赖时先报告环境阻塞或执行已授权的配置步骤。不能为了消除ImportError删除相关功能，不能为了测试通过降低断言。固定修复目标、允许修改范围与最大轮数。

闭环结束报告应包括修改文件、具体测试、实际结果和未解决项。最终成功由验证器依据事实产生，模型可以解释，但不能单独授予自己成功状态。

### K4. 把测试结果转换成有限的下一步

**读这一段是为了解决：** 哪种TestReport应继续、哪种必须blocked？

测试不通过可能是断言失败、导入错误、依赖缺失、无测试或超时。只有与目标缺陷相关的断言失败适合继续改业务代码；环境缺失先修环境或受阻；无测试意味着没有证据。解析器输出结构化分类和原始日志引用，Agent据此选下一步，避免让模型在一团日志中猜“应该算成功”。

### K5. 修复尝试与任务成功分开记账

**读这一段是为了解决：** 补丁被应用为什么还不叫任务成功？

一次尝试包含读取、提出补丁、执行、验证。补丁应用成功只证明写入成功；测试执行成功只证明进程完成；任务成功还需要目标断言、回归与约束都满足。为每次尝试记录基础版本、补丁哈希、测试报告、状态变化，才能比较第二次尝试是否真正比第一次好。

### K6. 避免让评判标准跟着答案移动

**读这一段是为了解决：** 为什么不能让Agent同时修改答案和评分标准？

如果Agent可以把失败测试删除或改弱断言，测试全绿不再证明问题解决。独立参考测试放在写权限之外，检查测试数量与修改范围；同时允许新增合理测试验证修复。你要学会区分修改被测实现与修改验收口径，后者需要显式审查。

### 与你已有语言经验的连接

嵌套dict应转成清晰结果对象；解析日志保留原文引用，不用一个宽泛正则推断全部状态。

## 深入推演：把知识点连成因果关系

### 修复闭环依赖三个相互独立的角色

模型提出假设与补丁，工具读取和修改真实工作区，验收器检查目标与回归。三者不能合并成“模型说修好了”。先保留失败基线，再运行补丁，最后在同一约束下执行独立测试。没有基线，你可能只是碰巧运行了另一份已经正确的代码；没有最终状态检查，你可能验证的是旧文件。

### 用分页错误手推一遍

任务约定页码从1开始、size为2。原实现从`page*size`开始，第一页直接跳过两个元素。目标测试先失败；候选修复改为`(page-1)*size`，第一页通过，但你还要检查第二页、不足一页、空输入和非法页码。不是所有边界都必须某一种行为，必须跟已有任务契约一致。测试用来区分“修了示例”和“实现了要求”。

### 把失败反馈压成可行动的信息

下一轮提供失败用例标识、期望与实际、相关堆栈窗口、当前代码版本与已尝试改动。直接把数万行日志全塞回模型会增加噪声；只给“失败了”又没有定位信息。先判断是测试断言失败、运行环境问题、补丁没应用还是调用协议错误，再决定是否让模型继续改源码。


## 3. 一次完整推演：先预测，再读下一步

1. 初始pagination测试失败，分类assertion_failure，读取页码约定后修改start。
2. 运行器返回0但收集测试数为0：状态no_tests，任务不能successful，先排查测试发现配置。
3. 目标测试通过、回归失败：保留失败证据并继续定位，不以“目标已修”结束。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 重试同一测试 | 怀疑暂态基础设施故障 | 有次数与时间预算 |
| 修改实现 | 可定位的业务断言失败 | 必须保护公共约束 |
| 停止并报告blocked | 依赖或权限无法满足 | 不要制造通过报告 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
def classify(exit_code, tests_run, import_error=False, timed_out=False):
    if timed_out:
        return "timeout"
    if import_error:
        return "collection_error"
    if tests_run == 0:
        return "no_tests"
    return "passed" if exit_code == 0 else "assertion_failed"

print(classify(0, 0))
print(classify(1, 0, import_error=True))
print(classify(0, 3))
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
python .local/concepts/L09/00-example.py
```

预期观察：

```text
no_tests
collection_error
passed
```

### 按因果关系理解输出

示例假设tests_run和import_error已经来自可信解析。实际框架可能有多种错误类型，优先使用结构化报告；文本解析需要专门案例验证，不能用一个含failed的字符串猜全部结果。

现在只修改练习副本`.local/concepts/L09/00-example.py`中的指定输入：追加classify(1,3)、classify(5,0)和classify(1,0,import_error=True)三次调用；不改分类代码。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 8. 面试时如何解释你做过的事

**为什么不把所有测试日志交给模型？**

既增加成本也可能淹没关键信息，但应保留原始证据以便补读。

**模型说已修复，测试通过就够吗？**

还要确认测试确实执行、范围足够、未篡改标准，并审查变更范围。

补一句反事实：如果“依赖或权限无法满足”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
