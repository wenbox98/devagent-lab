## 1. 为什么现在学这一课

**当前条件（不是对你进度的断言）：** 读取、补丁和运行器已经具备，但红色测试结果有多种根因。

**本课问题：** 怎样避免在依赖没装好时不停修改正确的业务代码？

**期望变化：** 用测试数量、收集错误和断言结果控制修复下一步，遇到环境问题停下排障。

**不做这一步的风险：** 把没有收集到测试或导入失败误当成代码通过，或者把环境故障当业务断言失败，都会导致错误修复和无效重试。

顺序前置：[L08本课目的](../L08/00-本课目的与文件导航.md)。前置是能力条件，不是“看过文档”即可；由Codex核对现有源码/测试。 后续[L10](../L10/00-本课目的与文件导航.md)继续使用本课产物。

**本课不负责：** 不修改裁判标准追求绿灯；分类函数不是完整测试运行器。

## 4. 今天先做哪一个动作

只想理解：打开[本课教程](01-教程.md)，先回答“怎样避免在依赖没装好时不停修改正确的业务代码？”。

想改一个输入：按[本课实验的A阶段](03-实验与排错.md)准备副本，**看classify(exit_code, tests_run, import_error, timed_out)。** 然后执行：追加classify(1,3)、classify(5,0)和classify(1,0,import_error=True)三次调用；不改分类代码。

已有或准备生成项目代码：把[本课02指令](02-交给AI.md)和当前源码交给Codex，发送“只分析本课意图与实际代码对应，不修改代码”。不必自己猜函数位置，也不必把六份Markdown拼接给它。

## 5. 读不懂时，带着什么目的查资料

下列问题与[教程](01-教程.md)的知识段一一对应。查到能回答该问题、能指出观察证据即可先回到实验，不要求把官方站点读完。

| 本课知识段 | 为什么讲：你要解决的具体问题 |
| --- | --- |
| 先区分测试结果类型 | 红灯是断言失败、零测试还是收集失败？ |
| 修复反馈应该足够具体 | 给模型什么事实才能指导下一轮修复？ |
| 环境问题不要自动变成代码修改 | 依赖未安装时改业务代码为何无效？ |
| 把测试结果转换成有限的下一步 | 哪种TestReport应继续、哪种必须blocked？ |
| 修复尝试与任务成功分开记账 | 补丁被应用为什么还不叫任务成功？ |
| 避免让评判标准跟着答案移动 | 为什么不能让Agent同时修改答案和评分标准？ |

可复制检索词：`pytest exit codes collection errors tests collected repair loop`。优先使用[本课教程末尾的官方参考](01-教程.md)和[官方阅读路线](../../09-技术版本与官方阅读路径.md)。这些链接沿用已有教材来源；本轮聚焦结构与指代，未重新核验所有网页或依赖版本。

## 6. 本课完成后要留下什么

**项目阶段怎样证明风险已被处理：** 分别制造导入失败、0测试和真实断言失败；检查下一步动作不同，不统一重试模型。

要能串起：**定位 → 补丁 → 测试 → 失败分类 → 下一步/停止；最终结论仍由独立验收给出。**

具体证据看：assertion_failed、no_tests、collection_error是否可区分。

在`docs/learning-records/L09.md`分别填写概念观察、实际实现、独立修改和未验证项。源码地图由Codex基于实际源码填写；个人理解由你填写。标准库示例、框架离线运行、真实API、完整服务是不同验证层次。
