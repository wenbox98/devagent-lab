### K1. 先理解线程池的接纳顺序

**读这一段是为了解决：** 线程池先建线程、入队还是拒绝？

ThreadPoolExecutor通常先用核心线程，再尝试入队，队列满后再扩至maximumPoolSize，仍无法接纳则执行拒绝策略。使用无界队列时，maximumPoolSize往往不能像预想那样帮助扩容，因为入队一直成功。

这解释了为什么配置max=100却只有少数线程工作、队列越来越长。队列容量必须结合任务时长与用户可接受等待决定，不是越大越稳。

### K2. 三种超时不能混用

**读这一段是为了解决：** 连接、HTTP响应、后台任务超时各说明什么？

连接超时是建立连接，HTTP响应/读取超时是等待本次响应，任务截止时间是整体业务期限。Java HTTP超时后，Python任务可能仍继续。需要显式查询或取消任务，而不是把Java异常直接写成任务取消。

取消线程或Future也不一定停止底层网络/远程工作，要了解客户端和执行器的取消传播，记录最终核对状态。

### K3. 把重试算进负载

**读这一段是为了解决：** 重试次数怎样放大真实下游请求？

10个原请求每个重试3次可能形成更多实际调用，多个层都重试会进一步放大。选择一层负责重试，设置上限、退避和总体截止时间。认证与参数错误不重试；写请求先复用J01身份与核对。

限制并发保护下游，有界队列保护等待资源，明确拒绝给客户端可处理的状态。不要靠无限等待制造表面成功率。

### K4. 怎样观察实验

**读这一段是为了解决：** 哪些指标能区分等待、运行和被拒绝？

记录活跃线程、队列长度、拒绝次数、请求总耗时和Python活跃任务数。先用固定受控延迟稳定复现，再在真实联调中看结果。负载仅针对自己的本地服务，不用于无授权压测。

### K5. 线程池的队列策略决定过载形态

**读这一段是为了解决：** 有界与无界队列改变了什么过载表现？

固定并发但无界队列会把压力积成越来越长的等待和内存占用；线程无限增加又会压垮CPU、数据库或下游。明确最大并发、队列容量、拒绝策略与用户可见结果。测active、queue_size、wait_time和rejected，而不是只看线程总数。即使使用虚拟线程，下游连接数和调用配额仍然有限。

### K6. 请求超时、任务超时与总deadline

**读这一段是为了解决：** 总deadline怎样限制多次等待？

HTTP等待2秒结束，不代表后台3分钟任务应该被杀；任务总期限另有配置。一次任务中的重试都共享剩余deadline，不能每次重新获得完整超时，否则最坏等待远超承诺。连接、读取与排队也消耗时间；把总预算传到下游并在执行前检查剩余值。

### K7. 多层重试会乘法放大

**读这一段是为了解决：** 多层重试的“3次”包含不包含首次，如何核对？

若浏览器、Java、Python每层最多3次总尝试，最坏下游尝试可达27次；如果说的是3次重试即4次尝试，则为64次。必须写清口径。选一个主要重试层，其他层传递错误与操作ID；退避、限流、熔断、隔舱解决不同问题，按故障证据引入，不把术语都塞上去。

### 与你已有语言经验的连接

Java重点：ThreadPoolExecutor、RejectedExecutionHandler、CompletableFuture超时不自动停止底层操作；理解Future.cancel的实际语义。

## 深入推演：把知识点连成因果关系

### 线程、队列和下游连接形成一条容量链

用户请求先进入Web线程，再等待业务执行器，再等待HTTP连接，最后到Python任务服务。把线程池开大可能只是把等待从一层移到另一层，并把下游压垮。观察活动线程、队列长度、连接占用、拒绝数和实际吞吐，而不是只看CPU低就加线程。

### 无界队列让过载变成慢性失效

到达速度长期大于处理速度，队列会持续增长，内存与等待时间越来越高。教学用有界队列、明确拒绝策略和提交限额，让过载可见。Java虚拟线程可改变线程等待的成本，却不会创造无限HTTP连接或模型配额；外部资源仍需并发上限。

### 超时预算应沿调用链递减

总任务受理预算若是2秒，下游不能每层各等2秒再重试三次。向后传递剩余deadline，区分连接超时、响应超时和任务执行超时；一个HTTP调用超时不应自动取消仍可能正常运行的远程Agent。重试只针对可恢复且有幂等保护的请求，记录实际attempt数与下游压力。


## 3. 一次完整推演：先预测，再读下一步

1. 配置4个worker、队列8个、每任务2秒，瞬间提交20个：最多12个被运行/排队接纳，其余按明确拒绝策略处理；具体观测受提交时序影响。
2. Java超时后Python仍执行：查询同execution_id，而不是创建新任务。
3. 注入下游限流，统计各层实际尝试次数；关闭重复重试层后检查放大是否下降、成功率是否受损。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 增加线程 | 确有可并行等待且下游有余量 | 受连接、内存和配额约束 |
| 有界队列+拒绝 | 过载时保护系统 | 调用者需处理忙碌状态 |
| 熔断 | 持续下游故障 | 不是正常容量管理的替代 |
| 隔舱 | 一个慢下游拖累其他能力 | 需要独立资源预算 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```java
import java.util.concurrent.*;

public class Demo {
    public static void main(String[] args) throws Exception {
        var gate = new CountDownLatch(1);
        var pool = new ThreadPoolExecutor(1, 1, 0, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(1), new ThreadPoolExecutor.AbortPolicy());
        Runnable slow = () -> {
            try { gate.await(); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };
        int rejected = 0;
        try {
            pool.execute(slow);
            pool.execute(slow);
            try { pool.execute(slow); }
            catch (RejectedExecutionException e) { rejected++; }
            System.out.println("rejected=" + rejected);
        } finally {
            gate.countDown();
            pool.shutdown();
            pool.awaitTermination(2, TimeUnit.SECONDS);
        }
    }
}
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
javac -encoding UTF-8 docs/course/lessons/J02/Demo.java
java -cp .local/concepts/J02 Demo
```

预期观察：

```text
rejected=1
```

### 按因果关系理解输出

一个任务占线程，一个排队，第三个被拒绝。CountDownLatch让慢任务稳定阻塞而不靠猜测sleep时间；finally释放它保证演示结束。生产拒绝应转成清楚的服务行为，不能把异常丢给用户后仍偷偷排队。

现在只修改练习副本`.local/concepts/J02/Demo.java`中的指定输入：先读Demo.java实际构造参数；只修改提交任务数量，不随意扩大线程与队列。预测哪些任务会被拒绝。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。
