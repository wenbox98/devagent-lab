## A. 不等项目生成，也能先做的概念实验

**执行目录统一为：学习项目根目录（能同时看到 `devagent/` 和 `docs/course/` 的目录）。** 尚未建项目时，先看[从这里开始](../../00-从这里开始.md)初始化步骤。以下命令中的`python`应指向你的Python环境；不是让你安装一个叫devagent的第三方包。

先创建本课副本（已有副本时工具会拒绝覆盖，不会丢掉你的改动）：

```text
python docs/course/tools/prepare_example.py J02 --project .
```

基准只读文件：[docs/course/lessons/J02/Demo.java](Demo.java)。本阶段**只改**`.local/concepts/J02/Demo.java`，不改`docs/course/`、公共裁判或项目主实现。

**具体看哪里：** Demo.main中的ThreadPoolExecutor构造参数、提交循环和RejectedExecutionException分支。

**具体改什么：** 先读Demo.java实际构造参数；只修改提交任务数量，不随意扩大线程与队列。预测哪些任务会被拒绝。

**为什么做：** 下游变慢时，为什么多开线程或叠加重试可能让问题更严重？

**观察什么：** 接纳和拒绝数、active与queue；没有测量时不写性能提升。

运行未改副本留基线，再修改指定输入运行同一命令：

```text

java -cp .local/concepts/J02 Demo
```

## 实验1：queue-full

**操作对象：** 本课生成的案例分派入口`java-task-service/src/test/java 下的 J02LessonTest（由Codex给出实际包路径）`，案例`queue-full`。先通过命令的案例参数触发，不需要手工去找并替换一个未知客户端。实现不符时，从`J02-code-map.json`中的入口跟到核心决策；业务修复改映射后的源码，不能改observed/断言来凑成功。

**先预测：** 固定线程和小队列，任务由latch受控阻塞时，哪一层应该发现问题？

触发方式：固定线程和小队列，任务由latch受控阻塞。执行本课AI生成的入口：

```bash
mvn -f java-task-service/pom.xml -Dtest=J02LessonTest -Dlesson.case=queue-full test
```

必须看到或核对：**超过容量明确拒绝，队列不无限增长**。

不要只看退出码。检查JUnit实际执行的案例和断言报告；故意触发的业务错误可能正是测试通过条件。

结果不符合时优先排查：查队列是否无界。先保留一次失败输出，再改一个主要因素重新运行；不要把预期值改成当前错误输出。

记录：运行命令、实际关键字段、是否与预测一致、证据位置、修改前后Git提交。
