## A. 先选对象，不等于要全部重做

未生成主项目时先跑概念例子；主项目命令必须在02实施完成后再执行。

执行目录是学习项目根目录（能看到devagent/与docs/course/）。准备原教材例子的副本：

```bash
python docs/course/tools/prepare_example.py L04 --project .
```

只改`.local/concepts/L04/00-example.py`，不改教材基准。具体观察：模块级script、history、for循环与追加tool_result的语句。

先预测，再改变条件：在副本中暂时注释追加tool_result的那一行，保持script不变，比较history。此脚本仍会final，所以只能证明反馈缺失，不能证明模型决策变化。

验证范围：history中是否包含同ID的tool_result；项目中再检查下一次真实传入消息。。这不是当前应用已完成的证明。

本版新增机制实验可以直接运行基准，也可以先复制再改：

```bash
python docs/course/lessons/L04/01-mechanism.py
```

看scope说明它用的是内存、临时文件、固定子进程还是排名fixture。不要把无网络脚本写成真实模型接入证据。

## B. 项目实现：先基线，再变更

把同目录02交给Codex，已有实现用REVIEW_ONLY，缺实现且明确授权时用IMPLEMENT。先读取相关旧测试、实际源码与Git状态，不能从模块不存在推断需要安装同名第三方包。

实施后按02列出的案例逐个跑。每个案例运行前写：输入、预期首个分支、调用/副作用、预期结果；运行后另写observed，不把预测复制成观测。

### 必需案例与实际要证明的行为

| 案例名 | 怎么触发 | 必须实际验证的结果 |
| --- | --- | --- |
| read-then-answer | 假模型先请求文件再回答 | 两轮模型调用，下一轮输入含真实工具结果 |
| repair-tool-error | 第一轮无效参数，第二轮更正 | 错误结果关联call_id，后续可用正确参数 |
| step-limit | 假模型不断请求相同工具，max_steps=3 | 模型调用不超过3，终止原因step_limit |
| real-read | 真实模型在练习仓库回答函数位置 | 可看到实际工具调用与最后回答；无配置则blocked |

## C. 只做一个独立变体

给循环增加一个可解释的等待用户状态，先定义等待时是否还调用模型、恢复后历史如何保留，再独立实现核心判断。

记录第一次判断，不先打开04。先写最小失败复现；定位首个不同分支后再改对应职责。不要同时修改模型、提示词、依赖与测试期望。

若卡住，给导师：实际输入、执行命令、预期、实际错误、两个可能原因、已排除哪个。请求定位提示，而不是让AI重写项目。

## D. 怎样收尾

先运行新增测试（用实际类名/方法），再当课与全量回归：

