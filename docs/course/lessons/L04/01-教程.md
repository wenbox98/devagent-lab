## 0. 这课为什么存在

L03 的工具调度器能执行一次调用，但还不会让模型根据结果决定下一步。L04 把模型调用、工具执行和反馈串起来，形成一个有终止条件的循环。

这里的“自主”不是不受控制，而是在程序允许的工具和预算内，由模型选择下一步。你不必先学框架，先能在日志里看到“读文件后答案发生变化”。

## 1. 一条具体方案：从输入到结果

### 用两轮响应看到闭环，而不是背 Agent 名词

第一轮：用户问“分页从第几项开始？”模型看不到文件，提出 c1/read_file。程序调用 L03 dispatcher，真实读到 `start = page_no * size`，把带 c1 的 ToolResult 追加到消息历史。

第二轮：模型收到问题、自己的工具提议和真实工具结果，才给出基于代码的解释。缺少回传这一步，第二轮即使继续调用模型，也仍可能是在猜。

### 采用的循环规则

```text
检查剩余预算
→ 构建本轮消息
→ 调用一次模型
→ 最终文本？返回“模型已给出答案”
→ 工具提议？逐个验证和执行，回传全部结果
→ 下一轮
```

“最终文本”表示循环得到答案，不自动表示修复成功。L09/L12 会加入真实测试和独立验收。

本课先按顺序执行多个工具提议，避免并发让关联和资源管理提前复杂化。步骤预算定义为模型调用轮次，工具调用数另计；否则一轮内20个工具可能绕过“5步限制”。

### 可重复验收

脚本模型按顺序给出“工具提议、最终答案”，但工具内容必须真实读取。断言第二次模型收到的历史包含真实 ToolResult；再让工具返回一次可修复错误，断言下一轮确实看到错误。只断言最后输出 done 不足以证明形成反馈循环。

### 为什么“while里调用两次模型”还不算反馈

核心是第二轮输入确实包含第一轮工具产生的新事实。最小教学骨架：

```python
for round_index in range(max_rounds):
    response = model.complete(messages)
    if response.kind == "final":
        return response.text
    messages.append(response.as_message())
    for call in response.tool_calls:
        result = dispatcher.execute(call)
        messages.append(result.as_message())
return stopped_result("budget_exhausted")
```

这是职责骨架，不是直接可运行的应用代码。`as_message`与`stopped_result`需由实际实现提供。不要从这段推断项目当前已经有相同方法名。

### 模型信息与执行信息怎样分开

messages里保留模型的工具提议和程序的工具结果；不能只追加结果而丢掉请求关联。ToolResult的content来自真正的工具执行，即使它是失败，也保留错误类别和call_id。

最后返回文本只结束模型交互。若任务是改代码，独立验收还在后面；若任务是只读定位，也需要引用存在、位置正确。一个“final”字段不是所有任务共同成功标准。

### 两条很有价值的反例

脚本模型永远返回同一个工具请求：循环必须有限结束。脚本模型第二轮尝试在没收到ToolResult时直接成功：测试检查实际历史，不能让固定答案掩盖回传缺失。

新增01-mechanism.py直接运行这条受控链：脚本模型、真实临时文件、两轮消息。你可以先看events，再回到项目loop逐条对应。它让机制可见，不证明真实LLM选择能力。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 一次循环里谁拥有什么权力

**读这一段是为了解决：** 模型、宿主、工具各自能决定什么？

**原教材的浓缩句：**

> 模型可以提议下一动作，程序决定哪些动作允许、怎样执行、何时停止。

**展开与落地：**

模型拥有“提议权”；程序拥有“校验、执行和停止权”。模型不能直接 open，不能通过输出文字给自己提高权限；工具注册表、工作区和预算仍由宿主控制。

分工落到代码上是 model_client、dispatcher、loop 三个职责。loop 不复制文件读取逻辑，也不把模型的推测当成工具事实。

### K2. 为什么必须回传结果

**读这一段是为了解决：** 不回传结果时下一轮少了什么事实？

**原教材的浓缩句：**

> 若你执行了read_file却没有把内容加入下一次模型请求，模型看不到环境变化，只能继续猜。

**展开与落地：**

工具结果是下一轮输入的一部分，必须包含调用ID、成功或失败、内容/证据位置。仅 print 结果给人看，不会让下一轮模型看见它。

检查实际发送给第二轮模型的 messages，而不是检查日志有没有打印文件。保留模型自己的工具提议，才能让 ToolResult 的ID有可匹配的上下文。

### K3. 预算与终止不是附加功能

**读这一段是为了解决：** 哪种终止必须由程序强制执行？

**原教材的浓缩句：**

> 没有终止条件的while True会在模型重复调用时一直花钱。

**展开与落地：**

每轮模型调用前先扣/检查轮次额度；执行工具前检查工具额度；到总截止时间或取消时不再发新请求。预算耗尽应返回明确终止原因和已有证据，不能强造成功答案。

最小版至少max_steps，并明确计数对象。没有有限退出的while True不应作为实现；供应商/框架递归限制也不能自动替代业务预算。

### K4. 怎样测试概率组件

**读这一段是为了解决：** 不用随机模型怎样验证编排？

**原教材的浓缩句：**

> 用脚本化假模型返回固定序列：第一轮读文件，第二轮最终回答。

**展开与落地：**

脚本模型固定输出顺序，验证的是循环分支、历史和调用数；真实模型测试验证在当前配置下是否能按接口提出工具调用。两种结果分开记录。

一个有效反例是篡改回传结果：如果第二轮请求完全不含真实content，测试必须失败。否则你可能只是把两段固定回复串起来，没有验证反馈。

### K5. Agent循环是带退出条件的状态机

**读这一段是为了解决：** 把循环写成状态机能看清哪条退出路径？

**原教材的浓缩句：**

> 最小状态包括任务、消息、待执行调用、观察结果、计数与最终状态。

**展开与落地：**

把状态限定为 running、awaiting_tools、answered、budget_exhausted、failed 等明确集合，未知响应类型直接协议错误；不要把“没识别出来”默认作为最终答案。

图或while都是实现形式。先写清每个状态由什么事实进入、能到哪里、何时不再调用模型，才有资格迁移到框架。

### K6. 观察结果怎样改变下一步

**读这一段是为了解决：** 工具失败应怎样改变下一步输入？

**原教材的浓缩句：**

> Agent区别于固定串联脚本的一点，是下一次动作可由新观察决定。

**展开与落地：**

观察改变下一步，应能用数据说出来：第一次文件不存在，下一轮改路径；读取成功，下一轮引用代码；权限拒绝，下一轮不能绕过授权。不是要求读取模型隐藏推理。

测试可以检查下一次 ToolCall 的参数、最后答案引用或调用序列。这样的外部证据比“模型说它反思了”更可靠。

### K7. 限制步数只是最后保险

**读这一段是为了解决：** 为什么max_steps还不足以识别无进展？

**原教材的浓缩句：**

> max_steps防止无限执行，却无法区分正常深入与原地打转。

**展开与落地：**

max_steps只兜底，不会识别三轮读取同一内容的空转。当前先保证会停；L11再加基于工具参数、代码版本、观察结果的无进展判断。

现在就返回停止原因和已用步数，为后续升级留下接口。不要为演示“成功”把超限改成无限循环，也别将停止直接写成修复失败而不说明原因。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 状态驱动 | 每轮根据response种类转移 | 工具→反馈→最终文本路径真实存在 | 答案结束不等于任务验收成功 |
| 预算 | 模型轮数与工具次数分别定义 | 永远提工具的模型也能终止 | 后续增加无进展检测 |
| 历史 | 把真实ToolResult按ID送入下一轮 | 检查第二次模型实收messages | print日志不等于传回模型 |
| 执行 | 先顺序执行全部提议并返回对应结果 | 多个call无遗漏/混淆 | 暂不实现并发Agent |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
