## 先定位阅读目的与对象

**本课要回答：上一步发生的事实，究竟怎样进入下一次模型请求？**

前提是：L03能执行单个工具，但模型尚未根据工具结果继续下一步。 本课把它推进到：把请求、实际结果、下一轮输入与停止条件串成有界循环。

本文的知识讲解是为完成上述变化服务，不要求先掌握所有相邻技术。范围边界：不把脚本列表当真实LLM；不要把脚本耗尽的IndexError当Agent预算停止。

**文中代码分两种。** [00-example.py](00-example.py)是包中已经提供的概念示例；本课“工程实现/职责路径”是对你项目的目标要求，除L00起始骨架外不表示应用已经生成。未生成时只研究示例；生成后让Codex把职责映射到实际文件，不照猜函数名找代码。

## 1. 先知道这课到底要解决什么

你现在能单独调用模型和工具，但两者还未形成闭环。用户问分页函数在哪里，模型需要先列目录、读文件，再回答。Agent循环做的事是保留对话状态，让模型看到上一步真实结果，然后决定下一步。

### K1. 一次循环里谁拥有什么权力

**读这一段是为了解决：** 模型、宿主、工具各自能决定什么？

模型可以提议下一动作，程序决定哪些动作允许、怎样执行、何时停止。每轮先检查预算与取消，再请求模型；模型返回最终答案就结束，返回工具调用就执行并将结果加入消息，然后进入下一轮。

不要把模型说“测试通过了”当作真实工具事件。模型输出和工具观察来自不同来源，应保留role/type、call_id和来源。

### K2. 为什么必须回传结果

**读这一段是为了解决：** 不回传结果时下一轮少了什么事实？

若你执行了read_file却没有把内容加入下一次模型请求，模型看不到环境变化，只能继续猜。若只回传结果而丢失对应assistant工具调用消息，供应商API可能拒绝，或模型无法对应。适配层负责把统一消息转换为提供商要求的合法顺序。

多轮历史不是字符串不断拼接就够了。工具请求和结果要成对，错误结果也要回传，让模型有机会修正。

### K3. 预算与终止不是附加功能

**读这一段是为了解决：** 哪种终止必须由程序强制执行？

没有终止条件的while True会在模型重复调用时一直花钱。最小版用max_steps和每次调用超时；max_steps定义为模型调用轮数，写入文档并测试。工具失败后可以继续一轮修正，但不能无上限重试。

本课先顺序执行工具。将来并行需要考虑依赖与副作用，不因为一个响应里有多个调用就全部同时执行。

### K4. 怎样测试概率组件

**读这一段是为了解决：** 不用随机模型怎样验证编排？

用脚本化假模型返回固定序列：第一轮读文件，第二轮最终回答。它验证的是编排数据流。再用真实模型跑同一个任务，观察它是否真正选择工具。模拟通过、真实失败说明下一步要查提示词、工具描述或模型能力，不能把编排测试当智能评测。

### K5. Agent循环是带退出条件的状态机

**读这一段是为了解决：** 把循环写成状态机能看清哪条退出路径？

最小状态包括任务、消息、待执行调用、观察结果、计数与最终状态。一次迭代先请求模型；有调用则校验并执行、写回结果、继续；无调用且有可接受答案才进入结束判断。不能把任何自然语言输出当任务成功。后面的修复课会加入独立验收，当前先把“模型结束发言”和“应用任务完成”分开。

### K6. 观察结果怎样改变下一步

**读这一段是为了解决：** 工具失败应怎样改变下一步输入？

Agent区别于固定串联脚本的一点，是下一次动作可由新观察决定。搜索无命中后可能改关键词；读到调用方后可能再读定义；工具拒绝后可能澄清。控制循环由代码掌握，模型在允许行动中提建议。如果每轮都清空工具观察，模型只能重复猜测；如果把全部结果无上限追加，上下文会膨胀，后续要做预算。

### K7. 限制步数只是最后保险

**读这一段是为了解决：** 为什么max_steps还不足以识别无进展？

max_steps防止无限执行，却无法区分正常深入与原地打转。先记录每轮动作与观察，再逐步加入L11的无进展检测。循环中异常也必须形成可解释终态：预算耗尽、工具不可用、等待澄清各不相同。错误时让模型编一段成功总结，会把工程故障掩盖成语言输出。

### 与你已有语言经验的连接

while与break/return差异；Enum表达有限状态；可变list在函数间共享会影响消息历史，注意拷贝边界。

## 深入推演：把知识点连成因果关系

### Agent循环和固定工作流的真正差别

固定流程提前规定下一步：读文件→改文件→跑测试。Agent循环则把本轮观察交回模型，由模型提出下一项允许操作。一次读文件可能发现目标不在这里，因此再搜索；一次测试失败可能揭示新边界，因此重新读代码。这不是“多调用几次模型就更智能”，而是后续动作依赖新观察。你的程序仍负责合法动作集合、预算和终止条件。

手推轨迹：用户任务→模型提议搜索→宿主执行搜索并追加工具结果→模型提议读取命中范围→宿主返回正文→模型给最终解释。若漏掉工具结果，模型实际上没有看到环境反馈；若每轮只保留最新用户输入，前面的调用记录就丢失；若把整个history再次追加到history，会成倍重复。把消息列表长度与每轮新增消息数打印出来，错误往往比看最终回答更明显。

### 终止必须是宿主可检查的状态

至少区分final、tool_calls、needs_input和error；最大步数、截止时间、调用预算属于外部限制，而非提示词请求。`while True`加“请适时停止”不能保证收敛。达到上限时保存已获取的证据和停止原因，不把未完成回答包装成成功。

### 用脚本化模型建立稳定回归

准备一个固定按顺序返回工具提议和最终消息的模拟模型，测试循环是否执行、追加、关联和停止。再注入未知工具、连续调用、空回答、超步数。这样每次失败都能复现。真实模型试验用来判断任务选择质量；模拟循环过关不说明真实模型一定能定位bug。


## 3. 一次完整推演：先预测，再读下一步

1. 第1轮提出search，第2轮收到命中文件后提出read，第3轮给引用答案：状态必须保留两次工具事实。
2. 把read改为权限拒绝：下一轮不能继续引用未读取文件；应改合法行动或结束为受阻。
3. 脚本模型连续返回同一个调用：在max_steps结束为budget_exhausted，不能successful。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 固定工作流 | 步骤已知且顺序稳定 | 少量条件分支即可 |
| Agent循环 | 下一步依赖不确定环境反馈 | 必须有预算与验收 |
| 多Agent | 确有可拆分独立角色与收益证据 | 不是无限循环的补救 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
script = [
    {"kind": "tool", "name": "read", "id": "c1"},
    {"kind": "final", "text": "found"},
]
history = []
for step in range(3):
    reply = script[step]
    history.append(reply)
    if reply["kind"] == "final":
        print("done", step + 1)
        break
    history.append({"kind": "tool_result", "id": reply["id"], "data": "code"})
print([x["kind"] for x in history])
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
python .local/concepts/L04/00-example.py
```

预期观察：

```text
done 2
['tool', 'tool_result', 'final']
```

### 按因果关系理解输出

脚本只含两轮，因为第二轮终止，第三次索引不会执行。工具结果插在两轮模型输出之间。真实循环的reply来自客户端，数据来自注册工具，不能仍用这个静态列表回答所有任务。

现在只修改练习副本`.local/concepts/L04/00-example.py`中的指定输入：在副本中暂时注释追加tool_result的那一行，保持script不变，比较history。此脚本仍会final，所以只能证明反馈缺失，不能证明模型决策变化。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 5. 本课在Code Agent里实际增加什么

- 统一模型响应支持final与tool_calls；扩展L01适配器和fake，保留旧纯文本请求兼容路径。
- 状态包含messages、step_count、max_steps、termination_reason；模型轮次与工具调用次数分别记录。
- 每个工具请求及对应结果按提供商合法顺序回传；同一轮多个请求先顺序执行，保留call_id。
- 支持final_answer、step_limit、model_error终止；不把step_limit包装成任务已完成。
- 加入脚本化客户端以检查真实传入消息；真实模式必须使用已接入客户端。

职责落点不是已存在断言；具体建议、当前源码确认方法见[本课文件导航](00-本课目的与文件导航.md)第3节。
