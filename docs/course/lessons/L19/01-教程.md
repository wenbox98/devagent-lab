## 先定位阅读目的与对象

**本课要回答：浏览器连接断开以后，任务还在哪里，谁拥有它的真实状态？**

前提是：单次Agent可能运行较久，但HTTP连接不能承担任务的完整生命周期。 本课把它推进到：先持久化任务身份再响应，worker领取与状态迁移可并发校验。

本文的知识讲解是为完成上述变化服务，不要求先掌握所有相邻技术。范围边界：不把202当已完成；状态字典例子不验证数据库或HTTP服务。

**文中代码分两种。** [00-example.py](00-example.py)是包中已经提供的概念示例；本课“工程实现/职责路径”是对你项目的目标要求，除L00起始骨架外不表示应用已经生成。未生成时只研究示例；生成后让Codex把职责映射到实际文件，不照猜函数名找代码。

### K1. 先持久化任务，再返回ID

**读这一段是为了解决：** 返回task_id以前必须先存下什么？

POST创建任务后返回202和task_id，表示接受，不表示修复成功。执行器从持久队列领取任务；GET查询事实；事件接口显示进度。连接断开后，任务仍有明确状态。

先做单执行器和数据库表即可，不必立即上MQ。关键是进程重启后queued任务仍可找到，不能只放进内存列表。

### K2. 状态迁移需要条件

**读这一段是为了解决：** 两个worker怎样避免同时领取？

queued可被领取为running；running可完成、失败或等待输入。更新使用WHERE status=旧状态或version=旧版本，避免两个执行器都领取同一任务。即使当前只一个执行器，也要理解数据库是状态事实来源。

记录事件序号帮助客户端断线后从last_seq续读；前端显示与执行状态应来自同一套事实，不能根据HTTP超时擅自标执行失败。

### K3. 创建幂等从Python接口开始

**读这一段是为了解决：** 重发同一execution_id为何还需检查请求内容？

未来Java调用Python遇到超时需要重试。因此Python创建接口接受稳定execution_id/提交键，同ID同内容返回同一任务，同ID不同内容冲突。这样Java接入时无需靠运气避免重复执行。

初期仅在本机访问。后面Java层做用户鉴权，Python内部接口仍需受保护，不应直接向任意外部用户暴露工具执行能力。

### K4. HTTP生命周期与任务生命周期解耦

**读这一段是为了解决：** HTTP连接断开为什么不等于任务失败？

长任务不适合靠一个连接一直等结果。提交返回稳定task_id与查询位置，后台worker推进状态，查询读取持久结果。连接断开只代表客户端不再等待，不代表任务取消。提交成功也只意味着任务已被可靠接受，不能提前宣称执行成功。前端轮询或事件通知只是观察通道，不是任务真相来源。

### K5. 状态转换要保护不变量

**读这一段是为了解决：** 终态和条件更新要保护什么不变量？

queued→running→succeeded/failed/cancelled等转移受条件约束，终态不能被迟到回调覆盖。数据库更新带expected_version或expected_state，避免两个worker同时占用。至少一次派发常比恰好一次容易实现，执行端依靠稳定操作ID去重。内存队列丢失时需要从持久任务记录恢复，而不是把列表当可靠队列。

### K6. 处理数据库与派发之间的缝隙

**读这一段是为了解决：** 保存成功但派发失败时任务如何找回来？

先写数据库再发消息可能在中间崩溃；先派发再写数据库可能执行了却没有任务记录。教学阶段可让worker扫描持久queued记录；更复杂系统用同事务写outbox再异步投递。无论哪种都要定义重复派发、未派发和执行中失联如何检测，不能只画一个队列图就认为可靠。

### 与你已有语言经验的连接

FastAPI等框架只提供HTTP入口，不自动提供持久任务执行；async def不代表CPU工作自动并行。

## 深入推演：把知识点连成因果关系

### HTTP请求与任务生命周期分离

用户提交一次修复可能耗时很长。接口应返回已接收的任务标识，执行器按状态机推进，用户再查询进度。客户端断开不等于任务取消，网关超时也不等于执行失败。响应需要明确语义：accepted只说明提交记录已成立，不意味着后台必然成功。

### 状态迁移要有唯一所有者

Python执行服务拥有queued、running、waiting_input和终态等事实。提交接口、worker和取消请求通过版本或条件更新协调，不能任意覆盖。若取消与成功同时发生，要定义可接受的顺序：例如以最后一次已提交的终态为准，并说明副作用可能已发生。Java以后只保存提交与映射，不能把一次查询超时改写成执行failed。

### “持久化了任务”不等于能恢复任务

数据库里有一行running，worker崩溃后仍可能永久卡住。需要失效检测、认领/租约或教学版单执行器恢复流程，并核对上一次外部副作用是否已执行。本版经过F05后可以采用LangGraph检查点，但HTTP任务状态、图状态与工作区实际内容仍须有明确映射，而不是存在三个互相矛盾的状态源。


## 3. 一次完整推演：先预测，再读下一步

1. 提交后连接立即断开：查询task_id仍能看到queued或running，任务不自动消失。
2. 两个worker抢同任务：带版本的状态更新只允许一个获得本次执行权。
3. 在持久化成功后、派发前杀进程：重启扫描queued并恢复；确认不会新增第二个业务任务。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 同步接口 | 任务短且耗时可控 | 受连接超时限制 |
| 持久表+worker扫描 | 教学和中低规模起点 | 轮询与锁需控制 |
| 队列+outbox | 吞吐和解耦需求明确 | 引入重复消费与运维复杂度 |

```python
allowed = {
    "queued": {"running", "cancelled"},
    "running": {"succeeded", "failed", "waiting_input", "cancelled"},
    "waiting_input": {"queued", "cancelled"},
}
def can_move(old, new):
    return new in allowed.get(old, set())

print(can_move("queued", "running"))
print(can_move("succeeded", "running"))
```

## 5. 本课在Code Agent里实际增加什么

- API固定POST /tasks接execution_id、request_hash、task；GET /tasks/{id}；GET /tasks/{id}/events?after_seq=；POST /tasks/{id}/cancel。
- 创建返回202；同ID同内容返回已有任务、异内容409；持久化后再响应。用户身份归属后续Java传可信主体，不从任意请求body自认。
- SQLite等单机数据库存任务、事件、状态版本；单独worker领取任务；领取与迁移用条件更新/事务。
- 先轮询事件即可，SSE可选；事件有seq，断线不改变任务成败。取消完整行为下课实现，当前接口可标记请求。

职责落点不是已存在断言；具体建议、当前源码确认方法见[本课文件导航](00-本课目的与文件导航.md)第3节。

## 8. 面试时如何解释你做过的事

**为什么返回202？**

表示已接受异步处理，具体完成状态通过任务资源查询。

**为什么不用一个后台线程就完事？**

线程可执行工作，但若缺少持久状态，重启和连接断开后的事实难恢复。
