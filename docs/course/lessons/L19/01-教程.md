## 0. 这课为什么存在

Agent任务可能持续很久，HTTP连接不应承担任务的全部生命周期。L19 把提交、持久状态与后台执行拆开，让断线后仍能查询同一个任务。

本课从小规模持久任务表和worker领取开始，不为“架构完整”立刻引入多套消息队列。

## 1. 一条具体方案：从输入到结果

### 先持久化，再返回202

提交接口认证主体，校验输入并生成/核对稳定提交身份，将queued任务提交到数据库后返回task/execution ID。worker另行从持久存储领取任务，HTTP请求结束不终止任务。

查询接口按可信主体授权读取状态和事件；客户端断线后用同一ID继续查，不重新创建一次业务操作。

### 任务领取用条件更新

```sql
UPDATE tasks
SET state = 'running', version = version + 1
WHERE execution_id = :id AND state = 'queued' AND version = :expected_version;
```

这是逻辑SQL，参数占位符按实际驱动调整。受影响行数为1才领取成功，为0说明状态已变，不能继续执行。多worker可使用实际数据库支持的事务/行锁策略，不能先SELECT再无条件UPDATE。

### 数据库与派发之间怎么办

小规模版让worker扫描持久queued任务；这样提交成功后进程在“发消息”前崩溃，任务仍可被后续扫描发现。若接消息队列，采用持久outbox+重复投递可幂等处理，而不是宣称DB事务与MQ天然原子。

提交幂等绑定主体、key和规范化请求hash；同key不同body冲突，重复同请求返回同一执行身份。L20再加取消/恢复，当前不把断线自动当取消。

### 先查再更新为什么会重复领取

workerA和B都SELECT看到queued，然后各自无条件UPDATE running，两者都可能执行。正确的关键不是多写一次查询，而是把资格条件放进数据库更新/锁定事务，并检查结果。

条件更新返回rowcount=1才获得资格；rowcount=0说明已被领取或状态变化。新增机制实验用SQLite多线程竞争同一行，实际断言只有一个成功领取；它不因此证明任务副作用或分布式恢复已幂等。

### 返回ID前后两个故障

落库前崩溃：请求未被接收，客户端同key重提可创建。落库后、响应前崩溃：任务已存在，重提必须返回原记录。靠请求线程是否存活无法区分，要查持久提交身份。

工作队列与数据库分离后又多一个派发窗口。先用数据库扫描是小规模可实施选择，不是所有项目都要立刻上MQ。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 先持久化任务，再返回ID

**读这一段是为了解决：** 返回task_id以前必须先存下什么？

**原教材的浓缩句：**

> POST创建任务后返回202和task_id，表示接受，不表示修复成功。

**展开与落地：**

数据库提交成功是返回已接收的前提。内存队列先入队再返回ID，进程崩溃可能丢任务；数据库未提交就返回则客户端拿到不存在的ID。

演示必须重启后仍可查询任务，而不是同进程字典保持了几秒。缺数据库环境就保留对应验收blocked。

### K2. 状态迁移需要条件

**读这一段是为了解决：** 两个worker怎样避免同时领取？

**原教材的浓缩句：**

> queued可被领取为running；running可完成、失败或等待输入。

**展开与落地：**

状态不是任意字符串，queued→running需要领取证据，running→succeeded需要验收，终态不能被旧worker写回running。

用预期状态/版本做条件更新并检查影响行数。模型不能自行调用“把状态设为成功”的无条件接口。

### K3. 创建幂等从Python接口开始

**读这一段是为了解决：** 重发同一execution_id为何还需检查请求内容？

**原教材的浓缩句：**

> 未来Java调用Python遇到超时需要重试。

**展开与落地：**

Python任务接口本身就需要幂等，因为Java或客户端可能重试提交。键绑定主体和请求内容，不能仅使用任务描述字符串判断重复。

并发同key由唯一约束或等价原子机制裁决。查无再插入在并发下会竞态，必须处理唯一冲突并查询原结果。

### K4. HTTP生命周期与任务生命周期解耦

**读这一段是为了解决：** HTTP连接断开为什么不等于任务失败？

**原教材的浓缩句：**

> 长任务不适合靠一个连接一直等结果。

**展开与落地：**

HTTP负责接收/查询，不长期占一个连接直到Agent完成。任务状态与事件可由轮询或流式通知展示，但通知丢失不改变持久事实。

断线仅表示客户端暂时没接收；是否取消要有单独协议。服务重启恢复待执行任务也不能依赖还活着的请求线程。

### K5. 状态转换要保护不变量

**读这一段是为了解决：** 终态和条件更新要保护什么不变量？

**原教材的浓缩句：**

> queued→running→succeeded/failed/cancelled等转移受条件约束，终态不能被迟到回调覆盖。

**展开与落地：**

成功必须来自对应执行与验收版本；状态事件有序号，更新有版本条件。迟到结果不能覆盖新状态。

测试两个worker领取同一任务，最多一个获得执行资格；再模拟旧版本完成回调被拒绝。调用次数与持久状态都要检查。

### K6. 处理数据库与派发之间的缝隙

**读这一段是为了解决：** 保存成功但派发失败时任务如何找回来？

**原教材的浓缩句：**

> 先写数据库再发消息可能在中间崩溃；先派发再写数据库可能执行了却没有任务记录。

**展开与落地：**

“存任务成功，但派发失败”是经典间隙。小版用数据库扫描直接消除独立消息派发步骤；有MQ时用outbox记录待投递消息，并允许重复投递。

Outbox保证有记录可重发，不保证worker效果天然只一次。仍需操作身份、领取和幂等执行。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 接收 | 持久queued后返回ID/202 | 重启后任务仍可查询 | 断线不等于取消 |
| 领取 | 预期状态/版本条件更新 | 并发领取最多一成功 | SELECT再无条件UPDATE不够 |
| 派发 | 小版DB扫描；MQ版outbox | 提交后派发前崩溃不丢任务 | 投递重试不等于效果幂等 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
