## 0. 这课为什么存在

模型能搜索和阅读以后，遇到含糊任务不一定该立刻执行，也不一定该把所有问题都问回用户。L06 把“是否澄清”做成一个可解释的决策：缺的信息是否会改变高风险动作。

成品不是一个万能聊天提示词，而是任务目标、约束、验收与等待状态，以及一个确定性只读流程作为对照。

## 1. 一条具体方案：从输入到结果

### 同一句“优化分页”，为何不能总是直接改

“帮我解释分页的实现”可以先只读；“优化分页，不能改接口，指标是P95低于某值”已有比较明确的约束；“优化分页”却没有说性能还是正确性，贸然写代码可能解决错问题。

本课先将描述整理为目标、约束、验收、已确认假设。缺少只影响展示方式的信息可采用低风险默认值并说明；缺少会改变写入范围、对外接口或验收标准的信息则提出一条聚焦问题。

### 不依赖玄学评分的最小规则

```text
下一步只读且可回退 → 可以收集更多证据
下一步有副作用，关键约束缺失 → waiting_input
目标和验收明确，流程固定 → 确定性workflow
需要依据观察选择多步工具 → Agent loop
```

这是本课的教学决策表，不是所有业务永远通用的最优规则。实现必须返回“缺哪项、为什么影响动作、等待哪个回答”，而不只给 ask=True。

### 等待之后怎样继续

保存 task_id、已有证据、待确认字段及当前状态。用户回答后更新相应字段并恢复决策，不重新创建另一任务。测试应确认等待期间不继续调用写工具，也不循环追问同一条已确认信息。

### 一个可执行的澄清判断，不依赖模型自评分

```python
def decide(next_action, missing, has_side_effect):
    critical = {"allowed_scope", "acceptance", "write_permission"}
    blocking = critical.intersection(missing)
    if has_side_effect and blocking:
        return {"state": "waiting_input", "missing": sorted(blocking)}
    if next_action in {"list_files", "read_file"}:
        return {"state": "can_gather_evidence"}
    return {"state": "ready_for_policy_check"}
```

这是规则示范，字段来自宿主定义，不是放任模型自报has_side_effect=false。最后的ready仍需具体操作的授权与预算校验。

你会发现这段并不复杂。工程价值在于把原本隐藏在提示词里的判断变成可测试条件：给定缺失字段和下一动作，应得到稳定状态。

### 为什么需要“保存问题”

不能只返回“请补充信息”就结束所有状态。等待记录至少对应task_id、question_id、缺失字段和当前证据版本。恢复时回答属于哪个问题要检查，否则晚到的答案可能套到更新后的任务。

当前课先本地构造等待与恢复状态；服务化时再把它持久化。不要为等待用户让一个HTTP线程无限阻塞。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 明确目标、约束与验收

**读这一段是为了解决：** 优化目标怎样转成可判定的验收？

**原教材的浓缩句：**

> 目标说明要改变什么；约束说明不能破坏什么；验收说明如何知道成功。

**展开与落地：**

把自然语言要求拆成可核验字段。例如 goal=修正第一页偏移，constraint=函数签名不变，acceptance=第一页/第二页测试通过。模型摘要不能悄悄删除“签名不变”。

程序至少验证字段是否存在、来源是否为用户确认或推测。推测放 assumptions，不写成 confirmed。后面执行和验收都从同一份约束读取。

### K2. 用可逆性与损失判断要不要问

**读这一段是为了解决：** 可逆探查与不可逆改动的澄清门槛为何不同？

**原教材的浓缩句：**

> 低成本、可撤销的内部查看可以先做；改API语义或删除数据应有明确授权和验收。

**展开与落地：**

不是遇到未知就问。先看错误决定的损失与可逆性：只读定位成本小，可以先读；删文件、提交外部订单、扩大授权则需要明确条件。

用具体反例测试规则：缺用户偏好但可安全只读不应卡住；缺是否允许写入就不能擅自改。不要依赖模型自报“我很有把握”替代规则。

### K3. 固定工作流也是一种合适方案

**读这一段是为了解决：** 为什么不是每个任务都需要自主Agent？

**原教材的浓缩句：**

> 如果任务总是“按指定测试运行并返回结果”，程序流程已知，直接调用工具即可。

**展开与落地：**

若步骤已知是列目录→读指定文件→返回行段，直接写工作流更容易验证。Agent适合下一步依赖新证据的情况，不是所有功能都必须交给模型规划。

对照同一任务的固定流程与 Agent：比较是否满足任务、调用数、耗时和失败点。不能只因 Agent 看起来智能就忽略多余调用。

### K4. 把澄清变成状态

**读这一段是为了解决：** 等待输入如何保存而不丢原任务？

**原教材的浓缩句：**

> 需要补充信息时返回waiting_input和具体问题，保存已有证据。

**展开与落地：**

waiting_input 是可查询状态，包含问题ID和待确认项，不是函数阻塞到用户回来。恢复时以原任务身份更新，不重复已完成的副作用。

测试提交答案前无后续工具调用，提交后从保存的节点继续；过期或属于别的任务的答案不能被套用。先本地实现状态，服务化在L19以后接入。

### K5. 澄清是降低决策风险的一次信息获取

**读这一段是为了解决：** 哪次提问会真的改变错误决策的风险？

**原教材的浓缩句：**

> 不是遇到任何缺失字段都问。

**展开与落地：**

澄清的价值是减少会改变决策的不确定性。问题应直接区分两个行动，例如“只解释还是允许修改？”比“请提供更多信息”更能推进任务。

不要一次问十个无关问题。先问阻止下一步安全行动的一个条件；已能从仓库或前文查到的内容应先查，不重复向用户索取。

### K6. 把任务描述转成可执行约束

**读这一段是为了解决：** 模糊需求中的哪一个字段必须明确？

**原教材的浓缩句：**

> “修分页”包含目标、允许范围、不可破坏事项与验收方法。

**展开与落地：**

执行代码需要结构化约束，不只是长提示词。限制可改文件、禁止改签名、预算等应有明确字段和验证位置；模型计划只是建议。

新信息与旧约束冲突时暂停并说明冲突，不能默认新文本覆盖全部事实。后续上下文压缩也必须保留这些硬约束。

### K7. 规划与执行的职责

**读这一段是为了解决：** 计划能否自行扩大执行权限？

**原教材的浓缩句：**

> 计划是可检查的行动顺序，不是结果证据。

**展开与落地：**

规划说明打算做什么，执行产生真实观察。plan_step completed 只有收到工具结果才能更新，不可依据模型文字自行勾选。

如果计划不适用，应在新证据下修订，但不得改写用户验收标准。用一条工具失败后改变计划的测试证明循环真的使用反馈。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 是否询问 | 按缺失信息对下一步风险的影响决策 | 只读不停、危险动作缺条件则等待 | 不是置信度越高越可越权 |
| 等待恢复 | 保存任务和待确认字段 | 回答前调用数不增长，回答后保留证据 | 不阻塞一个HTTP请求等待人工 |
| 工作流选择 | 固定步骤用workflow，分支依证据用Agent | 同任务比较任务成功与资源成本 | 框架不是选型理由 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
