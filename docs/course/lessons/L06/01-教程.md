## 先定位阅读目的与对象

**本课要回答：什么信息会改变验收目标，必须问；什么可以先从仓库查到？**

前提是：L05能够找到代码，但“优化分页”仍未说明要改变什么。 本课把它推进到：把目标、约束、验收与关键缺失项分开，选择澄清、探查或固定流程。

**文中代码分两种。** [00-example.py](00-example.py)是包中已经提供的概念示例；本课“工程实现/职责路径”是对你项目的目标要求，除L00起始骨架外不表示应用已经生成。未生成时只研究示例；生成后让Codex把职责映射到实际文件，不照猜函数名找代码。

### K1. 明确目标、约束与验收

**读这一段是为了解决：** 优化目标怎样转成可判定的验收？

目标说明要改变什么；约束说明不能破坏什么；验收说明如何知道成功。比如“修复page_no=1返回第二页的问题，保持函数签名”已经足够明确。相比之下“优化接口”缺少优化维度，无法定义是否达标。

先读取允许的代码和测试，已有事实能补齐的就不重复问用户。关键歧义影响外部行为时，再问一个能区分方案的问题。

### K2. 用可逆性与损失判断要不要问

**读这一段是为了解决：** 可逆探查与不可逆改动的澄清门槛为何不同？

低成本、可撤销的内部查看可以先做；改API语义或删除数据应有明确授权和验收。不要把任务中所有空缺都看成阻塞。把假设写进结果，让用户知道基于什么默认值推进。

不建议让一个未经校准的模型confidence直接决定是否追问。更可解释的起点是检查必要字段、已知约束与候选解释是否冲突。

### K3. 固定工作流也是一种合适方案

**读这一段是为了解决：** 为什么不是每个任务都需要自主Agent？

如果任务总是“按指定测试运行并返回结果”，程序流程已知，直接调用工具即可。若需要根据搜索结果探索不同文件，Agent更有价值。可以让程序固定外部边界，模型仅决定内部搜索步骤，不必全程自由规划。

本课比较同一组任务上的固定流程与Agent，记录完成率、调用次数和耗时。差异来自任务分布，不能得出某一种形式永远更好。

### K4. 把澄清变成状态

**读这一段是为了解决：** 等待输入如何保存而不丢原任务？

需要补充信息时返回waiting_input和具体问题，保存已有证据。拿到答案后继续原任务，而不是忘掉上下文重新开始。服务化前可以用CLI回传答案模拟，后面迁移到任务状态机。

### K5. 澄清是降低决策风险的一次信息获取

**读这一段是为了解决：** 哪次提问会真的改变错误决策的风险？

不是遇到任何缺失字段都问。先判断缺少的信息是否会改变行动、能否从授权环境可靠获得、错误行动能否低成本撤销。影响公共接口或业务语义且无法从测试确认时应问；目录已指定且能安全搜索时可先取证。把问题压缩成一个决定分支的条件，比让用户重复描述整个需求更有效。

### K6. 把任务描述转成可执行约束

**读这一段是为了解决：** 模糊需求中的哪一个字段必须明确？

“修分页”包含目标、允许范围、不可破坏事项与验收方法。明确哪些是假设，哪些是用户确认或测试证明的事实；把不可改签名等硬约束保存为字段，而不只是提示词中的一句话。澄清结果更新任务状态，并使旧假设失效，否则模型容易在后续仍使用最初猜测。

### K7. 规划与执行的职责

**读这一段是为了解决：** 计划能否自行扩大执行权限？

计划是可检查的行动顺序，不是结果证据。读取→修改→测试的主流程可固定，文件选择与局部修复允许模型决定。不要因为用了模型就把每个确定步骤也交给它选择。写操作前核对前置条件，执行后观察结果，失败时更新计划；单纯生成更长计划不一定改善成功率。

### 与你已有语言经验的连接

Optional/None表达未确定状态；不要用False同时代表未知与明确否定；条件分支先处理未知。

## 深入推演：把知识点连成因果关系

### 澄清不是礼貌话术，而是决策依赖

“修一下分页”可能欠缺页码从0还是1开始的契约；“修复这个明确失败的测试”则可能已经包含足够要求。你要识别哪些缺失信息会改变实现和验收。可以先从README、现有测试和调用点取证，证据仍互相矛盾时再问一个关键问题。不能把每个任务都反问一遍，也不能用自己熟悉的默认值覆盖明确存在的歧义。

### 用风险与可逆性判断能否先行动

只读定位通常容易撤回，改公共接口或删除文件则可能改变外部行为。因此不确定时可以先做受控只读调查，而不是提前进行写操作。记录假设与证据出处：来自用户明确要求、项目测试，还是暂定教学默认。用户确认之后，更新的是任务约束，不是只在聊天记录里留一句话。

### 等待输入应保留可恢复的任务状态

任务暂停时至少保存任务ID、问题、已确认约束、当前证据、尚未执行的动作。收到补充后核对版本再继续，而不是从头重复所有操作。先把这套状态用简单对象表达，后续F06再映射到LangGraph的中断和恢复。你会看到框架解决调度与状态承载，不能替你决定什么问题值得问。


## 3. 一次完整推演：先预测，再读下一步

1. 用户只说第一页错了，测试明确第一页从1开始：先读取测试，不必重复提问。
2. 仓库同时有0基与1基两个外部API：信息会改变修复语义，问“目标接口采用哪种页码约定”。
3. 用户确认后持久记录page_base=1，再检查生成补丁与测试是否一致；口头确认未进入执行输入等于没生效。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 直接执行 | 条件明确且行动在授权范围 | 保留证据 |
| 先检索 | 信息可由环境获得 | 限制成本 |
| 澄清 | 关键语义未知且影响行动 | 问题应能改变具体分支 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
def choose_action(task):
    if task.get("operation") == "run_named_test" and task.get("test"):
        return "workflow"
    if task.get("operation") == "optimize" and not task.get("metric"):
        return "ask_metric"
    return "agent"

print(choose_action({"operation": "run_named_test", "test": "test_page"}))
print(choose_action({"operation": "optimize"}))
print(choose_action({"operation": "fix", "bug": "wrong first page"}))
```

## 5. 本课在Code Agent里实际增加什么

- 建立TaskGoal(goal,constraints,acceptance,assumptions)和Clarification(question,missing_fields)结构；保留原任务。
- 明确分页修复应直接推进；含关键歧义的优化任务进入waiting_input；问题一次只问关键缺失项。
- 实现固定只读任务流程与已有Agent两条路径，使用相同工具和样例对照。
- 补充信息后延续已有证据，限制重复提问；无需先建Web服务。

职责落点不是已存在断言；具体建议、当前源码确认方法见[本课文件导航](00-本课目的与文件导航.md)第3节。

### 看生成代码的具体顺序

1. 找本课演示入口，确认它调用真实应用函数；期望值不能写死成observed。
2. 找输入对象与校验，标记哪些字段可信、哪些来自模型或用户。
3. 沿正常案例走主函数、下游调用、状态更新与返回。
4. 沿失败案例找到第一个不同分支，并核对工具调用次数/文件/状态。
5. 找测试，说明它能抓住哪种错误实现；再看Git diff为什么需要这些变更。

## 8. 面试时如何解释你做过的事

**为什么不是问题越多越安全？**

无效追问阻碍任务，且不能解决执行层权限问题。

**是否所有业务都应做Agent？**

流程确定时直接程序更易控制，只有需要动态决策的部分才值得引入。

补一句反事实：如果“关键语义未知且影响行动”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
