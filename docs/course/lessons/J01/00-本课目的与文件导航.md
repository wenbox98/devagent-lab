## 1. 为什么现在学这一课

**当前条件（不是对你进度的断言）：** Python有稳定execution_id与任务接口，Java现在接受用户提交。

**本课问题：** 为什么Java事务回滚了，也不能推断Python任务被撤销？

**期望变化：** 把本地提交意图、远程派发和去重分开；响应丢失时沿同一执行身份核对。

**不做这一步的风险：** Java重试提交与Python实际接受状态不一致，一个外部请求产生多个逻辑执行，线程安全容器也不能单独保证跨服务幂等。

顺序前置：[L20本课目的](../L20/00-本课目的与文件导航.md)。前置是能力条件，不是“看过文档”即可；由Codex核对现有源码/测试。 后续[J02](../J02/00-本课目的与文件导航.md)继续使用本课产物。

**本课不负责：** ConcurrentHashMap示例不是PostgreSQL唯一约束或分布式事务实验。

## 5. 读不懂时，带着什么目的查资料

下列问题与[教程](01-教程.md)的知识段一一对应。查到能回答该问题、能指出观察证据即可先回到实验，不要求把官方站点读完。

| 本课知识段 | 为什么讲：你要解决的具体问题 |
| --- | --- |
| 把提交身份和执行身份分开 | 用户重试身份与远端执行身份怎样关联？ |
| 事务边界要小且明确 | 为什么不能把远程等待包进长事务？ |
| 状态并发用条件更新 | 并发更新时怎样避免覆盖新状态？ |
| 本地事务无法回滚远程已完成操作 | 本地rollback为什么无法撤销Python任务？ |
| 唯一约束是并发幂等的最后裁判 | 唯一约束怎样裁决两个并发同键提交？ |
| Outbox是可靠派发记录，不是恰好一次魔法 | 派发记录能保证重试，但为何不能消灭所有重复？ |

可复制检索词：`Java local transaction outbox unique constraint idempotency`。优先使用[本课教程末尾的官方参考](01-教程.md)和[官方阅读路线](../../09-技术版本与官方阅读路径.md)。这些链接沿用已有教材来源；本轮聚焦结构与指代，未重新核验所有网页或依赖版本。

## 6. 本课完成后要留下什么

**项目阶段怎样证明风险已被处理：** 模拟Python接受后响应丢失，再重试提交；按execution_id确认没有第二个逻辑任务。

要能串起：**可信主体+幂等键 → request_hash唯一约束 → 稳定execution_id → Python提交 → 查询核对。**

具体证据看：映射中保存的body与冲突判断所需信息；真实服务需另核对request_hash。
