## B. 当前问题与选定基础方案

Java入口把任务交给Python服务时，本地数据库事务无法回滚远端已经开始的执行。本课落实提交幂等与小事务，而不是在Service方法加@Transactional就结束。

目标是同一用户的同一提交意图，无论超时重试或并发提交，都关联同一个Python执行身份。

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 幂等 | owner+key唯一，绑定规范化bodyhash | 并发同意图同execution | 不同body不能复用 |
| 事务 | 意图/结果短事务，HTTP在外 | 慢远程不长期占连接 | 本地回滚管不到远端 |
| 派发 | outbox可重发+下游幂等 | 丢响应重提不多执行 | 消息次数不是效果次数 |


这些具体选择用于解释并实现本课，不要求一次实现生产强化项。当前项目若已实现不同但等价的合同，先说明差异和兼容性，不强制搬文件。

## D. 必须产生并执行的案例

**以下是待实现的接口合同，不是本包已交付的完整应用命令。** 先确保生成/复用入口并给出实际位置，再运行。执行目录：学习项目根目录（能同时看到 `devagent/` 和 `docs/course/` 的目录）。分析模式不要运行。

生成JUnit测试类J01LessonTest，支持-Dlesson.case选择下面某个案例；未指定时执行所有案例。测试类必须存在并实际运行，不允许surefire因找不到测试而跳过。外部PostgreSQL/Python未准备好时报告blocked并给精确准备命令，不用内存模拟结果冒充联调通过。进程退出0表示断言符合预期，不意味着每次被测请求业务成功；例如预期409的案例通过也返回测试成功。

每个案例都必须有可控触发方式、真实观测值与断言，不能只打印预期字符串：

| 案例名 | 怎么触发 | 必须实际验证的结果 |
| --- | --- | --- |
| same-key | 顺序同用户同键同请求 | 同一任务和执行ID |
| body-conflict | 同用户同键不同请求 | 409，不创建第二执行 |
| concurrent | 20个并发请求同键 | 数据库一条逻辑提交，Python最多一个逻辑执行 |
| lost-response | Python接受后模拟响应丢失，重启Java投递器 | 同ID核对恢复，不重复任务 |

本课演示命令（在仓库根目录逐条执行）：

```bash
mvn -f java-task-service/pom.xml -Dtest=J01LessonTest -Dlesson.case=same-key test
mvn -f java-task-service/pom.xml -Dtest=J01LessonTest -Dlesson.case=body-conflict test
mvn -f java-task-service/pom.xml -Dtest=J01LessonTest -Dlesson.case=concurrent test
mvn -f java-task-service/pom.xml -Dtest=J01LessonTest -Dlesson.case=lost-response test
```

本课自动化验收：

```bash
mvn -f java-task-service/pom.xml -Dtest=J01LessonTest test
```

先检查测试是否被实际发现且数量大于零，再解释结果。对模型随机性不要求某个措辞逐字一致；验证任务条件、工具事实与最终状态。确定性编排测试用模拟客户端；真实模型表现单独标记，不混用。

演示必须调用实际业务函数；不在demo里直接打印常量成功。Python演示JSON包含lesson、case、observed、非空checks和verified。0表示该案例的预期被真实验证，1表示断言失败，2表示环境blocked；业务拒绝与演示进程成功是两种不同状态。Java案例提供实际JUnit断言与执行数。

零测试或全部skip不计为通过。框架、模型和真实服务验证单独报告，不能用标准库样例替代。
