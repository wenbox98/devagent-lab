### K1. 把提交身份和执行身份分开

**读这一段是为了解决：** 用户重试身份与远端执行身份怎样关联？

外部用户提供或客户端生成Idempotency-Key，Java按用户/租户+key去重；内部execution_id稳定映射到Python任务。同键同内容返回同一逻辑任务，同键不同内容409。请求指纹必须由规范化内容产生，字段顺序变化不应被误判为不同请求。

不能先查有没有记录，再决定插入，而不加唯一约束：两个线程都可能查不到。数据库唯一键让竞争最终有一个赢家，失败者读取已有记录并比较内容。

### K2. 事务边界要小且明确

**读这一段是为了解决：** 为什么不能把远程等待包进长事务？

Java数据库事务可以保证提交记录与本地状态更新，但不能自动撤销Python已经接受的任务。推荐先持久化execution_id与提交意图，事务提交后请求Python；失败或未知时用相同ID核对或重试。

这类似最小的可靠投递状态表。worker可扫描未确认意图并补发；无需本课立即引入MQ，但必须承认跨服务是多步协议。不要持有数据库连接等待数分钟Agent执行。

### K3. 状态并发用条件更新

**读这一段是为了解决：** 并发更新时怎样避免覆盖新状态？

UPDATE ... WHERE status='pending'或version=旧值，并检查影响行数。只在Java内存中if判断后无条件更新无法防多个实例竞争。Python拥有执行状态，Java保存提交映射与展示投影，不创建第二套互相矛盾的执行真相。

训练时要有并发请求与响应丢失测试，单线程连续调用成功不足以证明幂等。

### K4. 本地事务无法回滚远程已完成操作

**读这一段是为了解决：** 本地rollback为什么无法撤销Python任务？

Java数据库事务提交失败，不会自动撤销Python已创建的任务。把远程调用放进@Transactional只能延长锁和连接占用，不能创造分布式原子性。先建立本地业务请求与稳定execution_id，再异步或事务外提交；远端按同ID幂等接收。未知结果靠查询对齐，不把HTTP失败直接等同于远端未执行。

### K5. 唯一约束是并发幂等的最后裁判

**读这一段是为了解决：** 唯一约束怎样裁决两个并发同键提交？

先select没有记录再insert的两请求可能同时通过检查。对tenant_id与idempotency_key建立唯一约束，并保存request_hash、状态与远端ID。冲突后读取已有记录：同内容返回同任务，异内容返回冲突。应用层锁只覆盖单实例，不能替代数据库约束；去重保留期必须覆盖用户可重试窗口。

### K6. Outbox是可靠派发记录，不是恰好一次魔法

**读这一段是为了解决：** 派发记录能保证重试，但为何不能消灭所有重复？

同一个数据库事务写任务与待派发事件，提交后由worker投递。投递成功但来不及标已发送仍可能重投，所以消费方仍需幂等。事件包含稳定execution_id与请求哈希，重试复用；失败和积压可观察。先用表扫描实现最小可靠流程，有明确需求再加MQ，不为了架构图好看增加中间件。

### 与你已有语言经验的连接

Java重点：事务边界、唯一约束异常、record DTO、请求规范化哈希；Python执行端需实现同一幂等契约。

## 深入推演：把知识点连成因果关系

### 本地事务不能覆盖远程Python执行

Java开启数据库事务，写提交记录，调用Python，再提交事务。若Python已接受任务而Java事务回滚，远程任务并不会自动回滚；反过来，Java提交成功也不能保证远程请求真的到达。`@Transactional`管理的是其参与的本地事务资源，不是整个网络世界。这里必须设计可查询、可重试的提交协议。

### 用唯一约束表达幂等，而不是只靠先查再插

同一owner与idempotency_key建立唯一约束，并保存规范化请求指纹。两个并发请求都可能先查不到，所以“先SELECT再INSERT”本身不能去重；唯一约束负责仲裁，应用正确处理冲突后读取既有记录。同键不同body必须返回语义冲突，不能给用户另一项任务的ID。

### 用持久提交记录和核对处理不确定性

先保存待分发记录，分发时使用稳定execution_id或对端支持的幂等键；远程超时则查询对端已知标识，而不是生成新ID再创建。教学可用数据库轮询分发，不强制引入MQ。若对端没有查询或幂等能力，就不能仅在Java端声明端到端不重复。

### 迁移回L10的同一个问题

L10的“文件写完但响应丢失”变成“Python任务已建但Java没收到结果”。你要复用的是结果三态、稳定操作键与核对方法，不是复制文件工具代码。这才是举一反三：识别相同失败结构，换成适合当前边界的具体机制。


## 3. 一次完整推演：先预测，再读下一步

1. 两个并发提交同key同内容：数据库一条任务；两请求得到同task_id，远端执行次数至多一次。
2. 远端创建成功后响应丢失：本地unknown/submitting，按execution_id查询并同步状态。
3. 同key但另一份代码任务：request_hash不同，返回409，不复用旧任务也不覆盖。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 内存去重 | 单进程临时演示 | 重启和多实例失效 |
| 数据库唯一键 | 持久并发幂等 | 仍需远端同ID协议 |
| 事务内远程调用 | 通常不能解决跨服务原子性 | 占连接、增锁时间 |
| 任务表+outbox | 可靠提交与派发 | 投递仍可能重复 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```java
import java.util.concurrent.ConcurrentHashMap;

public class Demo {
    public static void main(String[] args) {
        var requests = new ConcurrentHashMap<String, String>();
        System.out.println(requests.putIfAbsent("user1:key1", "bodyA"));
        System.out.println(requests.putIfAbsent("user1:key1", "bodyA"));
        System.out.println(requests.putIfAbsent("user1:key1", "bodyB"));
        System.out.println(requests.get("user1:key1"));
    }
}
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
javac -encoding UTF-8 docs/course/lessons/J01/Demo.java
java -cp .local/concepts/J01 Demo
```

预期观察：

```text
null
bodyA
bodyA
bodyA
```

### 按因果关系理解输出

putIfAbsent原子保留第一次值，后续返回旧值。第三次需要调用方比较bodyB与旧bodyA并判冲突，不能仅返回旧结果。这仍只是进程内示意；重启与多实例要用数据库唯一约束和持久化记录。

现在只修改练习副本`.local/concepts/J01/Demo.java`中的指定输入：只把第三次提交的key改为user2:key1，对比跨用户命名空间；不要把返回旧值直接当同请求成功。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 5. 本课在Code Agent里实际增加什么

- 在java-task-service建立Java21/Maven服务，选择与JDK兼容的Spring版本并记录实际版本；PostgreSQL为事务实验数据库，连接信息不入Git。
- 提交表包含owner_id、idempotency_key、request_hash、execution_id、dispatch_state、version；UNIQUE(owner_id,idempotency_key)，execution_id也唯一。
- 本地事务保存提交意图后释放连接，再调用Python；unknown时按同execution_id核对/重投；Python复用L19去重协议。
- 同键同体复用、同键异体409、跨用户键隔离；同时20次受控提交只产生一个逻辑执行。
- Java不直接写Python任务数据库；最小投递扫描器恢复pending/unknown意图，不引入MQ。
