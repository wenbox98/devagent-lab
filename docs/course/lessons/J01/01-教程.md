## 0. 这课为什么存在

Java入口把任务交给Python服务时，本地数据库事务无法回滚远端已经开始的执行。本课落实提交幂等与小事务，而不是在Service方法加@Transactional就结束。

目标是同一用户的同一提交意图，无论超时重试或并发提交，都关联同一个Python执行身份。

## 1. 一条具体方案：从输入到结果

### 先定义两边各自拥有的事实

Java拥有用户提交记录及授权；Python拥有任务执行状态。Java的submission_id、Python的execution_id与网络请求attempt不是一个对象。

数据库对(owner_id,idempotency_key)设唯一约束，记录规范化request_hash、execution_id和派发状态。相同key同body返回原提交；不同body返回冲突。

### 正确拆事务

事务一：插入/取得提交记录与待派发意图，提交后释放连接。随后发远程HTTP，带稳定execution_id或对方认可的幂等身份。事务二：记录远端已确认结果；超时则记录unknown/pending_reconcile并查询远端，不再生成新ID。

```text
本地短事务保存意图 → 远程请求（不占DB事务）
→ 成功记结果 / 未知查对方状态 / 明确失败分类
```

### 并发的最后裁判

20个线程同时提交同key时，唯一约束裁决只有一条业务记录；其他请求读取相同记录。最终验收还要检查Python只有一个逻辑执行，不能仅看Java表里一行。Outbox可用于可靠派发，但重复派发仍需要下游幂等。

### 一条提交记录可采用的字段

```text
owner_id + idempotency_key：唯一约束
request_hash：规范化请求内容
submission_id / execution_id：本地与远端身份
dispatch_state：pending / confirmed / unknown / rejected
version：条件更新
created_at / updated_at：审计
```

状态字段不意味着直接等于Python任务状态。Java已确认远端接收，不表示Agent已执行完成。

### 事务伪代码应这样读

```text
begin local transaction
  insert-or-read submission with unique key
  compare request_hash
  write dispatch intent
commit
call Python using stable execution identity
begin local transaction
  conditional update confirmed/unknown
commit
```

不能为了“保持一致”把远程慢调用夹在一个数据库事务中长期持锁；也不能只靠捕获HTTP异常回滚本地记录，把已经发生的远端效果遗忘。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 把提交身份和执行身份分开

**读这一段是为了解决：** 用户重试身份与远端执行身份怎样关联？

**原教材的浓缩句：**

> 外部用户提供或客户端生成Idempotency-Key，Java按用户/租户+key去重；内部execution_id稳定映射到Python任务。

**展开与落地：**

提交身份对应一次用户业务意图，执行身份对应远端任务，trace_id对应一次请求观测。重试可有新trace，但不能变成新execution。

查询和取消根据可信owner授权，不因知道execution_id就放行。不要把用户可填owner_id当认证结果。

### K2. 事务边界要小且明确

**读这一段是为了解决：** 为什么不能把远程等待包进长事务？

**原教材的浓缩句：**

> Java数据库事务可以保证提交记录与本地状态更新，但不能自动撤销Python已经接受的任务。

**展开与落地：**

远程调用可能慢或不确定，不应长期占着数据库事务和连接。先提交意图，再调用，再记录结果，是两个本地事务加外部操作。

失败后不能简单回滚已对外发生的事。必须有重试/对账状态，让系统能解释中间结果。

### K3. 状态并发用条件更新

**读这一段是为了解决：** 并发更新时怎样避免覆盖新状态？

**原教材的浓缩句：**

> UPDATE ... WHERE status='pending'或version=旧值，并检查影响行数。

**展开与落地：**

状态更新带expected_state/version，检查影响行数。旧派发结果不能覆盖新的确认状态。

并发测试制造两次回调和相同key冲突；不要只在单线程里先查再插就认为幂等。

### K4. 本地事务无法回滚远程已完成操作

**读这一段是为了解决：** 本地rollback为什么无法撤销Python任务？

**原教材的浓缩句：**

> Java数据库事务提交失败，不会自动撤销Python已创建的任务。

**展开与落地：**

@Transactional只覆盖受事务管理的本地资源。远端已接收任务后Java超时，回滚本地插入会让下一次请求以为从未提交，反而重复执行。

持久意图和稳定远端身份用于跨资源恢复。对方没有幂等/查询接口时，必须明确无法自动确定副作用的范围。

### K5. 唯一约束是并发幂等的最后裁判

**读这一段是为了解决：** 唯一约束怎样裁决两个并发同键提交？

**原教材的浓缩句：**

> 先select没有记录再insert的两请求可能同时通过检查。

**展开与落地：**

先SELECT发现不存在，然后两个线程同时INSERT会竞态。数据库唯一约束是最终裁判，应用捕获冲突后核对hash并读取原记录。

幂等作用域包括用户/租户，不能不同用户偶然使用同key却拿到别人的任务。

### K6. Outbox是可靠派发记录，不是恰好一次魔法

**读这一段是为了解决：** 派发记录能保证重试，但为何不能消灭所有重复？

**原教材的浓缩句：**

> 同一个数据库事务写任务与待派发事件，提交后由worker投递。

**展开与落地：**

Outbox把“需要派发”与本地提交放在同事务中，让后台可反复尝试投递。它不保证消息只发一次，也不替代接收方去重。

记录投递次数和下一次重试时间，但业务效果以稳定执行ID核对。不能把outbox状态sent当作任务完成。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 幂等 | owner+key唯一，绑定规范化bodyhash | 并发同意图同execution | 不同body不能复用 |
| 事务 | 意图/结果短事务，HTTP在外 | 慢远程不长期占连接 | 本地回滚管不到远端 |
| 派发 | outbox可重发+下游幂等 | 丢响应重提不多执行 | 消息次数不是效果次数 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
