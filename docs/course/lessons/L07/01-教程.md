## 先定位阅读目的与对象

**本课要回答：模型读过文件以后，凭什么确定现在仍可安全写回？**

## 1. 先知道这课到底要解决什么

Agent读到文件版本A，准备把page_no*size改为(page_no-1)*size。在它思考时，用户改了同一个文件。若Agent直接写回自己基于A生成的全文，可能抹掉用户的新修改。本课学习带前置条件的写入。

- 独立完成“加入只读文件保护。”，并说明换到新业务时哪些条件需要重新确认。

### K1. 先读版本，再条件写

**读这一段是为了解决：** 写入前必须拿哪两个版本比较？

读取时计算内容哈希并作为expected_hash传给写操作。写之前再计算当前哈希；不一致则返回conflict，并提示重读。它类似Java数据库更新时带version条件的乐观锁。

哈希只反映字节是否相同，不说明业务语义。格式变化也会导致冲突，这是保守选择。不能遇到冲突就自动用新哈希重试旧补丁，因为旧补丁可能已不合适。

### K2. 小补丁比整文件覆盖容易审查

**读这一段是为了解决：** 整文件覆盖会隐藏哪些无关变化？

第一版可用精确旧片段+新片段，要求旧片段唯一匹配；不唯一就拒绝，而不是替换所有。diff展示改了哪几行，让用户和测试共同检查影响。写入先放临时文件再替换可减少半写文件，但不自动解决并发检查到写入之间的竞争。

在受控教学工作区内给同一文件写入加锁，或保证单写入者。后面任务隔离进一步减少共享写冲突。

### K3. 回退也必须检查版本

**读这一段是为了解决：** 回滚为什么也可能覆盖别人工作？

把旧内容存起来不代表随时可以恢复。如果你的写入后又有人修改，直接恢复旧内容仍会抹掉他人工作。回退前确认当前哈希等于本次操作写出的哈希，否则报告回退冲突。不要用git reset --hard作为通用回退。

### K4. 补丁实际上是一个有前置条件的写请求

**读这一段是为了解决：** 补丁缺哪个前置条件就不该执行？

读取版本h1后生成新内容，写入前必须确认当前仍是h1。这是乐观并发控制，与你熟悉的数据库version字段类似。前置条件失败就重新读取、重新生成或让用户合并，不能强行覆盖。补丁不仅保存new_text，还应关联路径、expected_hash与操作ID，便于审计和后续对账。

### K5. 原子替换不等于多文件事务

**读这一段是为了解决：** 一个文件替换成功是否代表多个文件原子完成？

同一文件先写临时文件再替换，可减少读到半文件的风险；跨文件改动中途失败仍可能留下部分结果。课程先在独立工作区完成变更，保存修改清单并检查所有前置条件；失败后恢复需确认当前状态没有被其他人修改。不能无条件把备份覆盖回去，否则回滚本身会覆盖新改动。

### K6. 最小修改与可审查性

**读这一段是为了解决：** 怎样从diff看出修复是否越界？

一次大范围重写可能让测试通过，却让你无法判断哪处解决问题。限定可修改文件和行段，拒绝修改独立验收，输出实际diff。正确性先于diff小，但无关格式化会增加比较噪声。可审查变更需要说明每个文件为什么改、哪些约束被保留，而不是只给一段“已修复”。

### 与你已有语言经验的连接

hashlib用于内容摘要；tempfile管理临时文件；异常路径仍要清理资源，但清理不能吞掉原错误。

## 深入推演：把知识点连成因果关系

### 补丁是带前置条件的状态转换

你在时刻T1读取文件，其指纹是H1，准备把分页起点改为`(page-1)*size`。另一位开发者在T2改了同一文件得到H2。若T3直接覆盖整文件，你会删除对方改动。可靠写入必须表达“仅在当前版本仍为H1时应用这份变化”；检查不匹配就拒绝，重新读取并生成新补丁。这和Java业务中的乐观锁version字段是同一类方法。

### 原子替换与并发控制不是同一件事

临时文件写好后rename或replace可以降低读者看到半截文件的风险，但并不会自动防止两个写者都基于旧版本覆盖彼此。你还需要明确锁、受控单写者或真正受支持的比较交换语义。教学先约束为独立工作区中的单执行器，别把静态hash检查加rename称为完整并发写入协议。

### 补丁范围与独立验收要分别保护

允许修改的是目标源码，不是所有可写文件。Agent不应顺手删除失败测试、改验收阈值或修改密钥配置。先显示diff，核对允许路径与变更规模，再执行。写入成功返回新指纹与实际变更；返回丢失时不能盲目再写，这将是L10的未知结果问题。


## 3. 一次完整推演：先预测，再读下一步

1. 读取h1，人工插入一行产生h2；用expected_hash=h1提交补丁，结果conflict，文件必须保持h2。
2. 从h2重新生成补丁，成功后得到h3并记录diff与操作ID。
3. 模拟第二个文件失败：报告partial/failed并用修改清单恢复受控副本，不能宣称整组原子成功。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 直接覆盖 | 无并发且一次性临时样例 | 不适用于共享工作区 |
| 哈希前置条件 | 检测读写之间的变化 | 需处理冲突重读 |
| 独立分支/工作区 | 隔离任务修改 | 合并时仍可能冲突 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
import hashlib

def digest(text):
    return hashlib.sha256(text.encode()).hexdigest()

read_version = digest("start = page_no * size")
current = "start = (page_no - 1) * size"
print(digest(current) == read_version)
print("conflict" if digest(current) != read_version else "can_write")
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
python .local/concepts/L07/00-example.py
```

预期观察：

```text
False
conflict
```

### 按因果关系理解输出

示例在内存中模拟版本变动。正式实现需要在受控锁/单写入者条件下核对真实文件，并在失败时保持当前内容不变。哈希不同仅要求重读，不表示哪一个版本一定正确。

现在只修改练习副本`.local/concepts/L07/00-example.py`中的指定输入：只把current改成与read_version对应的原始文本，再改成第三个版本；不要把expected_hash跟着错误结果一起改。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 8. 面试时如何解释你做过的事

**哈希检查能消除所有竞争吗？**

不能，检查和写入之间仍需单写入者或同步保证。

**为什么不直接覆盖完整文件？**

难以控制影响范围和保留新修改，小补丁与条件写入更便于发现冲突。

补一句反事实：如果“隔离任务修改”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
