## 0. 这课为什么存在

F01 是固定消息流水线，F02 才用 create_agent 接管模型与工具之间的循环。目标不是再写一套会读文件的Agent，而是用框架循环调用已有安全工具。

你要能比较原生和框架两种engine，知道同一个权限拒绝与验收标准有没有保持。

## 1. 一条具体方案：从输入到结果

### 将原生职责逐项换成框架职责

原来 loop 负责调用模型、识别tool_calls、执行并回传结果；create_agent 提供这套循环。宿主仍提供允许的工具、模型配置、工作区和验收器。

本课先用只读工具接入，不立即把写文件和命令执行全部开放。一个框架tool包装器只负责参数适配、取可信上下文、调用已有 read_file，并把结果转换成框架可用的表示。

```text
框架工具参数：path、start_line、end_line
可信运行上下文：workspace、owner、allowed_tools、budget
工具包装器 → 既有L02 read_file
```

workspace 不出现在模型可以自行填写的参数里。

### 先跑实际框架协议，再跑项目边界

已有 framework-example 使用真实 create_agent、脚本化模型和内存fixture。它验证工具提议→ToolMessage→最终回复的框架循环及call_id，但没有读取你的真实工作区。

项目验收还要让框架tool实际调用共享L02工具，传入根外路径必须拒绝。再把同一只读任务交给native与langchain engine，对比证据、权限结果和预算，不只比较生成措辞。

### 工具包装器的实际职责

```python
# 教学骨架：workspace来自宿主闭包/运行上下文，不来自模型参数。
def read_tool(path: str, start_line: int = 1, end_line: int | None = None):
    result = read_file(workspace, path, start_line, end_line)
    return format_tool_result(result)
```

`workspace`、`format_tool_result`在此为明确的待实现/绑定职责。框架需要的装饰器与运行上下文API按实际版本接入；不得让这段占位代码直接进入应用假装完成。

### 迁移不变量怎么检查

给native与framework相同任务及工作区；工具包装前后的path/行段相同；L02授权仍执行；错误可被模型看到但不升级权限；最终同一grader通过。只有模型文字不同不算失败，安全行为不同才是关键差异。

引入框架后新增一个“假返回read结果”的测试：让包装器不调用实际工具，验收应通过真实文件内容对照发现问题，不能固定expected字符串蒙混。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 从手写while循环映射到框架职责

**读这一段是为了解决：** 原生循环的哪项职责交给create_agent？

**原教材的浓缩句：**

> L04由你亲自完成模型调用、工具执行、消息追加与停止。

**展开与落地：**

逐项确认原生loop的职责是否迁移：消息历史、工具分派、结果关联、停止条件和异常处理。框架提供默认行为不等于完全匹配项目合同。

保留engine选择开关与原生回归，发现差异时能定位是封装丢字段还是框架行为不同，而不是只能重写全部工具。

### K2. 工具声明包含模型接口与真实实现

**读这一段是为了解决：** 工具Schema与函数权限检查为什么都需要？

**原教材的浓缩句：**

> 工具名称、描述、参数schema帮助模型决定何时以及怎样请求调用；Python函数执行真实行为。

**展开与落地：**

@tool描述的是模型看到的名字、参数和说明；包装器内部真正调用共享执行函数。参数校验与授权仍是两层。

不要把root、api_key、owner等可信控制字段暴露成可由模型填写的schema。可从受控运行上下文注入，但每次执行仍做资源授权。

### K3. 一次工具轮次的具体轨迹

**读这一段是为了解决：** 怎样将一次工具请求和结果配成一对？

**原教材的浓缩句：**

> 脚本模型第一次返回`read_fixture(path="src/page.py")`和调用ID `call-1`；Agent执行工具，生成带相同ID的ToolMessage；脚本模型收到工具结果后返回最终解释。

**展开与落地：**

观察三条消息：模型带call_id的工具提议，程序带同ID的ToolMessage，模型基于结果的最终回答。不要把工具返回打印在控制台却没进入下一轮消息。

遇到工具失败，明确采用可恢复错误结果还是终止任务的策略。权限拒绝不允许模型换一种包装绕过。

### K4. 对照迁移比重写更能说明能力

**读这一段是为了解决：** 为什么同任务对照比另做一个演示更有用？

**原教材的浓缩句：**

> 使用完全相同的任务、工具函数、文件版本和预算，分别运行native与langchain路径。

**展开与落地：**

同一任务、同一工作区快照、同一工具和grader才是公平迁移对照。运行次数、超时、停止原因等同样记录。

两个engine输出文字不同不一定是回归；框架engine读了未授权文件即使回答更好也不通过。先检查硬行为条件，再讨论效果。

### K5. 故障如何定位

**读这一段是为了解决：** 框架没调工具时先检查哪类轨迹？

**原教材的浓缩句：**

> 没有调用工具，先检查模型实际返回是否包含调用、工具是否正确提供以及任务是否真的需要工具；工具已调用但读错文件，检查领域路径与参数；返回结果没有进入下一轮，检查消息关联和框架适配；一直循环，检查终止与预算。

**展开与落地：**

框架没调用工具，先看实际模型响应是否含tool_calls、tool名是否注册、参数是否匹配。工具已调用但无证据，则查包装器和消息回传。

不要一遇失败就换模型或改system prompt。用脚本模型固定协议路径，排除循环/包装错误，再用显式授权的真实模型验证能力。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 包装 | 框架tool薄包装原安全函数 | 越界路径在两engine都拒绝 | 不新增第二套读取代码 |
| 上下文 | 可信控制与模型参数分离 | 模型伪造root/owner不能生效 | 框架schema不是授权 |
| 对照 | 原生/框架共享task和grader | 同快照验证语义与资源 | 不要求措辞逐字相同 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
