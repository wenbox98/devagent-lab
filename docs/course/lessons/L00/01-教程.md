## 0. 这课为什么存在

你要做的不是先造一个智能体，而是把“调用一次模型”做成能解释的程序。输入为空时不应调用下游；下游超时与返回空文本也不是一回事。没有这条最小边界，后面工具读写失败时只能猜。

本课的成品是一条可测试的数据路径，不是一组异常名词：`task → 输入校验 → complete → 响应校验 → RunResult`。你已经读过 L00 时，不必重新学全部语法，直接以一个正常案例和一个拒绝案例检查是否还能重建路径。

## 1. 一条具体方案：从输入到结果

### 从一个输入看到四个位置

以当前基线的 `run_task("  explain pagination  ", FakeModelClient())` 为例，以下是代码逻辑推演，不是本次运行记录。

1. 应用生成 `run_id`，先记录 `run_started`。这一步写日志失败会提前结束，因此“日志出错也照样调用付费服务”不是当前策略。
2. `isinstance(task, str)` 确认类型，`strip()` 得到 `explain pagination`；随后建立 `ModelRequest`。
3. `client.complete(request)` 只被调用一次。Fake 返回带“模拟输出”标识的 `ModelResponse`，不是模型理解了仓库。
4. 文本非空才返回成功。应用结果中 `exit_code=0`；CLI 再把这个码作为进程退出码。

对照输入 `"   "`：第 2 步发现清洗后为空，返回 `invalid_input/2`，不会到第 3 步。真正能证明提前拦截的是下游调用数为 0，而不只是最终打印了“输入错误”。

### 一张判断表足够组织第一组测试

| 输入/下游行为 | 第一个失败边界 | 下游次数 | 本课结果 |
|---|---|---:|---|
| 空白任务 | 输入校验 | 0 | invalid_input / 2 |
| 合法任务，Fake 超时 | complete | 1 | model_timeout / 3 |
| 合法任务，返回空文本 | 响应校验 | 1 | invalid_response / 4 |
| 合法任务，返回有效文本 | 无 | 1 | succeeded / 0 |

这是规定的契约，测试负责检查实现是否满足它。不要在 demo 中把这张表直接写成 observed。

### 把“分层判断”变成看得见的代码

下面是刻意压缩到最小的教学实现；主项目还有日志、配置和完整结果对象，不要拿它覆盖app.py。

```python
def handle(task, client):
    if not isinstance(task, str) or not task.strip():
        return {"status": "failed", "code": "invalid_input"}
    cleaned = task.strip()
    try:
        text = client(cleaned)
    except TimeoutError:
        return {"status": "failed", "code": "model_timeout"}
    if not isinstance(text, str) or not text.strip():
        return {"status": "failed", "code": "invalid_response"}
    return {"status": "succeeded", "output": text}
```

读这段时不要从def一路机械翻译。先圈出`client(cleaned)`：它是下游边界。上方的return说明拒绝发生在调用前；except说明下游没有正常返回；最后的if说明下游虽然返回了，但业务不接受结果。

现在换三个输入：整数42、三个空格、字符串fix。前两种都不会调用client；第三种必须调用后才知道成功、超时还是空响应。这是L00最重要的因果关系。

测试不能只断言错误码。例如下面这段错误实现也可能返回invalid_input：先调用模型再检查输入。只有额外断言调用数为0才能排除它。

### 日志怎么读，不背四个名字

`model_finished.status='succeeded'`的事实是“客户端正常返回”，不是“任务成功”。空响应仍可能随后产生`run_finished.status='failed'`。这两个状态看似矛盾，其实观察的是不同边界。

把一次请求的run_id筛出来再读事件；不能把多个请求的最后几行拼成一条因果链。测试追加日志时既检查旧字节保留，也检查run_id不同。UUID格式正确本身不能证明事件归属正确。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 先建立三层判断

**读这一段是为了解决：** 输入、执行、响应各在哪个边界判断？

**原教材的浓缩句：**

> 输入校验处理的是调用前就能知道的问题，例如任务全是空格。

**展开与落地：**

先找副作用发生的位置：本课是 `client.complete()`。能在调用前确认的输入错误必须在它前面拒绝；只有拿到响应后才能判断的空文本则放在调用后。这里不是强制分成三个类，而是把判断顺序与责任分开。

你可以用 Java 的 Controller 校验、HTTP 客户端、返回体检查类比，但不能只放在 CLI：测试和未来 HTTP 接口可能直接调用 `run_task()`。因此核心输入边界必须在共享应用函数。

### K2. 读懂本课Python

**读这一段是为了解决：** None、空串、真假值会让哪个分支走错？

**原教材的浓缩句：**

> def run(task: str) -> str 表示参数与返回值的类型提示；它不会自动拒绝空字符串。

**展开与落地：**

`task: str` 是类型提示，不负责拒绝整数；`strip()` 返回新字符串，也不修改原变量引用的字符串。先检查类型再调用 `.strip()`，才能把整数输入变成明确拒绝，而不是意外 AttributeError。

当前需要会的语法只有函数、if、return、try/except 和对象字段。看到压缩写法先展开普通 if/for，不需要追 Python 解释器源码。语法查阅集中在根目录《Python够用速查》，不再打断整节课。

### K3. 数据对象和程序入口

**读这一段是为了解决：** 结果对象和CLI入口为何分开？

**原教材的浓缩句：**

> dataclass类似轻量DTO，减少初始化方法，但字段类型不自动校验。

**展开与落地：**

`ModelRequest` 装输入，`ModelResponse` 装客户端响应，`RunResult` 装本次应用结果；它们像三种不同阶段的 DTO，不要为了省类把“用户问题”和“错误码”塞进一个随意变化的 dict。

`python -m devagent` 从包入口启动，工作目录要能定位该包。入口只选择参数、客户端和输出方式，不复制 `run_task` 的业务判断。`dataclass(frozen=True)` 限制直接重赋字段，不会自动验证字段内容，也不是深度不可变。

### K4. 先模拟，是为了控制变量

**读这一段是为了解决：** 为什么先模拟而不先接公网？

**原教材的浓缩句：**

> 模拟客户端只有成功、抛超时、返回空文本三条分支。

**展开与落地：**

Fake 不是“效果差的模型”，而是实验仪器。给它 success、timeout、bad_response 三种可控模式，就能在离线环境重复进入相同分支。超时实验可以立即 raise，不必真等网络超时。

测试通过只能说明这些受控条件下的编排正确。真实网络、鉴权与模型权限仍需 L01 的独立接入验证。把两个验证通道分开，可以避免把账号问题误判成应用算法问题。

### K5. 把一次失败拆成输入、执行、表达三层

**读这一段是为了解决：** 同一个“失败”能否来自三个不同层次？

**原教材的浓缩句：**

> 输入层检查用户有没有提供合法任务；执行层负责真实调用；表达层将结果交给调用者。

**展开与落地：**

K1 解决判断顺序，这里补“谁翻译错误”。知道网络事实的客户端把底层失败分类；应用把已知失败翻译成 `error_code`；CLI 负责表达结果。不能在最外面用一个 `except Exception` 把所有 Bug 都叫超时。

例如日志 OSError 只在日志写入边界转成 `trace_io`；客户端自己抛出的 OSError 不能因为名称相同就被误当日志故障。这样排错时才知道下一步看哪个模块。

### K6. 理解返回值、异常与退出码

**读这一段是为了解决：** 异常、返回值、进程退出码分别给谁看？

**原教材的浓缩句：**

> 函数返回对象是进程内协议；异常用于中断当前路径并交给能处理它的调用者；CLI退出码是进程间协议。

**展开与落地：**

函数 return 是交给同进程调用者；raise 是中断当前路径并交给上层异常处理；CLI 退出码是给操作系统或脚本。它们不是三种同义写法。

当前应用的失败退出码不等于 demo 的失败退出码：demo 故意制造超时，确认应用正确返回 model_timeout 后，demo 本身可以退出 0。检查时同时写出“业务结果”和“测试/演示结果”，就不会把红色业务状态误认为测试没通过。

### K7. 把日志设计成可以反驳假设的证据

**读这一段是为了解决：** 哪条日志能排除“客户端已经调用”的猜测？

**原教材的浓缩句：**

> “开始请求”“发生异常”无法证明下游是否被调用。

**展开与落地：**

记录事件名、关联 ID、顺序和单调时钟耗时，才能重建请求。正常应有 run_started、model_started、model_finished、run_finished；无效输入不应出现 model 事件。

日志默认不含密钥、完整任务或源码。需要证明未调用时用调用计数；需要证明追加写入时比较旧文件前缀是否保留。日志本身也可能失败，所以事件缺失只能与调用结果、异常一起判断，不能凭“没找到日志”宣布未执行。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 输入拒绝 | 类型/清洗/长度检查放在 complete 前 | 无效输入下游计数为 0 | 不等于 CLI 参数解析已足够 |
| 外部错误 | 只捕获约定的异常类别 | 分别检查错误码和退出码 | 未知 Bug 不伪装成成功 |
| 观测 | JSONL 追加、真实 ID、单调耗时 | 旧记录保留且不同 run_id 可分组 | 不记录敏感全文 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
