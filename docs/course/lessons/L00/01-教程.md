## 先定位阅读目的与对象

**本课要回答：我怎样从一次失败区分“没资格调用”“调用没返回”“返回了但不能用”？**

前提是：只有一次输入和一个可替换的模型客户端，尚未建立可靠的错误分类。 本课把它推进到：把输入错误、客户端超时、响应无效分开；拒绝输入时证明客户端没有被调用。

### K1. 先建立三层判断

**读这一段是为了解决：** 输入、执行、响应各在哪个边界判断？

输入校验处理的是调用前就能知道的问题，例如任务全是空格。调用层处理超时或连接错误。结果校验处理“调用成功但没有有效内容”。这三者对应不同修复：补输入、检查服务、检查返回协议。不能全归为模型不好。

以Java类比：Controller接到空body、HTTP客户端超时、HTTP 200但body缺字段，是三个不同位置。Python同样应在对应边界检查，不把所有判断堆到命令行入口。

### K2. 读懂本课Python

**读这一段是为了解决：** None、空串、真假值会让哪个分支走错？

def run(task: str) -> str 表示参数与返回值的类型提示；它不会自动拒绝空字符串。task.strip()返回去掉首尾空白的新字符串；原字符串不会原地改变。if not task检查空字符串等假值，因此先strip再检查。

try中的函数可能用raise TimeoutError(...)主动抛异常。except TimeoutError只捕获这一类；ValueError可以表示输入或业务约束不满足。不要用except Exception然后一律返回“超时”，否则代码Bug也会被误诊。

### K3. 数据对象和程序入口

**读这一段是为了解决：** 结果对象和CLI入口为何分开？

dataclass类似轻量DTO，减少初始化方法，但字段类型不自动校验。ModelRequest只装任务，ModelResponse只装响应，app函数协调它们。python -m devagent从包入口启动：你必须站在包含devagent目录的仓库根目录，Python才容易定位它。

with path.open(...) as f类似Java的try-with-resources，用完文件会关闭。JSONL是每行独立JSON；append模式追加，write模式会覆盖。日志里的run_id用于把同一请求的事件连起来。

### K4. 先模拟，是为了控制变量

**读这一段是为了解决：** 为什么先模拟而不先接公网？

模拟客户端只有成功、抛超时、返回空文本三条分支。它不理解代码，只让你稳定练错误处理。故意超时无需真等十秒，直接抛异常即可。通过这些测试只能说明应用控制正确，下一课仍必须连接真实模型。

### K5. 把一次失败拆成输入、执行、表达三层

**读这一段是为了解决：** 同一个“失败”能否来自三个不同层次？

输入层检查用户有没有提供合法任务；执行层负责真实调用；表达层将结果交给调用者。三层混在一个大try里时，输入为空也可能被记录成“模型故障”，导致无用重试。先写清每层能观察到的事实：输入层知道字段，客户端知道超时，输出层知道序列化是否成功。错误必须在拥有事实的层分类，再由边界统一转成稳定错误码。

### K6. 理解返回值、异常与退出码

**读这一段是为了解决：** 异常、返回值、进程退出码分别给谁看？

函数返回对象是进程内协议；异常用于中断当前路径并交给能处理它的调用者；CLI退出码是进程间协议。三者不能互相替代：stdout打印error但退出0，会让脚本误判成功；程序退出1却没有机器可读原因，调用者也无法决定如何处理。给Result定义status、error_code、message、trace_id，把用户可读提示与程序判断字段分开。

### K7. 把日志设计成可以反驳假设的证据

**读这一段是为了解决：** 哪条日志能排除“客户端已经调用”的猜测？

“开始请求”“发生异常”无法证明下游是否被调用。至少记录事件类型、关联ID、耗时和结果类别。trace_id贯穿一次请求，事件序号区分先后。日志不是越多越好：在输入拒绝时检查client_call_count=0，比打印整个请求更能验证提前拦截；错误堆栈留在开发诊断侧，密钥不进入日志。

### 与你已有语言经验的连接

dataclass类似简单DTO，但类型提示不会自动校验；理解raise、except、finally、函数返回与sys.exit的不同作用。

## 深入推演：把知识点连成因果关系

### 从一段程序建立完整的执行模型

先把“程序失败”改成四个可以观察的问题：入口有没有拿到原始任务？清洗后是否仍有效？客户端是否被调用且返回？业务是否接受该返回？例如输入是三个空格，`strip()`产生空串，输入边界就能结束任务；这时客户端的调用计数必须是0。输入是`fix pagination`，客户端被调用后抛出`TimeoutError`，才属于调用层失败；这时计数是1。输入相同而返回空文本，说明调用正常结束，但响应不能满足业务要求。这两种情况的最终状态可以都叫failed，诊断码却不能相同。

现在手画一张表：原始输入、清洗后输入、client调用数、是否进入except、退出码。用同一张表走本课四个样例，先写预测再运行。重点不是记住四个英文状态，而是能回答“哪个判断在副作用之前，哪个判断只能在副作用之后”。下一课副作用是付费API，后续是改文件和启动进程；这条顺序会直接影响成本与安全。

### 类型提示、对象、异常分别解决什么

`task: str`只向读代码的人和类型检查器表达意图，不等于Java运行时自动完成了参数校验。`dataclass`负责存放字段，不会替你保证任务非空、响应合法、退出码一致。因而把对象建出来和通过业务校验是两件事。若客户端意外返回`None`，示例里的`text.strip()`会暴露异常，这是概念例子的刻意简化，不应在应用里被改成“成功但没有内容”。完整实现应在适配边界校验响应对象，或明确让程序缺陷上报为内部错误。

Python函数本身能作为参数传入。`handle(task, client)`中的client不一定是某个复杂接口实例，只要按约定可调用即可；这就是为什么可以用lambda快速替换下游。对比Java中的函数式接口：你保留了依赖替换能力，却不需要先造工厂、父类和实现类。先让调用契约足够小，等真实需求出现再抽象。

### 用事件顺序，而不是用一条“失败”日志推断原因

正常轨迹应依次包含开始、调用开始、调用结束、任务结束；空输入没有调用事件；空响应有正常的调用结束，却有失败的任务结束。`run_id`把四件事连起来，事件类型说明位置，错误码说明原因。耗时应来自单调时钟之差，不能拿系统时间调整造成的负数解释性能。日志默认记录长度与脱敏标识，不记录密钥和整段源码。

最小测试除了断言状态，还要断言客户端调用次数。仅断言`invalid_input`可能漏掉“先调用付费模型，再返回输入错误”的错误实现。你应能解释每个断言排除的具体错误，而不是为了覆盖率再写一个相同的正常样例。


## 3. 一次完整推演：先预测，再读下一步

1. 输入空字符串，先预测：客户端应该收到几次调用？答案是0；因此把计数器放在客户端入口而不是CLI入口。
2. 换成合法任务但注入TimeoutError。输入校验通过，调用数为1；结果归类model_timeout，不能归类bad_input。
3. 让输出序列化失败：保留内部关联ID并检查错误处理自身不会再次序列化不可支持对象。此时重试模型不能修好输出层。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 显式结果对象 | 预期会发生的业务拒绝 | 调用者必须检查status |
| 异常 | 当前函数无法继续且上层能处理 | 不能用except Exception后返回成功 |
| 重试 | 暂态外部失败且重试安全 | 输入错误不重试 |

## 4. 可运行小例子：看见机制

**当前代码的已知限制：** `00-example.py`中的`handle`直接调用`task.strip()`，没有显式类型检查。整数42会产生`AttributeError`而不是规范的`invalid_input`；这是概念示例尚未覆盖的边界，目标应用必须补齐。具体可运行探针见本课实验。

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
def handle(task, client):
    task = task.strip()
    if not task:
        return "invalid_input"
    try:
        text = client(task)
    except TimeoutError:
        return "model_timeout"
    if not text.strip():
        return "invalid_response"
    return "succeeded"

def timeout_client(task):
    raise TimeoutError("simulated")

print(handle("  ", lambda task: "ok"))
print(handle("fix", timeout_client))
print(handle("fix", lambda task: ""))
print(handle("fix", lambda task: "ok"))
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
python .local/concepts/L00/00-example.py
```

预期观察：

```text
invalid_input
model_timeout
invalid_response
succeeded
```

### 按因果关系理解输出

第一个调用在client之前就返回，所以不能消耗模型请求。第二个调用跳进except。第三个调用没有异常，却因空结果失败。第四个才通过三层判断。lambda是一个短匿名函数，类似Java lambda；这里仅用来快速替换下游行为。示例没有日志与CLI，完整实现会在这些边界记录事件。

现在只修改练习副本`.local/concepts/L00/00-example.py`中的指定输入：先保持 handle 函数不变，用本课探针把 task 设为整数42，再设为字符串"42"。然后在独立练习副本中补运行时类型判断。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 5. 本课在Code Agent里实际增加什么

- ModelRequest(task:str)、ModelResponse(text:str,provider:str)、RunResult(run_id,status,output,error_code,exit_code)；错误和空值有明确约定。
- FakeModelClient.complete：success返回【模拟输出】+清理后的任务；timeout立即抛TimeoutError；bad_response返回空text。
- run_task先校验输入、只调用客户端一次、校验响应；invalid_input/timeout/invalid_response退出码2/3/4，正常0。
- JSONL事件run_started/model_started/model_finished/run_finished；空输入不出现model事件；空响应的model_finished成功但run_finished失败。
- 日志默认.local/traces/runs.jsonl；追加UTF-8，UUID真实生成，耗时用单调时钟，不记录任务全文。首条日志失败不调用客户端，日志失败用trace_io表达。

## 8. 面试时如何解释你做过的事

**返回0就代表Agent成功了吗？**

这里仅证明模拟请求符合本课契约；真实任务还需要工具和结果验证。

**为何不把空结果当作超时重试？**

它是可观察的无效响应，根因可能是协议或解析错误；盲目重试没有定位问题。

补一句反事实：如果“暂态外部失败且重试安全”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
