## 先定位阅读目的与对象

**本课要回答：为什么“模型忘了”可能其实是我在组装输入时删掉了约束？**

前提是：长任务已有多轮工具结果，硬约束可能在压缩时被丢掉。 本课把它推进到：把稳定约束、工作状态、摘要和证据分开装配；核对丢弃与过期。

本文的知识讲解是为完成上述变化服务，不要求先掌握所有相邻技术。范围边界：不默认摘要无损；这里的字典修改不是检索器或长期记忆数据库。

**文中代码分两种。** [00-example.py](00-example.py)是包中已经提供的概念示例；本课“工程实现/职责路径”是对你项目的目标要求，除L00起始骨架外不表示应用已经生成。未生成时只研究示例；生成后让Codex把职责映射到实际文件，不照猜函数名找代码。

先读[本课文件导航](00-本课目的与文件导航.md)，练习具体改动位置见[实验与排错](03-实验与排错.md)，源码定位方式见[代码地图](05-过关卡与代码地图.md)。需要代码AI帮助时只给[本课Codex指令](02-交给AI.md)与当前源码，并指定“只分析，不修改”。


## 1. 先知道这课到底要解决什么

用户最初说“不修改公共函数签名”，几十轮后这句被历史压缩丢了，Agent通过改签名完成测试。另一种失败是相关文件压根没被检索到。它们表面都是“模型忘了”，但解决方法不同。

完成后，你应该能：

- 用自己的话回答：“数据库存了历史等于模型记得吗？”并给一个反例。
- 沿下面案例说明输入经过哪些判断，哪条证据使下一步改变。
- 独立完成“给摘要加入保留字段校验并注入一次遗漏。”，并说明换到新业务时哪些条件需要重新确认。

先写你的原始判断，不要立刻让AI告诉你答案。需要保存的是能重建方法的记录，不是抄下术语。

### K1. 拆开四种失败

**读这一段是为了解决：** 没召回、被丢弃、被误读和已过期怎么区分？

没检索到相关文件是召回问题；找到了却没放进请求是装配问题；摘要删除关键信息是压缩问题；信息明明存在但模型使用错误是理解/推理问题。先看真实模型输入与证据记录，才能决定改哪一层。

把所有历史重复发送只能拖延问题，不能无限扩容。上下文还要预留输出与工具定义空间，超限前应主动裁剪。

### K2. 约束、状态、证据分开存

**读这一段是为了解决：** 为什么硬约束不能混在可改写摘要里？

用户硬约束保存为结构化task_constraints，不只寄存在自由文本摘要。已完成动作、当前假设与未解决问题保存为可更新状态；文件内容通过路径、行段、哈希引用，必要时重读。

摘要适合减少冗长过程，不应抹掉操作ID、未确认副作用、权限边界和关键约束。摘要也可能出错，应有保留字段校验和回归任务。

### K3. 按需取证的最小策略

**读这一段是为了解决：** 当前需要的原文证据从哪里取？

先找候选文件，取小段上下文，发现调用关系不够再补读。每段内容带来源与版本。若索引落后于当前仓库，重新检索或核对，而不是把旧内容当当前事实。

本课先比较全量历史、检索装配、检索+摘要三种策略。向量检索不是必须，关键词与符号索引已经足以学会召回、选择和证据刷新。

### K4. 预算是工程控制

**读这一段是为了解决：** 上下文预算耗尽时谁决定丢什么？

输入预算=模型允许上下文减去预留输出及其他开销；优先使用模型匹配的Token计数器。临时估算要标注estimated并留余量，不用字符串字符数伪装精确Token数。预算不足时拒绝加入低价值大块内容，并提供补读机制。

### K5. 上下文窗口不是记忆数据库

**读这一段是为了解决：** 模型看到的窗口和持久事实存储有什么区别？

模型只看到本次真正发送的消息；保存到本地状态但没组装进请求的信息不会被模型自动知道。反过来，把所有历史都发送也会超限且增加噪声。区分持久状态、检索证据、临时模型输入：状态保证约束不丢，检索拿到所需事实，装配器决定本轮暴露什么。分别记录三层，才能定位“忘了”的真实原因。

### K6. 用预算分配解释保留顺序

**读这一段是为了解决：** 约束与低价值历史的保留优先级如何确定？

假设教学预算8000 tokens，预留输出1500、工具定义1000、系统约束500，余下5000给任务、证据与必要历史。数值仅用于演算，实际按模型容量与计数器配置。先保留硬约束、当前目标、未确认副作用和最近有效证据；低价值重复日志先移出。预算不足可以再检索而非一次塞齐，截断必须可追踪。

### K7. 摘要是一种有损转换，需要不变量

**读这一段是为了解决：** 如何发现一次流畅摘要丢了关键限定？

摘要可能把“不能改签名”变成“最好不改”，或漏掉某次写入结果未知。把硬约束和操作状态从自由摘要中分离，用结构字段保留；摘要保存来源范围与版本。验证摘要不变量，例如操作ID集合、未解决事项和引用版本不能无故丢失。对摘要漂移建立长任务回归，而不是只评价文字是否顺畅。

### 与你已有语言经验的连接

区分对象引用与副本；装配器返回新messages而非直接删持久历史；估算Token字段明确标estimated。

## 深入推演：把知识点连成因果关系

### 上下文是有预算的工作集，不是档案仓库

一个任务会积累目标、约束、工具调用、原始日志、源码与中间假设。全部保留很快占满窗口；只保留摘要又可能丢失仍需校验的细节。先划分不可丢约束、当前工作证据、可按引用重取的原始材料和已过期信息。将“事实来自哪里、对应哪个版本”保存为结构，而不是让摘要承担全部记忆。

### 摘要是一项有损转换

例子：原文规定只能改`pagination.py`且不得改公共函数签名。摘要只写“修分页”会让后续行动越界，即使读起来很流畅。约束字段应单独保留，摘要只压缩过程；重要代码或测试用精确引用回读。对比压缩前后任务成功、权限边界和引用正确性，不能只看token减少比例。

### 调用与结果是一对协议单位

不能裁掉某次工具请求却留下其结果，也不能把结果拼成普通用户消息。保留成对关系和调用ID，删除时遵守模型消息协议。长期偏好、当前会话消息、执行检查点是三种不同状态：偏好可跨任务，消息表达本轮上下文，检查点承担恢复；把它们全放一个历史列表会让隔离和过期策略混乱。


## 3. 一次完整推演：先预测，再读下一步

1. 失败问题“忘了不能改签名”：先检查任务状态是否保存约束，再检查实际请求是否携带，最后看模型是否遵守。
2. 调用方证据未检索到：归类retrieval_miss；已检索但被预算裁掉：归类assembly_drop；两种修复不同。
3. 压缩20轮历史后仍保留pending_operation_id，恢复时先查结果，不重复写入。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 扩大窗口 | 必要信息确实很多 | 更贵且不保证正确使用 |
| 按需检索 | 大仓库局部问题 | 召回和版本必须验证 |
| 摘要 | 历史冗长而事实已稳定 | 有损转换需不变量 |
| 结构状态 | 约束与操作结果 | 需定义更新与过期规则 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
state = {
    "constraints": ["keep public signature"],

    "evidence": [{"path": "pagination.py", "hash": "v1"}],

new_summary = "Boundary validation remains"
state["summary"] = new_summary
print(state["constraints"])
print(state["evidence"][0]["path"])
```

### 按因果关系理解输出

示例用独立字段让摘要更新不会直接覆盖约束。正式程序仍需权限与校验：模型生成的摘要不能顺便修改constraints；证据hash也要对应实际内容，不是字符串v1。

现在只修改练习副本`.local/concepts/L16/00-example.py`中的指定输入：只替换new_summary文本，确认constraints仍保留；另在副本故意删除constraints，观察消费者缺什么。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 5. 本课在Code Agent里实际增加什么

- ContextState含原任务、不可随意改写的constraints、摘要、证据引用、未确认操作；组装器按优先级和预算选择。
- 摘要仅更新允许字段，保留约束/操作标识/未完成项；摘要后运行约束完整性检查。
- 读取证据时核对文件哈希，过期则重读；记录included/dropped及原因，避免无声丢信息。
- 同任务集比较全量、检索、检索+摘要；真实用量不足时用带标记估算，不宣称精确费用。

职责落点不是已存在断言；具体建议、当前源码确认方法见[本课文件导航](00-本课目的与文件导航.md)第3节。

### 看生成代码的具体顺序

1. 找本课演示入口，确认它调用真实应用函数；期望值不能写死成observed。
2. 找输入对象与校验，标记哪些字段可信、哪些来自模型或用户。
3. 沿正常案例走主函数、下游调用、状态更新与返回。
4. 沿失败案例找到第一个不同分支，并核对工具调用次数/文件/状态。
5. 找测试，说明它能抓住哪种错误实现；再看Git diff为什么需要这些变更。

## 8. 面试时如何解释你做过的事

**记忆是不是保存所有聊天记录？**

保存只是基础，实际还需选择、刷新和控制哪些信息参与当前决策。

**扩大上下文就能解决吗？**

可能缓解容量，但不能解决错误召回、过期事实和约束丢失。

补一句反事实：如果“约束与操作结果”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
