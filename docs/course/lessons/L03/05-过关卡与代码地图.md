## 3. 项目目标预测：明确这是“应该怎样”，不是“现在已经怎样”

**问题：模型传入tenant_id=admin，Schema完全合法，应该执行吗？**

目标数据流：模型tool_call → tool_call_id关联 → schema校验 → 宿主授权 → executor → tool_result。

未实现时答“目标在哪个职责边界判断、应阻止或允许什么、需要什么证据”，不填函数位置。已实现时，用源码地图查到真正入口与分支，再回答“当前代码实际怎样”。结果不符合目标正是要排查的偏差，不能把答案里的目标行为写成观察到的事实。

## 4. 让Codex找五类位置，而不是找五个预设文件名

| 角色 | 必须从实际代码回答的问题 | 证据要求 |
| --- | --- | --- |
| 入口 | 本课输入从哪个函数、HTTP接口、测试或命令进入？ | 实际路径+符号/配置块 |
| 输入边界 | 哪个条件首先决定继续还是拒绝？ | 原文锚点+具体输入类型/值 |
| 核心决策 | 怎样推进本课目标：模型提议与执行权限？ | 关键分支/字段前后值 |
| 下游/状态 | 调用了什么或修改了什么，次数与身份是什么？ | 调用参数/次数、状态、文件或记录 |
| 测试 | 哪条断言会让错误实现失败？ | 具体测试方法、实际收集数与输出 |

有些角色由同一文件承担，有些课没有模型调用：不要把所有章节都强行解释为client调用数。Java类路径、SQL迁移脚本与评测文件都可以成为真实观察对象。

## 6. 过关证据保存在哪

个人记录：`docs/learning-records/L03.md`。源码地图：`docs/learning-records/L03-code-map.json`，只有实施阶段由Codex写入真实映射；只读分析阶段在回复中展示，不写文件。

按“输入/状态 → 首个相关分支 → 下游或状态变化 → 实际证据”作答。把工具看成RPC：参数合法、调用者有权和操作成功是三个独立判断。

源码定位检查只验证文件、锚点与哈希存在，不证明业务正确。仍需[实验案例](03-实验与排错.md)与独立修改。预测/迁移的参考在[04-复习与迁移答案.md](04-复习与迁移答案.md)。
