### K1. 三个对象分别是什么

**读这一段是为了解决：** 工具描述、调用提议和执行结果各由谁产生？

ToolSpec是能力说明：名称、用途、参数结构。ToolCall是某次请求：call_id、name、arguments。ToolResult是执行事实：同一个call_id、是否成功、data或error。把三者分开，就能区分“模型知道工具存在”“模型想调用工具”“程序已经执行工具”。

Java里可类比接口描述、请求DTO、响应DTO；但这里请求由概率模型产生，不能因为它符合JSON就相信内容有效。

### K2. 两层校验不可省略

**读这一段是为了解决：** Schema通过后还要检查什么？

结构校验检查必填字段、类型、未知字段。例如start_line必须是整数，不能接受字符串"3"再悄悄转换，也要小心Python bool是int子类。业务校验检查start_line>=1、路径存在、权限符合要求。

JSON Schema帮助描述形状，但不自动证明业务条件成立。模型可能有结构化输出能力，也仍需执行侧校验。

### K3. 注册表限制实际能力

**读这一段是为了解决：** 为什么注册表必须限制可执行函数？

用字典把允许的工具名称映射到函数。不能eval模型返回的表达式，也不能根据任意字符串动态导入执行。遇到未知工具就返回unknown_tool，模型可据此改正；权限错误也要形成结构化结果，不把敏感路径内容回传。

工具错误结果应包含code、message、retryable。retryable表示在什么条件下值得再次尝试，不能让参数错误默认可重试。

### K4. 调用ID为什么重要

**读这一段是为了解决：** 并列工具结果怎么配回各自请求？

如果模型连续请求两个文件，两次结果都叫read_file，仅靠工具名无法对应。call_id连接模型请求、工具结果和执行日志。将来并行执行时结果返回顺序不同，这个ID更不能丢。

### K5. Schema约束形状，不约束世界事实

**读这一段是为了解决：** 路径合法字符串就一定可读吗？

参数有path:str不代表路径存在，更不代表可以读；limit:int也不保证正数。解析JSON、检查字段与类型、检查业务范围、检查当前权限是连续关卡。工具注册表保存名称、描述、参数模式、权限与执行函数；模型只产生候选调用，分发器才有执行权。与Java Controller的Bean Validation和Service授权类似，二者都不能省。

### K6. 调用ID是协议关联键

**读这一段是为了解决：** call_id重复或丢失会破坏什么证据？

一个模型消息可能提出多个工具调用，返回顺序可能不同。结果必须使用原tool_call_id关联，不能按列表位置猜。缺失、重复、未知调用ID需要明确拒绝或去重策略。工具返回后把事实附到对话，让模型继续判断；别把结果伪装成新的用户命令，也别让工具输出里的文本修改执行权限。

### K7. 工具描述是接口的一部分

**读这一段是为了解决：** 工具描述不清会在哪个阶段导致误选？

“搜索代码”太模糊，模型不知道何时用它。描述至少说明适用任务、输入约束、输出事实和不适用场景。例如全文搜索返回文本出现位置，不承诺函数调用关系。描述与Schema变动都可能改变选择行为，应该版本化并回归；修改函数实现却不更新描述，会形成难以定位的误选。

### 与你已有语言经验的连接

Callable保存可调用对象，装饰器改变函数包装方式；TypedDict主要用于静态提示，运行时仍需验证。

## 深入推演：把知识点连成因果关系

### 一次工具调用是两段协议，不是一段文本

假设模型返回调用ID `call-7`、工具名`read_file`、参数`{"path":"src/page.py"}`。到这一刻文件尚未被读。宿主先校验工具是否存在、参数是否符合形状和业务边界、当前主体是否有权限，之后才执行；执行结果还必须带着`call-7`回到模型。调用ID类似请求关联键：两个同名工具请求可以参数不同，不能只靠工具名称配对。

把模型输出直接`eval()`会把“受约束的调用提议”变成任意代码执行。正确办法是结构化解析、查白名单注册表、调用明确函数。JSON能解析只说明语法成立，不说明path合法；schema通过也不能替代权限与文件存在检查。这里依次有语法、类型、业务、授权四道边界。

### 失败也必须遵守结果协议

未知工具、参数缺失、越界读取和文件不存在，分别应形成可诊断的工具结果或受控终止，而不是让模型收到一段无关联的“出错了”。可恢复错误可以给出允许的修正方法，例如“请使用相对路径”；不可恢复或越权不应为了让模型继续而放宽限制。正常结果和错误结果都需保留调用ID，否则下一轮可能把错误当成另一个请求的结果。

### 领域工具与模型工具声明要分开看

真正的`read_file()`可以独立单测；schema、名称和描述只是它对模型的接口。这种分层会让后续迁移LangChain时只增加工具包装，而不重写路径校验。测试应同时覆盖函数业务行为与调用协议，否则框架能调用的函数仍可能读到不该读的文件。


## 3. 一次完整推演：先预测，再读下一步

1. 调用read_file，args是字符串而不是对象：协议层拒绝，不到文件系统。
2. args是合法对象但path越界：业务权限层拒绝，错误码与JSON解析失败不同。
3. 同时得到call-1、call-2且call-2先完成：按ID回填，不能把第二个结果给第一个调用。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| Schema校验 | 字段与类型错误 | 不能代替权限检查 |
| 描述优化 | 模型误解适用范围 | 不能改变底层真实能力 |
| 注册表白名单 | 限定可执行工具集合 | 未知名称应失败而非eval执行 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
registry = {"double": lambda x: x * 2}

def execute(call):
    if call["name"] not in registry:
        return {"call_id": call["id"], "ok": False, "code": "unknown_tool"}
    value = call["arguments"].get("x")
    if type(value) is not int:
        return {"call_id": call["id"], "ok": False, "code": "invalid_args"}
    return {"call_id": call["id"], "ok": True,
            "data": registry[call["name"]](value)}

print(execute({"id": "c1", "name": "double", "arguments": {"x": 3}}))
print(execute({"id": "c2", "name": "double", "arguments": {"x": True}}))
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
python .local/concepts/L03/00-example.py
```

预期观察：

```text
{'call_id': 'c1', 'ok': True, 'data': 6}
{'call_id': 'c2', 'ok': False, 'code': 'invalid_args'}
```

### 按因果关系理解输出

字典是注册表，不是让模型自由运行表达式。type(value) is int在这个有限示例里故意排除bool；通用系统可使用明确的Schema验证器。这里只演示一个参数，完整协议还需验证arguments本身的结构与未知字段。

现在只修改练习副本`.local/concepts/L03/00-example.py`中的指定输入：把第二个调用的x从True改为3；另增加name=missing的调用。不需要创建名为admin的真实租户。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 5. 本课在Code Agent里实际增加什么

- ToolSpec(name,description,input_schema)；ToolCall(call_id,name,arguments)；ToolResult(call_id,ok,data,error)，error含code/message/retryable。
- 注册L02只读工具；结构校验与业务校验分开；未知字段是否拒绝在Schema中明确，本课默认拒绝。
- 执行器不eval、不任意导入；未知工具/缺字段/类型错误均返回结构化失败；每个结果保留对应ID。
- 工具描述写清用途、输入边界与不适用场景，不通过含糊工具名区分权限。

职责落点不是已存在断言；具体建议、当前源码确认方法见[本课文件导航](00-本课目的与文件导航.md)第3节。

## 8. 面试时如何解释你做过的事

**Tool Calling等于执行了吗？**

它表达调用意图；应用才负责授权、校验与真正执行。

**结构化输出能替代校验吗？**

它能降低形状错误，但不能决定权限、文件存在或业务边界。

补一句反事实：如果“限定可执行工具集合”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
