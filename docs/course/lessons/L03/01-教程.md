## 0. 这课为什么存在

这一课开始把模型“说的话”变成可被程序执行的工具请求。L02 已经有受控文件工具，L03 给它加稳定的调用协议。模型只提出工具名和参数，真正的权限仍由执行代码判断。

你会第一次看到 Agent 的动作接口，但不是让 Python 执行模型生成的任意字符串。成品是一个工具调度器：接收 ToolCall，返回与之关联的 ToolResult。

## 1. 一条具体方案：从输入到结果

### 一个调用从提议到真实文件操作

设宿主固定 workspace=受控 tiny_repo。模型给出教学样例：

```json
{"call_id":"c1","name":"read_file","arguments":{"path":"pagination.py","start_line":1,"end_line":3}}
```

这不是当前已有的 ModelRequest 格式，而是本课待实现的领域工具调用。

调度器先查注册表，只允许 read_file/list_files；再校验 arguments 是对象、path 是字符串、行号是合法整数；然后调用绑定了 workspace 的 read_file。注意 root 不从模型参数复制进去。

成功时，ToolResult 中保留 c1 和真实 content/行号；`../outside.py` 形状合法但 L02 授权失败，返回 c1 的失败结果。未知工具名则在查表时拒绝，根本不走文件工具。

### 最小调度方案，而不是 eval

下面是教学骨架，不是可直接替代项目的完整实现：

```python
spec = registry.get(call.name)
if spec is None:
    return tool_failure(call.call_id, "unknown_tool")
args = spec.validate(call.arguments)
# spec.execute 已绑定可信工作区；不要执行 eval(call.name)
result = spec.execute(args)
return tool_success(call.call_id, result)
```

validate/execute/tool_failure 是职责占位符，实施时需映射真实符号。优先复用 L02，不再在 schema 层复制一套路径授权。

### 注册表究竟存什么

可以从下面的概念结构理解，不必先造复杂插件系统：

```python
registry = {
    "read_file": {
        "validate": validate_read_arguments,
        "execute": read_in_fixed_workspace,
    }
}
```

这里两个函数是待映射职责名，不是当前仓库已存在。validate只接模型参数；execute已经通过宿主注入固定workspace。模型可以选名字，但不能提供一个函数对象替换execute。

### 三种失败放在哪

未知name：调度器查表失败，不能执行。arguments不是dict或类型不对：结构验证失败，不能执行。参数是合法字符串但路径越界：结构验证通过，L02执行侧授权拒绝。

不要把所有失败都抛到循环最外层并丢call_id。将预期失败转成ToolResult，loop可以把它作为观察回传；不可恢复内部Bug可以终止，但仍记录哪次调用失败。

### 先检查哪些测试

给未知工具绑定一个一调用就raise的handler，验证它不会被碰到；给read_file传`../outside.py`，验证结构校验不等于授权通过；给两个合法call不同ID，验证每个result对应正确ID。

这三条比只测试`double(2)==4`更能证明工具协议在当前项目中安全落地。新增机制实验展示同一条链，但不替代L02的完整执行策略。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 三个对象分别是什么

**读这一段是为了解决：** 工具描述、调用提议和执行结果各由谁产生？

**原教材的浓缩句：**

> ToolSpec是能力说明：名称、用途、参数结构。

**展开与落地：**

ToolSpec 是“有哪些工具、各需什么参数”的定义；ToolCall 是模型这次选择什么；ToolResult 是程序实际做了什么。这像 Java 接口说明、请求 DTO、响应 DTO 三个层次。

把三者分开，模型就不能靠给 ToolCall 塞一个 success=true 来伪造执行结果。工具输出由真实 handler 产生，不是把请求原样回显成完成。

### K2. 两层校验不可省略

**读这一段是为了解决：** Schema通过后还要检查什么？

**原教材的浓缩句：**

> 结构校验检查必填字段、类型、未知字段。

**展开与落地：**

第一层校验结构：必要字段、类型、允许参数、范围。第二层校验现实约束：路径归属、授权、文件大小。`{"path":"../secret.py"}` 能通过字符串类型检查，但仍必须被文件授权拒绝。

本课默认未知参数拒绝，错误携带稳定代码和可修复提示。不要为提高成功率静默忽略 allow_all=true 一类额外字段；也不要让模型决定可信根目录。

### K3. 注册表限制实际能力

**读这一段是为了解决：** 为什么注册表必须限制可执行函数？

**原教材的浓缩句：**

> 用字典把允许的工具名称映射到函数。

**展开与落地：**

注册表是程序维护的名字到执行函数的映射。模型给 read_file 时只能拿到已注册的 handler，不能通过 import模块、getattr任意对象或 eval 扩大能力。

最小实现可以是 dict，不需要动态插件平台。注册时检查工具重名；列给模型的定义与实际执行注册表同源生成，避免“模型看见的能力”和“程序允许的能力”不一致。

### K4. 调用ID为什么重要

**读这一段是为了解决：** 并列工具结果怎么配回各自请求？

**原教材的浓缩句：**

> 如果模型连续请求两个文件，两次结果都叫read_file，仅靠工具名无法对应。

**展开与落地：**

call_id 用来关联请求和结果，不是装饰字段。模型一次提出 c1读A、c2读B，返回时两个结果都必须携带对应ID，不能按偶然顺序猜。

先为重复ID选择明确策略：本课同一轮拒绝重复或保证不重复执行并返回协议错误。跨轮副作用幂等不是仅靠ID字段解决，留给 L10 的持久操作身份。

### K5. Schema约束形状，不约束世界事实

**读这一段是为了解决：** 路径合法字符串就一定可读吗？

**原教材的浓缩句：**

> 参数有path:str不代表路径存在，更不代表可以读；limit:int也不保证正数。

**展开与落地：**

这一点不是再背一遍“两层校验”。用反例测试：参数JSON完全符合schema，但目标在工作区外；测试应确认 handler 内部仍做授权、目标没有打开。

结构错误通常可以让模型修改参数；权限错误不能用重试绕过。ToolResult 的错误信息需要表达能否修复输入，而不是把所有失败都写成“请再试”。

### K6. 调用ID是协议关联键

**读这一段是为了解决：** call_id重复或丢失会破坏什么证据？

**原教材的浓缩句：**

> 一个模型消息可能提出多个工具调用，返回顺序可能不同。

**展开与落地：**

上一点讲ID用途，这里讲协议不变量：每个可执行 ToolCall 都必须有对应结果；正常、拒绝、业务失败都不能丢ID。未知ID结果和重复结果不能悄悄追加进历史。

测试乱序结果、缺结果、重复ID。真正验证的是关联正确，不是 UUID 长度是否好看。供应商ID与领域ID怎样映射，也应在适配边界写清。

### K7. 工具描述是接口的一部分

**读这一段是为了解决：** 工具描述不清会在哪个阶段导致误选？

**原教材的浓缩句：**

> “搜索代码”太模糊，模型不知道何时用它。

**展开与落地：**

好的描述写明何时使用、参数单位、结果含义和限制。例如 read_file 读的是受控工作区内UTF-8文本，行号从1开始且end包含，不是“万能读取工具”。

描述属于给模型的接口信息，但不是授权机制。工具描述写“不要读外部”仍必须有执行检查。先用一个正常调用和一个错误参数查看模型是否理解，质量评估与schema合法性分开。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 工具选择 | 固定注册表，不动态eval/import | unknown_tool 时handler次数0 | 新工具只能由程序注册 |
| 参数 | 结构校验后进入原L02工具 | 坏类型拒绝、合法类型越界仍拒绝 | schema不是权限系统 |
| 关联 | 请求与结果保留call_id | 多调用和拒绝都有正确ID | 不等于跨进程幂等 |
| 模型适配 | 增加工具提议的领域表达，Fake同步升级 | 工具提议不误判空文本 | 单纯兼容HTTP地址不足以证明模型支持 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
