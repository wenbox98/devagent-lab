## 先定位阅读目的与对象

**本课要回答：一次工具选择中，哪些是不可违反的条件，哪些只是偏好？**

前提是：已有文本搜索与原生/框架编排，准备比较文本与符号工具。 本课把它推进到：先检查工具资格与索引新鲜度，再选择和验证，而不是按工具名高级与否选。

本文的知识讲解是为完成上述变化服务，不要求先掌握所有相邻技术。范围边界：AST符号索引不是向量检索；便宜不能抵消不支持或无权限。

**文中代码分两种。** [00-example.py](00-example.py)是包中已经提供的概念示例；本课“工程实现/职责路径”是对你项目的目标要求，除L00起始骨架外不表示应用已经生成。未生成时只研究示例；生成后让Codex把职责映射到实际文件，不照猜函数名找代码。

### K1. 把人群标签还原成任务条件

**读这一段是为了解决：** 所谓某类用户偏好能否还原成任务条件？

不要只记“用户甲用A，用户乙用B”。先问差异来自什么：访问范围、任务类型、索引是否存在、代码版本、时延要求。用户换了仓库或查询方式，适合工具也可能变化。能直接观测的条件优先使用，不依赖推测个人身份。

本课群体分为明确文本、符号定位、索引过期、两者均可、条件未知。这样你能解释为什么选，而不是记死用户名单。

### K2. 硬条件先过滤，偏好后排序

**读这一段是为了解决：** 权限不足的便宜工具可以先试吗？

无权限、没有索引、索引不满足版本要求，是资格问题；成本和速度通常是偏好。不能把权限违规作为低权重扣分后仍让工具获选。先构造eligible集合，再按可验证规则或模型判断选择。

规则清楚时直接程序选择；需要理解自然语言意图时可让模型在候选里选。候选为空就报告不可用或提出关键问题，不能凭空增加权限。

### K3. 工具合并还是保留两个

**读这一段是为了解决：** 合并工具会隐藏哪种外部语义差异？

如果A/B对外语义相同，只是内部实现和服务等级不同，可以暴露统一search并在内部路由。但仍需记录选了哪个后端、策略版本及原因。若参数和能力差异显著，例如一个精确文本搜索、一个符号关系查询，分开工具更利于表达。

不存在“工具越少越好”的绝对答案。合并后模型不再选后端，但内部路由仍需上下文；拆开后可表达差异，但描述模糊会增加误选。

### K4. 如何做有意义的优化实验

**读这一段是为了解决：** 对照实验中什么必须保持相同？

V0两个模糊描述；V1只改名称与边界；V2加硬过滤；V3加规则/语义路由。每次保留相同任务与模型配置，分别统计群体结果。最终任务成功是主指标，工具选择仅在可接受工具集合明确时作诊断。

教学数字例子：80个文本任务和20个索引任务，策略X分别成功72和8，总80；策略Y分别成功68和16，总84。Y总体改善，但文本群体从90%降到85%。这不是自动接受或拒绝，而要结合群体服务目标和损失权衡。数字是讲解样例，不是你的实测。

### K5. 失败时能不能切备用工具

**读这一段是为了解决：** 失败后回退是否可能重复副作用？

空搜索结果可能是真没有匹配，也可能是查询不合适，并不代表服务故障。切备用前确认权限、输入与结果语义兼容。索引过期应刷新或回退当前文件搜索，而不是继续拿过期证据修代码。写操作降级更不能盲目重复。

### K6. 先定义任务分组与可接受答案集合

**读这一段是为了解决：** 可接受工具集合如何避免武断判错？

用户A、B只是面试题的表面标签。你需要追问差异对应哪些可以观测的条件：语言、权限、仓库大小、索引版本、精确标识符或自然语言查询，以及延迟目标。定义eligible(task)得到有资格的工具；再定义acceptable(task)表示这道任务哪些路径都可以正确完成。两者不同：有资格不一定有效，有时A和B都有效，此时不能把选B判为路由错误。

### K7. 将选择过程拆成资格、排序、执行、验证

**读这一段是为了解决：** 资格、选择、执行、验证为什么分成四步？

资格是硬门槛，例如没有权限或索引过期；排序是在候选之间比较质量、延迟、费用。规则可以覆盖明确场景，语义模型负责难以通过字段表达的意图；模型只能在候选集里选择。执行后仍要验证工具结果是否满足任务，不以“路由到了标准工具”作为成功。失败回退需确认备用工具拥有权限且语义兼容，空命中不能直接当服务故障。

### K8. 优化前先明确损失和分母

**读这一段是为了解决：** 只看成功样本会怎样改变分母？

假设100个任务：80个文本组、20个符号组；X分别成功72和8，总成功80%；Y成功68和16，总84%。Y使符号组40%→80%，文本组90%→85%。如果文本组要求至少88%，Y就不能直接上线。比较每组成功、样本数、p95时延、费用与硬违规；教学数字用于算清决策，不代表你的实测。上线后流量组成变化，还要用相同分组和固定权重复看，防止平均数误导。

### K9. 工具合并的判断依据是外部语义

**读这一段是为了解决：** 统一入口什么时候有益、什么时候掩盖约束？

如果两个后端输入输出语义相同，内部统一search入口可减少模型选择负担；仍需路由日志与策略版本。如果一个返回文本位置，另一个返回符号关系，强行合并可能让参数充满可选项，反而难理解。还要考虑维护成本：新增后端时哪个接口变化、故障如何定位。技术选择不是选“最先进”的工具，而是找满足约束且有证据支持的最简单方案。

### 与你已有语言经验的连接

策略可以是接收TaskContext返回Decision的纯函数；Decision保存候选、选择理由码、策略版本，解释字段不要替代实际判断。

## 深入推演：把知识点连成因果关系

### 把“A用户用A工具”改成可解释的任务特征

工具A直接搜当前代码，工具B查询预构建符号索引。决定因素应是用户有无权限、目标是否属于索引范围、索引是否对应当前版本、查询究竟是错误字符串还是定义关系，以及预算与时延要求。人群标签可能只是这些条件的代理；换仓库、换任务后，原来的身份标签会失效。先用可观察约束解释差异，再考虑是否需要模型分类。

### 资格过滤与偏好排序不能混为一层

假设B相关度0.95但索引过期，A相关度0.70却查询当前文件。把“过期”仅减0.1分仍会选择B，这无法保证正确性。正确流程是硬条件生成eligible集合，再按偏好或语义意图选择，执行时再次授权。候选为空返回明确不可用或提出必要澄清，不把“总得选一个”当业务要求。缓存的候选列表也需绑定权限与索引版本。

### 描述改进、规则路由与训练如何选

先测V0模糊名称，再测V1清晰名称与边界；若错误来自无法看到索引状态，补V2硬过滤比训练更直接；需要理解自然语言意图时再增加分类或模型路由。只有在定义稳定、已有有代表性的标注数据和留出评测时，才讨论训练是否值得。训练不能创造实时权限与索引新鲜度，也不能修复工具本身错误。

### 用反例读懂总体提升

教学样例：80个文本任务、20个符号任务。方案X分别成功72和8，总80；方案Y分别68和16，总84。总体提高4个百分点，但文本组从90%降到85%，符号组从40%升到80%。是否采用Y取决于业务分组目标和损失，不能只说84大于80。若两种工具都可接受，就用允许集合判断选择，不强迫每题唯一标准工具。

这里的路由是“先决定调用哪条检索路径”；R02的联合检索是“调用多条路径后融合结果”。二者属于不同决策层，可以组合，不能简单互称替代品。


## 3. 一次完整推演：先预测，再读下一步

1. 案例：开发者问“哪个函数计算第一页起点”，具备两工具权限，AST索引却落后一个提交。先排除B，不能因B语义更匹配就使用旧证据。
2. 改成当前索引并询问函数调用关系，B提供关系证据；A只能文本命中，后续需多次读文件才能完成，两种最终正确路径都接受。
3. 部署规则路由后文本组退化：查看是否误分类自然语言中包含精确报错的混合查询；新增复合场景到调优集，保留集不跟着改。
4. 失败时先检查工具是否超时、真无匹配、权限拒绝或证据过期。只针对可兼容原因回退，并记录回退后的最终结果与额外费用。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 改善名称与描述 | 能力重叠但描述含糊 | 实现简单，仍依赖模型理解 |
| 规则路由 | 边界可用稳定字段表达 | 清晰可测，需处理未知条件 |
| 规则+语义路由 | 复杂意图占比足够 | 增加模型开销与误分类 |
| 统一工具后端路由 | 对外语义相同 | 要保留内部选择与失败证据 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
def route(query_kind, index_ready, index_fresh, allowed):
    eligible = [name for name in ("text", "symbol") if name in allowed]
    if not index_ready or not index_fresh:
        eligible = [name for name in eligible if name != "symbol"]
    preferred = "symbol" if query_kind == "symbol" else "text"
    if preferred in eligible:
        return preferred
    return eligible[0] if eligible else "unavailable"

print(route("symbol", True, True, {"text", "symbol"}))
print(route("symbol", True, False, {"text", "symbol"}))
print(route("symbol", True, True, set()))
```

## 5. 本课在Code Agent里实际增加什么

## 8. 面试时如何解释你做过的事

**A适合A群体B适合B群体，选哪个？**

先确认是否必须全局二选一；可动态路由则按权限/任务/版本选择，全局选型才比较分组收益和维护成本。

**优化了工具选择率就证明更好？**

不一定，多条路径可正确完成；最终结果、成本与群体退化必须一起看。

**什么时候不用模型路由？**

条件稳定且可直接判断时，规则更可解释并省一次调用；语义歧义才可能需要模型。

补一句反事实：如果“对外语义相同”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
