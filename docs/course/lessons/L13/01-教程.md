## 0. 这课为什么存在

有两个相似工具时，问题不是给它们各写一句简介就让模型随便选。本课把选择分成资格过滤、任务匹配、执行和验证，避免把不可用或无权限工具排成第一名。

用户群标签只是线索；真正决定工具选择的是任务对象、精确度、索引新鲜度、授权和成本。

## 1. 一条具体方案：从输入到结果

### 两个搜索工具的具体选择

A是即时文本搜索，支持字面关键词；B是符号索引，能按定义/引用定位，但可能过期。用户问“字符串timeout在哪出现”优先A；问“page函数定义及调用”在索引新鲜且权限满足时优先B。

若B索引版本落后当前工作区，不能因为语义更合适就直接使用。先过滤不可授权、不可用、不够新鲜的候选，再按任务需求排序。必要时降级A并说明能力差异，不能声称得到了同等引用语义。

### 选择过程需要可解释记录

```text
候选：[text, symbol]
硬拒绝：symbol(index_stale)
剩余：[text]
选择：text
结果核验：原文位置和版本仍匹配
```

不是只记录“模型认为text更好”。

### 怎样证明优化

固定任务集和允许答案集合，按字面/符号/索引陈旧/权限拒绝分组。比较always-A、always-B、规则路由，检查每组成功率、延迟、调用数和降级原因。不能只看总体平均值，把某一类用户完全退化藏起来。

### 资格过滤的伪代码顺序

```python
eligible = [t for t in tools
            if authorized(t, principal)
            and available(t)
            and fresh_enough(t, task)]
if not eligible:
    return no_eligible_tool()
selected = rank_by_task_semantics(eligible, task)[0]
result = execute(selected, task)
return verify_result(result, task)
```

这些函数是方案职责，不是固定仓库符号。第一段过滤必须在内容/能力暴露边界生效；后面执行仍需处理权限随时间变化。

### 何时拆工具，而非继续加分支

返回语义、参数约束、更新频率不同，通常值得独立工具或适配器；完全相同的合同可以共享后端接口。不要以“一次只差两行”否认长期独立演进的成本，也不要一处字段包装就复制整个系统。

验收用不同任务组观察选择与结果，两者都对才算路由有效。把资格失败的工具从分母静默删除会夸大成功率。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. 把人群标签还原成任务条件

**读这一段是为了解决：** 所谓某类用户偏好能否还原成任务条件？

**原教材的浓缩句：**

> 不要只记“用户甲用A，用户乙用B”。

**展开与落地：**

“新手用A、专家用B”不够具体。专家也可能做字面搜索，新手也可能需要精确符号定义。先把人群需求转换成任务特征和约束。

记录候选工具能处理的输入、要求的资源与可返回证据，再写选择规则。真实用户标签不能替代任务验证。

### K2. 硬条件先过滤，偏好后排序

**读这一段是为了解决：** 权限不足的便宜工具可以先试吗？

**原教材的浓缩句：**

> 无权限、没有索引、索引不满足版本要求，是资格问题；成本和速度通常是偏好。

**展开与落地：**

授权、可用性、索引版本属于硬条件，先过滤；匹配程度、延迟、成本属于剩余候选排序。不能把权限作为一个可被高匹配分抵消的权重。

测试最相似但无权限的候选必须不被执行，调用计数为0；再测试新鲜度不足的候选不能伪装正常。

### K3. 工具合并还是保留两个

**读这一段是为了解决：** 合并工具会隐藏哪种外部语义差异？

**原教材的浓缩句：**

> 如果A/B对外语义相同，只是内部实现和服务等级不同，可以暴露统一search并在内部路由。

**展开与落地：**

相同外部语义但不同后端可以共享一个接口，内部选择实现；语义不同则保留清晰的工具，避免一个search接几十个模糊参数。

判断依据是调用者需要知道什么，不是类越少越优雅。共同的授权/结果结构可以复用，独立变化仍留在各自模块。

### K4. 如何做有意义的优化实验

**读这一段是为了解决：** 对照实验中什么必须保持相同？

**原教材的浓缩句：**

> V0两个模糊描述；V1只改名称与边界；V2加硬过滤；V3加规则/语义路由。

**展开与落地：**

比较时固定语料版本、任务输入、预算和评分器。样本量与未运行项如实写，不把一次演示当线上收益。

统计成功率要说分母：全部任务、具备资格的任务还是实际执行的任务。排除失败任务后再算成功率会掩盖路由缺陷。

### K5. 失败时能不能切备用工具

**读这一段是为了解决：** 失败后回退是否可能重复副作用？

**原教材的浓缩句：**

> 空搜索结果可能是真没有匹配，也可能是查询不合适，并不代表服务故障。

**展开与落地：**

备用工具必须仍有权限、可用且满足最低任务语义。B索引不可用时A可能只能提供候选文本，不应把降级结果宣称精确符号分析。

限定切换次数与总预算，避免A失败切B、B失败又切A。记录原失败与降级理由。

### K6. 先定义任务分组与可接受答案集合

**读这一段是为了解决：** 可接受工具集合如何避免武断判错？

**原教材的浓缩句：**

> 用户A、B只是面试题的表面标签。

**展开与落地：**

一条查询可能有多个有效答案。先给任务定义可接受的文件/符号集合和必要证据，避免只认可某个固定排序。

分组用于发现系统性偏差，例如代码符号查询一直不如字面任务，而不是给用户群贴优劣标签。

### K7. 将选择过程拆成资格、排序、执行、验证

**读这一段是为了解决：** 资格、选择、执行、验证为什么分成四步？

**原教材的浓缩句：**

> 资格是硬门槛，例如没有权限或索引过期；排序是在候选之间比较质量、延迟、费用。

**展开与落地：**

执行后还要验证结果：候选选对并不保证索引返回新鲜证据。权限和版本必须在真正暴露内容前有效。

记录资格、排序、调用和结果校验四段数据，失败时可以定位在哪个阶段，而不是统一说模型选错工具。

### K8. 优化前先明确损失和分母

**读这一段是为了解决：** 只看成功样本会怎样改变分母？

**原教材的浓缩句：**

> 假设100个任务：80个文本组、20个符号组；X分别成功72和8，总成功80%；Y成功68和16，总84%。

**展开与落地：**

把误选成本写清：执行不了、返回无关证据、泄漏无权限内容、耗时过长分别有不同严重性。安全约束不能用平均分抵消。

优化目标是在硬条件满足下提高任务成功，延迟和成本另报告。无需先造一个万能加权评分公式。

### K9. 工具合并的判断依据是外部语义

**读这一段是为了解决：** 统一入口什么时候有益、什么时候掩盖约束？

**原教材的浓缩句：**

> 如果两个后端输入输出语义相同，内部统一search入口可减少模型选择负担；仍需路由日志与策略版本。

**展开与落地：**

如果调用者总要知道是文本命中还是符号定义，就不要强行抹平为字符串列表。共同字段是来源/版本/错误，能力差异需保留。

反过来，两个后端都返回同样的定义位置时，可隐藏后端细节并统一接口。不要仅按供应商名字决定是否拆工具。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 路由 | 先资格后排序 | 权限/陈旧候选不会被调用 | 不把安全当权重 |
| 降级 | 保持最低语义并说明差异 | 候补可用才执行、切换有上限 | 文本检索不是符号分析等价替代 |
| 评测 | 按任务组比较三种策略 | 分母和每组退化可见 | 不凭单次主观效果选型 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
