## 1. 先知道这课到底要解决什么

### K1. LLM调用的最小模型

**读这一段是为了解决：** 应用实际发送和接收的最小信息是什么？

模型接收上下文并生成后续输出。一次HTTP请求通常不会自动记住上次对话；应用要按API契约发送历史。system/developer等指令角色与user内容的具体支持取决于提供商，不能假设接口完全相同。Token是模型处理文本的单位，不等于汉字数或Python len。

上下文容量同时受输入、工具定义、历史和预留输出影响。temperature等采样参数会影响输出分布，但设为0也不应作为逐字完全可重复的保证。先只发一个简单任务，避免把模型接入与多轮记忆混在一起。

### K2. 适配器该隔离什么

**读这一段是为了解决：** 为什么不把SDK对象传遍业务层？

业务代码需要text、tool_calls、usage、finish_reason等统一概念，供应商可能用不同名字或嵌套对象。适配层负责请求构造、字段转换、错误映射；Agent循环不直接读取SDK对象。现在只接文本；到L04再扩展工具调用，保持模拟客户端一同升级。

不要为了“统一”丢掉重要语义：没有用量数据要记录unknown，不能填0；没有最终文本也可能是工具调用或输出被截断，后续不能简单当空结果。

### K3. 把配置错误与服务错误分开

**读这一段是为了解决：** 缺配置和限流为何不能同样重试？

密钥没配置时，应在发网络请求前返回config_missing；401/403通常需要检查身份或权限；429需要区分速率限制与额度不足，并参考提供商信息；网络超时不等于认证失败。只对明确支持的错误做映射，原始错误信息经过脱敏保留。

你已有聊天订阅不代表API一定有可用额度。先在选定提供商的官方控制台准备访问方式；没有凭据可做模拟部分，但真实接入项保持未通过。

### K4. 如何学习SDK而不被版本困住

**读这一段是为了解决：** 遇到旧SDK代码该核对什么？

先看项目里是否已有SDK与配置；没有就选自己能访问的一个提供商。代码生成AI必须读取该提供商当前官方文档，给出真实安装版本和最小调用。你关注输入、返回、异常和超时四件事。模型名来自你实际有权限的列表，不从教材猜一个可能不存在的名称。

### K5. 模型不是普通的确定性纯函数

**读这一段是为了解决：** 为什么一次正常回应不能证明长期稳定？

同样输入可能得到不同输出；调用还可能包含工具提议而非最终文字。客户端适配器要保留消息角色、工具调用、结束原因和实际用量，不要只返回字符串。你在Java里习惯的Service接口仍然适用：领域层依赖统一Client协议，具体SDK放在适配器。这样更换供应商时主要修改边界，不扩散到整个循环。

### K6. Token、上下文与价格的关系

**读这一段是为了解决：** 字符长度、Token用量、计费为何不能混算？

Token是模型编码单位，不能把一个汉字永久等同于一个Token。上下文容量约束本次输入与输出空间；价格通常按输入输出用量等维度计费，具体查供应商。先预留输出空间，再给输入分配预算。请求前可估算，响应后记录实际usage；供应商未给usage就标unknown。零用量意味着确定没有消耗，两者会导致完全不同的成本结论。

### K7. 超时分层与能力探测

**读这一段是为了解决：** 哪个超时发生在连接前、响应中或整任务上？

连接失败、读取超时、被限流、认证失败不是一种错误。认证失败应先修配置；限流可能适合有界等待；读取超时可能无法确定远端完成情况。还要探测模型是否支持工具调用和结构化输出，不能因为接口地址兼容就认定能力完全兼容。用最小真实请求核对能力，再让离线客户端验证编排。

### 与你已有语言经验的连接

Protocol表达接口约定；dict.get默认值要区分缺失与0；环境变量由入口读取，避免在模块导入时发请求。

## 深入推演：把知识点连成因果关系

### 适配器隔离的是变化，而不是抹平所有差异

你的应用想要的是“输入消息、得到结果或可解释的错误”，供应商SDK却可能返回不同对象、不同用量字段和不同错误类型。把SDK留在适配器内部：配置读取→构建请求→真实调用→解析响应→转为领域结果。上层不应到处访问`response.choices[0]`之类供应商特定结构。换供应商时，修改面主要集中在适配器与兼容测试，而不是工具、路由和验收器。

但统一接口不代表各模型功能相同。某模型支持工具调用不等于支持所有结构化输出策略；某个参数在一家有效，在另一家可能被拒绝。因此适配器还需要可验证的能力说明，不能静默删掉不支持的参数后宣布接入成功。把实际SDK版本、模型标识、端点类型、超时与重试配置写进环境记录，不使用“永远最新”作为依赖约束。

### 一次网络失败包含哪些不同事实

没有配置密钥，应在请求前失败；认证失败通常需要修凭据，重复请求没有解决条件；限流可能需要等待或降低并发；读超时说明客户端没按时获得完整响应，不代表服务端没有完成计算。先保留这些区别，再决定哪些错误能重试。注意SDK可能自己重试，应用再套一层会放大真实调用次数。你要查实际配置，而不是只数代码里出现几次`complete()`。

### 怎样设计不碰运气的测试

先用模拟SDK响应验证字段映射：有文本、空文本、缺字段、用量缺失、抛认证异常、抛超时。然后用一个极短真实请求验证网络、凭据、模型权限和解析链路。前一组通过说明适配逻辑符合你构造的契约，后一组才说明当前环境真的接通；两者不能互相替代。用量字段缺失应记录unknown/null，不能写0，否则会把“没观测到”误当成“免费”。

ChatGPT订阅与自行开发程序使用的API是不同产品入口；课程不会把你的聊天登录状态当作API凭据。仅在你自行配置服务和预算后运行真实调用。


## 3. 一次完整推演：先预测，再读下一步

1. 请求只含user消息时，把system约束遗漏作为实验；检查真正发送的消息列表，而非你以为拼入的提示。
2. 让脚本客户端先返回工具提议：如果适配器只提取text，下一层看不到工具，此时应修适配协议。
3. 响应usage缺失，报表保留null/unknown；随后真实请求补齐用量，比较估算误差并注明模型版本。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 脚本客户端 | 确定性错误与分支测试 | 不能用来证明模型能力 |
| 真实调用 | 核对工具能力与结果质量 | 有费用和随机性，记录配置 |
| 换模型 | 证据已齐仍反复推理失败 | 不能修复适配器丢字段 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
def normalize(raw):
    return {
        "text": raw.get("answer", ""),
        "input_tokens": raw.get("usage", {}).get("input"),
        "output_tokens": raw.get("usage", {}).get("output"),
    }

print(normalize({"answer": "hello"}))
print(normalize({"answer": "hello",
                 "usage": {"input": 12, "output": 3}}))
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
python .local/concepts/L01/00-example.py
```

预期观察：

```text
{'text': 'hello', 'input_tokens': None, 'output_tokens': None}
{'text': 'hello', 'input_tokens': 12, 'output_tokens': 3}
```

### 按因果关系理解输出

这是自定义假响应，用于理解适配思想，不是任何供应商SDK格式。第一次缺usage时保留None，第二次保留真实计数。实际实现要按官方结构映射，不能把这里的answer字段直接套到所有API。

现在只修改练习副本`.local/concepts/L01/00-example.py`中的指定输入：只把第二次调用的usage字段去掉，再设为None；先观察当前简化函数是否支持None，再讨论适配器如何明确处理。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 8. 面试时如何解释你做过的事

**为何不直接在业务里调用SDK？**

短期可行，但多处依赖厂商格式会使升级、模拟和换模型的改动分散。

**用量缺失能算免费调用吗？**

不能；这是未观测到费用依据，不是实际费用为零。

补一句反事实：如果“证据已齐仍反复推理失败”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
