## 0. 这课为什么存在

L00 已经允许替换 client，现在要把真实供应商放到这个位置。新增的价值不是学会一个 SDK 方法，而是让 URL、鉴权、JSON 字段和错误变化停在边界里，上层仍只认识领域结果。

你可以用 Java 接口加 Adapter 理解，但不需要照搬 SPI 自动发现机制：接口契约与服务加载是两个问题。本课先做统一调用形状和供应商翻译，不做插件平台。

## 1. 一条具体方案：从输入到结果

### 对着已实现的代码区分三层

当前基线使用标准库 HTTP 客户端，不是供应商 SDK：

```text
__main__.main 选择 fake / real
    → app.run_task 调用 client.complete
    → OpenAICompatibleAdapter 构建请求
    → UrllibJsonTransport.post_json 负责 HTTP 与 JSON
    → normalize_response 转成 ModelResponse
    → app.run_task 转成 RunResult
```

`complete()` 从 config 或环境变量取得配置，拼 `/chat/completions`，构造含 user 消息的 payload。它把网络交给 transport，所以测试可以注入 ScriptedTransport；默认的 UrllibJsonTransport 才使用真正的 urlopen。

### 从响应字段理解“统一但不造假”

供应商样本 `usage.prompt_tokens=4` 被映射到 `ModelResponse.input_tokens=4`；缺失 usage 则映射到 None。`usage="unknown"` 不是合法缺失，而是类型错误，当前代码会抛 ProviderResponseError。

`app.py` 用 `except ProviderResponseError` 显式返回 `provider_parse_error/4`。异常类名与错误字符串没有自动转换规则，是我们写的映射代码在连接它们。

当前练习还支持单层 `response` 包装。外层 `status/code` 不会自动当成 HTTP 状态或业务成功证明；新供应商若给这些字段定义了成功/失败语义，应另定协议规则，不能只看到包一层就盲目解包。

### 两种测试各证明哪一段

`test_provider_errors_stay_distinct_and_are_not_retried` 注入会抛领域异常的 ScriptedTransport，验证最终 RunResult；`test_http_transport_maps_status_and_timeout_without_retry` patch 底层 urlopen，验证 HTTPError/TimeoutError 怎样被翻译。二者各自有边界，不能用其中一个宣称整条真实网络都验证过。

### 从一个真实方法拆开三次翻译

在当前`OpenAICompatibleAdapter.complete()`中，先取得配置，再组装外部请求。关键片段如下：

```python
config = self._config or load_provider_config(self._environ)
endpoint = config.base_url.rstrip("/") + "/chat/completions"
headers = {"Authorization": "Bearer " + config.api_key,
           "Content-Type": "application/json"}
payload = {"model": config.model,
           "messages": [{"role": "user", "content": model_request.task}]}
raw = self._transport.post_json(endpoint, headers, payload, config.timeout_seconds)
return normalize_response(raw, config)
```

这是从真实代码抽取的主干，省略了异常分支，并非整方法。`ModelRequest.task`是内部名字，messages/content是外部协议；`post_json`返回raw；`normalize_response`再把它翻译回内部`ModelResponse`。

`config = ... or ...`在当前对象有真值的条件下做默认选择，但语义上是“有显式配置就用，否则加载”。如果将来允许自定义假值对象，应改成明确的is not None，不把or当空值合并运算的完全替代。

### 为什么可以换transport而不重写业务

Adapter只要求transport提供post_json。默认实现真的HTTP；ScriptedTransport直接返回或抛异常。两种路径都经过相同的normalize_response和app，只有最底层输入来源不同。

你要证明字段映射，就给raw；要证明HTTP异常转换，就patch urlopen；要证明真实接入，再用真实服务。替代哪一层决定你能得出多大范围的结论，不是用了mock就所有业务都假了。

### 为什么新增字段不会迫使Fake重写所有调用点

新字段有默认None，例如`model: str | None = None`，原有`ModelResponse(text, provider)`仍能构造；但类型兼容只是第一步，还要运行L00回归检查原成功、超时、空响应和trace语义。

模型字段缺失时当前代码回退config.model；usage字段缺失则不回退为0。这两个默认策略不同，是因为“模型请求标识可从配置知道”，但实际用量不能从配置推断。

### 从错误类到错误码没有魔法

`ProviderResponseError`由适配边界抛出；`app.run_task`捕获后明确写`provider_parse_error`。如果你只是新建一个异常类，却没有决定上层如何处理，错误字符串不会自动出现。

这像Java的领域异常被ControllerAdvice映射成响应码，但当前Python实现是在应用函数内显式处理。不要为符合Java习惯而立即引入额外框架。

## 2. 逐点展开：原句省略了哪些步骤

不是新的八股题。已经熟悉的经典概念可略读，但要能指出本项目采取的策略与验证证据。

### K1. LLM调用的最小模型

**读这一段是为了解决：** 应用实际发送和接收的最小信息是什么？

**原教材的浓缩句：**

> 模型接收上下文并生成后续输出。

**展开与落地：**

先只发一个短 user 任务，打印脱敏后的请求结构或用测试捕获 payload。所谓上下文，是这次接口实际接收的消息和证据，而不是程序员脑中记得的聊天历史。

API 是否由服务端保存历史，要看接口合同；无状态请求必须由应用带上历史。当前 ModelRequest 只有 task，不能把教材提到 system、tool_calls 当成基线已经实现多轮消息。本课知道输入/输出边界，消息扩展在 L03/L04 明确落实。

### K2. 适配器该隔离什么

**读这一段是为了解决：** 为什么不把SDK对象传遍业务层？

**原教材的浓缩句：**

> 业务代码需要text、tool_calls、usage、finish_reason等统一概念，供应商可能用不同名字或嵌套对象。

**展开与落地：**

分开三件事：请求构造把领域输入变成外部 payload；字段映射把外部响应变成 ModelResponse；错误映射把外部失败变成已知类别。不要让 app 到处读取 choices[0]。

统一格式不等于统一能力。没有 usage 用 None 表达未知；不支持工具调用应由能力说明或明确不支持状态表达，不假造一次工具调用。小包装差异可由专门解包函数复用解析；若不同供应商独立演进，就分别维护适配器，不能长期积累猜字段的 if/elif。

### K3. 把配置错误与服务错误分开

**读这一段是为了解决：** 缺配置和限流为何不能同样重试？

**原教材的浓缩句：**

> 密钥没配置时，应在发网络请求前返回config_missing；401/403通常需要检查身份或权限；429需要区分速率限制与额度不足，并参考提供商信息；网络超时不等于认证失败。

**展开与落地：**

当前 load_provider_config 未收到显式映射时使用 os.environ；传入 {} 则是刻意构造缺配置，不应被 `environ or os.environ` 覆盖。必填 provider/model/key/base_url，超时有默认值。

测试应注入 fixture_config，不依赖本机密钥。缺配置时必须证明 transport 调用数为 0；只有真实发请求后的认证拒绝才是另一种事实。配置错误和服务错误都可以让任务失败，但修复动作不同。

### K4. 如何学习SDK而不被版本困住

**读这一段是为了解决：** 遇到旧SDK代码该核对什么？

**原教材的浓缩句：**

> 先看项目里是否已有SDK与配置；没有就选自己能访问的一个提供商。

**展开与落地：**

按“当前实际依赖 → 官方接口文档 → 最小请求 → 记录版本和返回结构”学习。不为了跟教材字面一致就额外安装一个 SDK。当前使用 urllib，记录 Python/client_version；未来改 SDK 时要记录其实际版本、超时和默认重试配置。

模型名从真实账号可用列表取得，不把教学 fixture-model 放进真实请求。没有访问凭据时保留 real-once blocked，照常完成离线映射测试。

### K5. 模型不是普通的确定性纯函数

**读这一段是为了解决：** 为什么一次正常回应不能证明长期稳定？

**原教材的浓缩句：**

> 同样输入可能得到不同输出；调用还可能包含工具提议而非最终文字。

**展开与落地：**

测试确定性的适配逻辑时固定 raw 或异常，而不是断言模型每次都说同一句话。真实接入测试只验证当次环境能取得可解析响应，不能证明长期效果稳定。

同理，temperature=0 不应当作逐字可重现保证。本课的控制流测试依赖 scripted transport；模型质量需要后续任务集和重复试验。不要让同一个绿色测试同时冒充这两类证据。

### K6. Token、上下文与价格的关系

**读这一段是为了解决：** 字符长度、Token用量、计费为何不能混算？

**原教材的浓缩句：**

> Token是模型编码单位，不能把一个汉字永久等同于一个Token。

**展开与落地：**

字符数是本地文本限制，token 是模型编码/计费相关单位，不能固定换算。输入与输出用量分别保留；缺失任一项就不能把该项费用算成零。

一个可执行的报表策略是：已知部分求和，另列 unknown_call_count；有未知调用就把总费用标成不完整估计。价格另由已核对的计价表绑定 provider/model/日期，不写进通用 Adapter 的字段解析。

### K7. 超时分层与能力探测

**读这一段是为了解决：** 哪个超时发生在连接前、响应中或整任务上？

**原教材的浓缩句：**

> 连接失败、读取超时、被限流、认证失败不是一种错误。

**展开与落地：**

先识别观测边界：配置读取发生在网络前；HTTP 状态来自响应；读取超时表示客户端未及时拿到完整结果，不证明远端未计算。当前本课不加自动重试，测试断言每个受控调用点只被调用一次。

Mock 的 call_count 是这个函数被调用的次数，不是服务器收到的请求数；真实 HTTP 重定向、SDK 内部重试是更低层事实。能力探测也需要单独的最小请求，地址格式兼容不能证明 tool calling 等能力兼容。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 替换供应商 | 上层依赖 ModelRequest/ModelResponse，外部字段留在 Adapter | 相同输入协议下检查输出各字段 | 同名 provider 样本不证明两家真实服务兼容 |
| 未知用量 | None 保留未知，显式 0 保留 0 | 分别构造缺失和零用量 | 不把缺失当免费 |
| 网络测试 | 注入 transport 或 patch 底层调用，分别验业务结果与次数 | 异常映射和 call_count 双断言 | 不实际请求公网 |
| 跨平台 CLI | 父进程 encoding UTF-8，子进程 PYTHONIOENCODING UTF-8 | 中文成功输出可被 json.loads | 源码保存编码不是管道编码 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
