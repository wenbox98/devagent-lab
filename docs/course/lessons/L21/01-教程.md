## 先定位阅读目的与对象

**本课要回答：同一个任务跨两个服务以后，谁判断“是谁”，谁判断“做完没有”？**

前提是：Python和Java分别可用，组合后还要统一身份、ID与状态来源。 本课把它推进到：让提交、查询、取消、恢复和产物访问沿可信身份授权，并保留两端证据。

本文的知识讲解是为完成上述变化服务，不要求先掌握所有相邻技术。范围边界：知道ID不等于有权限；教学authorize不是完整认证系统。

**文中代码分两种。** [00-example.py](00-example.py)是包中已经提供的概念示例；本课“工程实现/职责路径”是对你项目的目标要求，除L00起始骨架外不表示应用已经生成。未生成时只研究示例；生成后让Codex把职责映射到实际文件，不照猜函数名找代码。

## 1. 先知道这课到底要解决什么

Python单独能修bug，Java单独能接受任务，但联调时用户查不到任务、重复提交又出现两个ID。完整项目的难点在边界：谁判断权限、谁拥有执行状态、哪个ID可以追踪一次操作。

- 独立完成“加入跨用户产物下载检查。”，并说明换到新业务时哪些条件需要重新确认。

### K1. 确定状态所有权

**读这一段是为了解决：** Java和Python各拥有哪一种状态事实？

Python拥有实际执行状态、工作区和工具事件；Java拥有用户身份、提交幂等记录与执行ID映射。Java可缓存展示状态，但不能凭HTTP异常创造另一套事实。查询或事件同步需要版本/序号，避免旧消息把新状态覆盖。

联调文档要列请求字段、错误码和版本，不靠双方各自猜测。提交、查询、取消三个动作都测试。

### K2. ID不是权限

**读这一段是为了解决：** 知道execution_id为什么仍要校验资源归属？

知道task_id并不代表可以查询该任务。Java从可信认证上下文取owner，再检查提交归属；不能相信用户body里自填owner_id。Python内部接口限制访问和服务身份，避免绕过Java直接调用任意执行能力。

教学版可以使用仅本地的明确测试身份配置，但要标注边界。禁止把可随意伪造的请求头当生产鉴权。

### K3. 从干净环境复现

**读这一段是为了解决：** 为什么要从干净环境验证一次启动？

把必需服务、环境变量名称、依赖版本、数据库迁移与启动顺序写清。使用示例配置而非真实密钥。先启动数据库与Python，再Java，运行健康检查与演示任务。

演示包含一个正常修复和一个超时/取消/恢复路径。只演示顺利流程，无法说明你解决了工程问题。

### K4. 联调失败的排查顺序

**读这一段是为了解决：** 协议、身份、状态和运行环境怎样分层排障？

先身份与权限，再接口契约，再execution_id映射，再状态事件，最后具体工具行为。若Java查询404，先确认查询的是Java提交ID还是Python执行ID，不要立即重写Agent循环。

### K5. 身份由可信入口产生并贯穿整个任务

**读这一段是为了解决：** 哪个入口能可信地产生用户身份？

用户请求中的tenant_id不能直接成为授权事实。入口认证得到principal，授权后生成任务；Java调用Python使用服务身份与签名/令牌等既定方案，但仍传递经校验的任务归属。查任务、取结果、取消和下载产物都检查所有权。拥有随机task_id不代表拥有访问权，随机性只是降低猜测概率。

### K6. 业务ID、执行ID和追踪ID分工

**读这一段是为了解决：** 业务ID、执行ID、追踪ID各回答什么问题？

task_id关联用户业务任务；execution_id或attempt_id区分执行；operation_id为副作用幂等；trace_id帮助追踪一次调用链。把它们全部用一个字符串替代会混淆重试与新任务。日志中建立映射，但接口返回只暴露必要字段。错误转换也要保留来源与可操作类别，避免Java把Python的unknown统一映射成failed。

### K7. 联调验证最容易漏掉组合故障

**读这一段是为了解决：** 正常单服务测试会漏掉哪些组合故障？

单模块测试通过，不代表重复提交+服务重启+取消并发时正确。用受控故障逐次改变一个条件，再组合高价值场景；记录各服务状态与外部副作用计数。跨服务对齐必须有最终一致的期限或待对账状态，不能承诺网络分区下立即一致。所有实验用隔离工作区与测试数据。

### 与你已有语言经验的连接

HTTP状态、业务状态与异步终态分别建模；协议序列化不丢失unknown和错误来源。

## 深入推演：把知识点连成因果关系

### 联调的困难主要在契约，不在各自能否启动

Java提交后得到submission_id，Python执行有execution_id，LangGraph运行有thread_id，工具副作用还有operation_id。它们相关却职责不同，不能用一个字符串到处替代。建立明确映射，并在日志中记录关联关系；对外接口只暴露必要标识，内部thread_id不能当作用户拥有任务的凭据。

### 身份必须来自可信边界

请求body里自填owner_id不构成认证。Java从可信认证上下文识别主体，再检查资源归属；Python内部接口验证服务身份并限制访问，避免用户绕过Java直接提交执行。教学的alice/bob只是测试身份，要明确其启用范围，不宣传为完整生产认证。

### 一份干净环境复现比一次本机演示更有价值

锁定实际依赖，说明数据库迁移、配置变量名、启动顺序、健康检查与演示命令。至少演示正常修复、重复提交、权限拒绝、取消和恢复。数据同步采用序号或版本处理重复与乱序，避免迟到的running覆盖succeeded。环境缺项应清楚标blocked，不在报告里写“理论上应该成功”。


## 3. 一次完整推演：先预测，再读下一步

1. 用户甲提交任务，用户乙持有task_id查询、取消和下载：均拒绝，不能只保护提交接口。
2. Java等待超时，Python已完成：通过稳定execution_id对账，最终任务成功且只执行一次。
3. 取消请求与完成事件竞争：根据状态转换规则得到一个可解释终态，产物与状态一致。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 信任请求中的租户字段 | 仅作为待校验输入 | 不能作为身份来源 |
| 服务认证+任务归属检查 | 跨服务可信传递 | 两层都要实现 |
| 统一trace | 定位跨服务路径 | 不替代业务ID与幂等ID |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
submission = {"owner": "alice", "execution_id": "exec-7"}
def authorize(current_user):
    if current_user != submission["owner"]:
        return "forbidden"
    return submission["execution_id"]

print(authorize("alice"))
print(authorize("bob"))
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
python .local/concepts/L21/00-example.py
```

预期观察：

```text
exec-7
forbidden
```

### 按因果关系理解输出

current_user在示例中是直接传参，真实服务必须从经过验证的认证上下文获得；这个函数本身不完成登录验证。它演示认证之后仍要做资源归属校验。

现在只修改练习副本`.local/concepts/L21/00-example.py`中的指定输入：保持execution_id不变，把current_user从alice换成bob；再换成不存在的用户。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 8. 面试时如何解释你做过的事

**为什么不能按task_id直接查？**

ID是定位资源，不是授权凭据，仍需校验当前主体与资源归属。

**Java和Python状态冲突听谁的？**

执行事实以Python为主，Java提交与身份记录有自己的明确职责，投影需版本核对。

补一句反事实：如果“定位跨服务路径”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
