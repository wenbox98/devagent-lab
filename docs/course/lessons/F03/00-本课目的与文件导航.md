## 1. 为什么现在学这一课

**当前条件（不是对你进度的断言）：** 框架循环可用且已有独立grader，现在增加调用控制和结构化声明。

**本课问题：** 为什么格式正确的“成功报告”，还需要独立证明它说的事情发生过？

**期望变化：** 区分可信context、调用中间件、输出Schema和事实验证。

**不做这一步的风险：** 重试、鉴权和输出校验的顺序不清，可能重复执行本应拒绝的动作；结构合法的结果也可能缺少真实证据。

顺序前置：[L18本课目的](../L18/00-本课目的与文件导航.md)。前置是能力条件，不是“看过文档”即可；由Codex核对现有源码/测试。 后续[F04](../F04/00-本课目的与文件导航.md)继续使用本课产物。

**本课不负责：** 结构合法不等于任务成功；不让模型填写自己的权限。

## 4. 今天先做哪一个动作

只想理解：打开[本课教程](01-教程.md)，先回答“为什么格式正确的“成功报告”，还需要独立证明它说的事情发生过？”。

## 5. 读不懂时，带着什么目的查资料

下列问题与[教程](01-教程.md)的知识段一一对应。查到能回答该问题、能指出观察证据即可先回到实验，不要求把官方站点读完。

| 本课知识段 | 为什么讲：你要解决的具体问题 |
| --- | --- |
| 一、为什么不能把所有控制都写进提示词 | 哪些约束必须控制真实调用而非只写入提示词？ |
| 二、包围型中间件是在控制真正的调用 | handler未调用和调用失败怎样区分？ |
| 三、结构化输出解决的是形式契约 | 结构化输出最多保证哪一层契约？ |
| 四、用一个反例暴露两类校验 | 合法成功结构但证据不存在时由谁拒绝？ |
| 五、把权限、业务状态与观测分层 | 身份、业务验收和观测为什么不应混成一个中间件？ |

可复制检索词：`LangChain middleware runtime context structured output Pydantic validation`。优先使用[本课教程末尾的官方参考](01-教程.md)和[官方阅读路线](../../09-技术版本与官方阅读路径.md)。这些链接沿用已有教材来源；本轮聚焦结构与指代，未重新核验所有网页或依赖版本。

## 6. 本课完成后要留下什么

**项目阶段怎样证明风险已被处理：** 调换重试和鉴权中间件顺序，看被拒绝调用是否被重复；使用计数器而不是仅看日志文案。

要能串起：**宿主context → model/tool middleware → schema结果 → verifier事实校验；四者责任不同。**

具体证据看：schema_error、missing_evidence、wrong_task、not_verified之间的区别。

在`docs/learning-records/F03.md`分别填写概念观察、实际实现、独立修改和未验证项。源码地图由Codex基于实际源码填写；个人理解由你填写。标准库示例、框架离线运行、真实API、完整服务是不同验证层次。
