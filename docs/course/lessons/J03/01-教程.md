### K1. 先画一条请求耗时账

**读这一段是为了解决：** 响应时间应怎样拆成可定位的阶段？

记录request_id、submission_id、execution_id，并分解Java排队、拿连接、SQL、Python请求与序列化时间。若拿连接耗时占大头，先查连接池占用者；若SQL执行占大头，再看执行计划。总时间不能仅由某条日志间隔猜测。

模拟环境应固定数据量与请求分布。修改前后使用同一数据和查询，不用小表快查询来证明大表索引效果。

### K2. 索引要与过滤排序对应

**读这一段是为了解决：** 过滤和排序字段怎样决定候选索引？

典型查询按owner_id与dispatch_state过滤，再按created_at倒序取20条。可比较无索引与(owner_id,dispatch_state,created_at DESC)组合索引。索引是否被使用由统计信息、选择性和优化器决定，不能强求任何规模都出现Index Scan。

EXPLAIN描述计划，EXPLAIN ANALYZE会实际执行语句。这里只对测试数据库的SELECT使用；检查实际行数、过滤行数、循环次数、排序和buffer，而不是只看计划节点名字。

### K3. 长事务和连接泄露的区别

**读这一段是为了解决：** 连接一直被持有可能是长事务还是泄漏？

长事务可能合法持有连接但时间过长；泄露是借出后没有归还。若业务在数据库事务中等待远程Agent两分钟，即使finally正确，也会耗尽连接。应缩短事务范围，把远程等待放到事务外，再用状态协议衔接。

线程转储看线程在等锁、连接、网络还是计算。看到WAITING并不能直接判断异常，要结合对应资源与请求负载。

### K4. 形成可复现诊断报告

**读这一段是为了解决：** 什么样的报告能让别人复现诊断？

写明现象、两个假设、区分实验、修复和回归。修好SQL后还需验证返回顺序和分页语义；缩短事务后还需验证状态一致性。性能优化不能破坏正确性。

### K5. 慢请求要先拆耗时再改SQL

**读这一段是为了解决：** SQL很短时为什么还可能请求很慢？

接口慢可能发生在连接池等待、数据库执行、锁等待、远程调用或结果序列化。总耗时与SQL日志中的执行耗时并不相同。先通过trace分段：若SQL只执行20ms而连接等待2秒，加索引未必有效；若大事务占着连接等待模型，就应移动远程调用出事务并检查事务范围。

### K6. 读执行计划需要看估计与实际

**读这一段是为了解决：** 执行计划的估计和实际差异告诉什么？

EXPLAIN给计划估计；EXPLAIN ANALYZE会实际执行，写语句尤其不能随意在真实业务库上试。关注扫描方式、过滤行数、实际/估计行数、循环次数和缓冲区，不能把Index Scan自动当好计划。小表顺序扫描可能合理，低选择性索引可能成本更高；用代表性数据量与参数验证。

### K7. 索引由查询条件和排序需求决定

**读这一段是为了解决：** 索引为什么不能只按字段有没有来判断？

任务查询常用tenant_id、status、created_at与稳定id排序，复合索引顺序要结合等值过滤和范围排序。深offset需要跳过越来越多行，可比较键集分页；但并发插入与状态变化仍涉及一致性约定。索引会增加写入和存储成本，应记录前后计划与耗时，避免为每个字段盲目建索引。

### 与你已有语言经验的连接

Java重点：连接池指标、事务持续时间与调用链；SQL重点：过滤、排序、复合索引、EXPLAIN证据。

## 深入推演：把知识点连成因果关系

### 慢请求先分段，再决定看SQL还是线程

一次查询任务列表慢，可能耗在排队、连接池、SQL执行、锁等待或序列化。先用trace_id关联入口与下游耗时，找到主要等待段。若没有分段证据就加索引，可能掩盖连接耗尽或长事务；若SQL本身快，线程dump和连接池指标更有价值。

### 索引设计要对应查询谓词与排序

示例按owner与状态过滤，再按created_at倒序取20条。复合索引的列顺序应结合真实过滤选择性和排序需求；不是把WHERE出现的列随便拼一起就一定快。比较执行计划中的估计与实际行数、扫描方式和缓冲命中，理解优化器为何选择计划。小表顺序扫描可能合理，不能见到Seq Scan就说数据库有问题。

### 测试计划也可能真正执行写入

EXPLAIN ANALYZE会执行语句，应只对授权测试环境和受控查询使用；不要对生产写操作试验。数据库统计、数据量、冷热缓存都会影响结果，记录实验环境和多次观察，而不是挑最快一次。建立索引还增加写入维护和存储成本，需把读收益与写负担一起说明。


## 3. 一次完整推演：先预测，再读下一步

1. 接口p95=2.2s、SQL=30ms、连接等待=2s：检查连接池占用及长事务，不先加索引。
2. 测试库构造足量且分布合理的任务数据，对tenant/status排序查询比较计划，记录实际行数与估计差异。
3. 把远程调用移出事务后再测，确认连接等待下降；若SQL仍慢，再针对查询和索引优化。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 加索引 | 过滤/排序确有扫描瓶颈 | 有写放大，需计划验证 |
| 调大连接池 | 数据库仍有可用吞吐 | 过大可能争用更严重 |
| 缩短事务 | 连接被无关远程等待占用 | 保持业务一致性协议 |
| 键集分页 | 深分页且排序键稳定 | 跳页与一致性语义有变化 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT execution_id, dispatch_state, created_at
FROM task_submission
WHERE owner_id = 'user-1' AND dispatch_state = 'pending'
ORDER BY created_at DESC
LIMIT 20;

CREATE INDEX idx_task_owner_dispatch_state_created
ON task_submission (owner_id, dispatch_state, created_at DESC);
```

## 8. 面试时如何解释你做过的事

**用了索引就一定更快吗？**

取决于选择性、数据量、排序和缓存等，要看真实执行与结果。

**连接都在用就是连接泄露吗？**

也可能是长事务或慢调用持有，需追踪借用生命周期。
