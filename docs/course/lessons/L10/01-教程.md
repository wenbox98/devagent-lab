## 先定位阅读目的与对象

**本课要回答：超时告诉我没收到什么，却不能告诉我没发生什么？**

前提是：L09能自动修复，但写入已完成、返回丢失时无法凭超时判断结果。 本课把它推进到：稳定操作身份绑定请求内容；未知状态先核对，重试不产生第二次逻辑写入。

本文的知识讲解是为完成上述变化服务，不要求先掌握所有相邻技术。范围边界：内存records不是崩溃恢复；不宣称外部副作用恰好一次。

## 1. 先知道这课到底要解决什么

工具修改了文件，随后把结果发回应用时连接断了。应用看到超时，文件却已经变了。直接重试可能重复追加；直接报告失败又可能误导用户。这课训练你处理“结果未知”，它同样会出现在Java订单、支付和任务提交中。

- 独立完成“为幂等记录增加处理中状态。”，并说明换到新业务时哪些条件需要重新确认。

### K1. 超时只描述观察，不描述结果

**读这一段是为了解决：** 没收到回应可以推出操作没执行吗？

客户端没收到结果，不代表服务端没执行。先区分执行前明确拒绝、执行后已确认成功、无法确认三种状态。对未知状态，优先用操作ID查询或核对目标状态；只有确认条件允许才重试。

读操作通常更容易重试，但仍要考虑费用、数据版本和限流；写操作还要考虑重复效果。重试上限、退避和截止时间是控制额外负载，不是幂等保证。

### K2. 幂等键需要绑定请求内容

**读这一段是为了解决：** 同一个键为什么还要核对请求指纹？

记录operation_id与request_hash。如果同一个ID和同一个内容再次出现，返回已知结果；同一个ID却换内容，返回冲突。只用ID去重而不校验内容，会把用户新需求误当旧请求。

数据库唯一约束或单写入者保证同时到达的请求不会都赢。一个普通字典可以演示概念，但没有持久化和同步就无法处理多进程或重启。

### K3. 修改文件与写操作记录不是天然原子

**读这一段是为了解决：** 文件已改但记录未写时怎么判断？

你不能用一个数据库事务同时原子提交普通文件写入。若文件已改而操作记录尚未更新就崩溃，恢复时要比较before_hash和after_hash：当前等于after可补全结果，等于before才考虑重新执行，其他内容进入冲突/人工核对。

对任意外部系统，未必能靠状态判断执行了几次，因此不要声称实现了普遍的exactly-once。教学文件场景有明确前后指纹，才可以做有限恢复。

### K4. 超时是观察失败，不一定是操作失败

**读这一段是为了解决：** 调用方的超时与服务方的执行事实如何并存？

客户端没收到回应，只能证明期限内没有确认。服务端可能没收到、正在执行、已经成功但响应丢失。对只读请求再次查询通常较安全；对写请求直接重做可能重复。明确状态unknown并建立查询机制，才能把不确定性逐步变成已确认结果。不要为了接口好看把unknown硬映射成failed。

### K5. 幂等是同一业务操作重复提交的语义

**读这一段是为了解决：** 幂等键的业务作用域应该是什么？

操作ID要在第一次发起前生成并稳定复用，不能每次重试换ID。服务端记录ID、规范化请求哈希和结果；同ID同内容返回已有结果，同ID不同内容拒绝。并发重复时需要原子占位或唯一约束，单线程字典查询后插入不能证明并发安全。记录的保留期也必须覆盖允许的重试窗口。

### K6. 重试必须有停止条件与对账路径

**读这一段是为了解决：** 什么时候先核对而不是再发一次写请求？

错误分类决定能否重试，幂等决定重复是否安全，预算决定还能重试多久。退避和抖动只能缓解拥塞，不能消除重复副作用。写操作超时先按ID查询状态；确认未开始才重发；状态未知时保留待核对。后面J01把同样逻辑迁移到跨服务任务提交。

### 与你已有语言经验的连接

time.monotonic用于计算期限；uuid仅是ID生成手段，业务语义由稳定复用和服务端约束提供。

## 深入推演：把知识点连成因果关系

### 失败、成功和未知是三个不同结果

服务端完成文件写入后，返回包在网络中丢失。客户端看到超时，此时“没有拿到成功响应”为真，“文件没有写入”为假。若直接重试追加操作，就可能重复修改。这种不确定性不能用一个failed布尔值表达，必须留出unknown状态并查询真实结果。

### 幂等键要绑定语义，不能只是随机字符串

把一次操作绑定到稳定operation_id，同时保存请求指纹。相同ID和相同请求返回既有结果；相同ID配不同请求应冲突，不应复用旧结果。对于补丁还要保存前后版本和实际执行状态，以便恢复时核对。先查询再写在并发下可能仍有竞争，需要唯一约束、锁或其它原子认领机制；课程先在明确单执行器条件下推导，再到J01用数据库并发约束迁移。

### 重试是一项有成本的策略

读操作通常较容易重试，写操作要先判断是否重复有害及能否查询。可重试错误也必须受总deadline、次数与退避限制；每次重试有独立attempt_id，仍属于同一operation_id。把一次尝试的超时误当成整任务预算，会导致多层重试不断延长总执行时间。


## 3. 一次完整推演：先预测，再读下一步

1. op-7写补丁成功，响应故意丢失：客户端进入unknown，文件已是新内容。
2. 重复发送op-7且请求哈希相同：读取已存结果，不再次写文件。
3. 复用op-7但内容不同：返回conflict；换ID会变成新操作，不能假装是原重试。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 直接重试 | 无副作用或已有幂等保证 | 仍有次数与deadline |
| 先查状态 | 写操作结果未知 | 需要稳定操作ID |
| 人工/异步对账 | 下游无可靠查询能力 | 保持不确定终态而非伪造成功 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
records = {}
def submit(op_id, payload):
    if op_id in records:
        if records[op_id] != payload:
            return "conflict"
        return "replayed"
    records[op_id] = payload
    return "applied"

print(submit("op-1", "patch-A"))
print(submit("op-1", "patch-A"))
print(submit("op-1", "patch-B"))
```

```

```

## 5. 本课在Code Agent里实际增加什么

- 操作记录含operation_id、request_hash、before_hash、after_hash、status、result；同ID异内容拒绝。
- 复用L07条件写，注入写入成功后丢响应；调用方进入unknown并核对，不立即再写。
- 保存可恢复操作记录并在重启时核对文件指纹；before/after/other分别处理；无法判断不冒充成功。
- 明确重试策略：输入/权限错误不重试；暂时性读取错误有限重试；写操作先核对身份与状态。

职责落点不是已存在断言；具体建议、当前源码确认方法见[本课文件导航](00-本课目的与文件导航.md)第3节。

## 8. 面试时如何解释你做过的事

**重试为什么可能更糟？**

会放大负载或重复副作用；先确定错误类别和已发生事实。

**唯一键能保证外部操作只执行一次吗？**

只保证对应记录的唯一性，外部副作用仍需协议支持与核对。
