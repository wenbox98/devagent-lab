## 0. 这课为什么存在

create_agent覆盖常见循环，LangGraph让你明确表达自定义状态、分支与节点。F04 不把画图当完成，而是让每条边由可观察事实触发。

成品是有限修复状态图，节点返回增量，Reducer明确怎样合并状态。

## 1. 一条具体方案：从输入到结果

### 从三种节点构造一个最小图

```text
plan → execute → verify
                  ├─ 目标与回归通过 → END
                  ├─ 可修复且剩预算 → plan
                  └─ 环境失败/无预算/未知状态 → stop
```

State保存任务约束、当前代码版本、操作引用、尝试次数和结果摘要，不保存文件句柄、数据库连接或密钥。

### 最容易出现的重复问题

假设messages用追加Reducer：旧状态 `[m1]`，节点应返回增量 `[m2]`，合并后 `[m1,m2]`。如果节点返回整个 `[m1,m2]`，Reducer又追加一次就得到 `[m1,m1,m2]`。

同理，按ID合并消息与简单列表相加的语义不同。应为每个字段规定覆盖、追加、按ID更新或拒绝冲突，并写重复更新测试。

### 明确的实现策略

先串行执行节点，路由只读已验证状态；未知状态失败关闭。graph的递归限制是兜底，业务attempt预算仍由状态字段检查。一个节点报错和一次工具正常失败不是同一种边，分别记录。

### Reducer的三种常见合同

覆盖：新值替代旧值，适合当前status。追加：old+delta，适合事件流但需去重策略。按ID合并：同ID更新或拒绝，适合消息/操作记录。它们不是可任意互换的装饰器。

```python
def append_events(old, delta):
    return old + delta

assert append_events(["e1"], ["e2"]) == ["e1", "e2"]
# 错误调用：把完整历史当增量，会重复e1。
assert append_events(["e1"], ["e1", "e2"]) == ["e1", "e1", "e2"]
```

### 谁能改哪个字段

plan产生下一步提议，execute产生工具结果，verify产生验收事实。不要让每个节点都返回完整state并覆盖别人的新字段，这会让并发/恢复更难推断。

先串行图通过，再引入并发节点与冲突合并规则。图能画出来只是定义可视化，实际事件顺序与合并结果才是验收。

### K1. 为什么已经有create_agent还要学图

**读这一段是为了解决：** 何时需要显式图状态而不仅是默认循环？

**原教材的浓缩句：**

> 当流程包含明确阶段、人工审批和恢复点，你可能需要比通用模型工具循环更明确的控制。

**展开与落地：**

自定义图适合需要明确分支、恢复位置和状态归属的流程，不是因为图看起来更高级。已有简单循环满足要求时无需强行变图。

迁移时把原工具和grader作为节点内部服务复用，图负责协调，不重写安全判断。

### K2. 状态应该存什么，不该存什么

**读这一段是为了解决：** 状态中哪些是持久事实、哪些不应序列化？

**原教材的浓缩句：**

> 为受控修复流程保存任务标识、当前代码指纹、候选补丁引用、测试摘要、预算与错误。

**展开与落地：**

State只存可序列化、可解释且有所有权的数据。大块源码可保存版本化引用，需要时通过受控工具取回；密钥留运行环境。

每个字段明确由谁写：verify写验收结果，execute写操作记录引用，plan不能自行把verified改true。

### K3. Reducer为什么容易产生重复

**读这一段是为了解决：** 返回旧历史为何造成重复追加？

**原教材的浓缩句：**

> 假设evidence字段用列表追加规则。

**展开与落地：**

Reducer是并发/多次更新的合并规则，不是自动去重魔法。追加字段返回delta，覆盖字段返回新值，按ID字段定义重复事件处理。

用小列表手算合并再运行测试，能立即发现重复消息。别先钻图框架内部调度代码。

### K4. 手推一个有限修复图

**读这一段是为了解决：** 条件边怎样利用刚更新的状态决定停止？

**原教材的浓缩句：**

> 入口进入read，获得版本与局部证据；plan产生候选；verify读取测试结果；条件边在成功时进入END，失败且还有预算时回plan，预算用完时进入failed。

**展开与落地：**

每条边对应一个可判断条件：tests_passed、retryable_failure且budget剩余、terminal_error。条件要互斥且覆盖未知情况。

未知值不要默认回到plan，避免无限循环。写预算耗尽和未识别状态测试，确认不会继续发模型请求。

### K5. 异常与正常失败要分开

**读这一段是为了解决：** 业务失败与节点抛异常为什么走不同路径？

**原教材的浓缩句：**

> 测试断言失败可以是业务状态，进入下一轮修复；节点内部KeyError是实现缺陷，不能伪装成“测试还没通过”。

**展开与落地：**

工具返回not_found是可表示的业务失败，节点自身抛TypeError可能是程序Bug。前者可以形成观察再路由，后者应报告内部错误而非伪造工具成功。

框架异常与领域错误在边界转换，保留足够诊断。统一except后返回空状态会让图继续运行在缺失事实之上。

### K6. 本课需要读懂的Python

**读这一段是为了解决：** TypedDict和Annotated怎样表达状态与合并合同？

**原教材的浓缩句：**

> `Annotated`给字段附加合并规则，`operator.add`在列表上是连接，字典返回值只包含本节点增量。

**展开与落地：**

TypedDict/类型注解主要帮助静态检查，不自动深度验证所有运行时状态。Reducer函数普通输入输出可以单测，图集成另验。

先会读节点签名、返回增量与路由函数即可。图可视化是导航，实际执行事件序列才是证据。

## 3. 本课选什么方案，怎样证明它有效

| 具体问题 | 本课基础方案 | 怎样验收 | 没有覆盖什么 |
|---|---|---|---|
| 状态 | 字段有所有权与序列化边界 | plan不能伪造verify结果 | 不存密钥/连接句柄 |
| 合并 | 每字段选Reducer，节点返回delta | 重复更新不复制整个历史 | 不同Reducer语义需单测 |
| 路由 | 有限且未知状态停止 | 预算耗尽不再调用 | 递归限制不代替业务预算 |

这些是教学基线的选择，不是所有场景的唯一方案。改变威胁模型、规模、平台或供应商合同后，要重新确认假设；不要把“以后可强化”写成已经解决。
