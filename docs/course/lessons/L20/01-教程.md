## 先定位阅读目的与对象

**本课要回答：用户点了取消，哪些工作已经发生，哪些还必须真实停止？**

前提是：L19把任务独立出来，但取消信号与恢复执行可能交叉。 本课把它推进到：取消请求和实际停止分开，恢复先核对操作与工作区，避免双执行。

本文的知识讲解是为完成上述变化服务，不要求先掌握所有相邻技术。范围边界：next_action只决定下一步，不证明正在运行的进程已经停止。

**文中代码分两种。** [00-example.py](00-example.py)是包中已经提供的概念示例；本课“工程实现/职责路径”是对你项目的目标要求，除L00起始骨架外不表示应用已经生成。未生成时只研究示例；生成后让Codex把职责映射到实际文件，不照猜函数名找代码。

### K1. 取消是请求，确认是另一个事实

**读这一段是为了解决：** 收到cancel请求与确认cancelled为何分开？

设置cancel_requested后，worker在下一步前检查；运行中的测试由运行器停止并确认子进程处理；之后再标cancelled。若取消与完成竞争，需要明确优先规则，终态不能随意翻转。

HTTP客户端超时不会自动传播成任务取消。Java稍后必须显式调用取消接口，用户界面也要区分“请求取消”和“已取消”。

### K2. 检查点不包含所有外部事实

**读这一段是为了解决：** 检查点为何不足以说明外部副作用？

检查点保存已完成步骤、消息、待执行动作和操作ID。崩溃可能发生在外部写入后、检查点前，因此恢复先核对L10操作记录与文件状态，再决定跳过、重试或人工处理。

恢复的任务要获取执行所有权。旧worker若仍存活，不能和新worker同时写。同机单worker方案可先确保旧进程确实结束；多worker需要租约/代际号等更强机制，不在本课宣称完整分布式恢复。

### K3. 工作区隔离与资源隔离不同

**读这一段是为了解决：** 独立目录与独立计算资源分别保证什么？

每个task_id使用独立临时目录或git worktree，防止文件互相覆盖。它不自动限制CPU、内存或网络，因此仍复用L08运行器。并发上限与有界队列控制资源，两个任务隔离演示只能证明教学场景。

### K4. 恢复也要保留可解释结果

**读这一段是为了解决：** 恢复之后如何解释哪些事已发生？

任务发现未知文件状态时进入needs_review/failed并说明证据，不假装成功。每次恢复记录attempt、旧/新执行者和核对结果。用户应能知道为什么没有继续，而不是看见永久running。

### K5. 取消是一种协作协议

**读这一段是为了解决：** 取消信号如何传到真正执行工作的地方？

cancel_requested表示已请求停止，cancelled表示执行已停止且清理结果已确认。worker在安全边界检查取消标记；外部子进程需终止和回收。若写操作已经完成，取消不能假装抹去它；记录已完成副作用并决定是否需要补偿。用户停止等待与系统停止执行必须是两个可观察事件。

### K6. 租约与围栏解决不同问题

**读这一段是为了解决：** 租约到期为什么还需要阻止旧worker写入？

租约允许worker占用任务一段时间并续约；超时后新worker接手。旧worker可能并未真正死亡，网络恢复后继续写入，所以只靠租约仍会出现双写。围栏token是单调递增执行代号，写入端拒绝旧token。教学先做数据库状态条件更新与独立工作区，再明确外部系统是否也接受围栏；不支持的副作用仍需幂等和对账。

### K7. 恢复必须重建可验证状态

**读这一段是为了解决：** 恢复前怎样核对工作区、待确认操作与执行身份？

持久化摘要不能替代副作用账本。重启时读任务、最近已确认步骤、未知操作ID、代码版本和环境，先核对外部结果再继续。工作区按任务隔离，清理时只清自己的路径；对保留调试证据与磁盘配额有规则。恢复测试要真的杀进程，不只调用一个名为resume的函数。

### 与你已有语言经验的连接

asyncio.CancelledError、协作取消与进程终止不同；异常处理不能吞取消信号后继续循环。

## 深入推演：把知识点连成因果关系

### 取消是一段协议，不是一个布尔变量

用户发出取消请求，执行器在安全检查点收到信号，停止调度新操作，尽力中断可中断的模型或进程调用，回收资源，核对已发生的写入，最后提交终态。这些步骤有时不能瞬间完成，因此可以需要cancel_requested或cancelling这样的内部阶段。必须明确取消对已发生副作用的含义，不承诺自动回到原状。

### 恢复需要同时核对逻辑状态与物理状态

检查点保存已处理消息和下一节点，但文件系统可能已经完成了写入；恢复后再次执行节点会重复副作用。将稳定operation_id、工作区指纹和执行记录一起核对，必要时返回unknown等待人工检查。不要声称框架checkpointer自动带来了端到端exactly-once。

### 并发隔离从命名与所有权开始

每个任务使用独立工作区、状态命名空间与日志关联标识。多个用户同名任务不能共享临时目录；用户ID不是由模型填入的参数。F05/F06已经学过图检查点和审批，这一课要检验服务层是否沿用了同样的身份、任务版本与操作键，不再另起一套恢复逻辑。


## 3. 一次完整推演：先预测，再读下一步

1. 测试进程运行中取消：先看到cancel_requested，再确认进程退出，最后才cancelled。
2. worker1租约过期，worker2持有token=8；worker1用token=7提交结果，应被拒绝。
3. 写入后未落状态就崩溃：恢复先用操作ID查结果，而不是无条件再次应用补丁。

每一步在学习记录写三列：已知事实 / 仍未确定 / 下一步最小行动。不要把“模型说”填进已验证事实列。

### 为什么选择这个方案，而不是另一个

| 方案 | 适用条件 | 代价或边界 |
| --- | --- | --- |
| 取消标记 | 可协作的长步骤之间 | 不能独自停止阻塞外部进程 |
| 租约 | 发现失联与允许接管 | 旧worker可能仍存活 |
| 围栏+幂等 | 防迟到写与重复副作用 | 需要下游实际执行约束 |

## 4. 可运行小例子：看见机制

小例子的本次检查范围见[验证报告](../../validation/report.md)；Java/SQL需要相应环境。 小例子只演示一个关键机制；完整应用需要按第5节及02文档增量生成。

```python
def next_action(cancel_requested, operation_state):
    if cancel_requested:
        return "stop_before_next_step"
    if operation_state == "unknown":
        return "reconcile"
    if operation_state == "applied":
        return "skip_duplicate_write"
    return "execute"

for pair in [(True, "pending"), (False, "unknown"), (False, "applied")]:
    print(next_action(*pair))
```

运行位置为自己的项目根目录，教材已复制到docs/course/：

```bash
python .local/concepts/L20/00-example.py
```

预期观察：

```text
stop_before_next_step
reconcile
skip_duplicate_write
```

### 按因果关系理解输出

顺序重要：已请求取消不应开始新的写操作；未知操作不能立即重放。这是决策示例，运行中的子进程和已经发生的副作用仍需额外处理，取消不是回滚。

现在只修改练习副本`.local/concepts/L20/00-example.py`中的指定输入：加入(True,"applied")；观察停止下一步是否等同于撤销已经完成的操作。 运行前先写预测。预测错误时，指出首个与预期不同的分支；不要直接让AI解释完就跳过。

## 5. 本课在Code Agent里实际增加什么

- cancel_requested与cancelled分开；每次模型/工具前检查，长测试取消交给运行器并确认；完成/取消竞争有条件状态更新。
- 持久检查点包含消息摘要、待确认操作ID、工作区版本和执行attempt；恢复先核对再推进。
- 每任务独立工作目录；单机worker重新接管前确保旧执行停止，防双执行；不夸称分布式exactly-once。
- 至少两任务并发与取消测试，设最大活跃数和队列上限；目录清理由任务所有权控制。

## 8. 面试时如何解释你做过的事

**取消是否自动撤销改动？**

不是，取消阻止后续工作；回滚已有副作用需独立策略和版本条件。

**恢复等于重新运行吗？**

不等于，需核对哪些动作已生效，避免重复执行。

补一句反事实：如果“防迟到写与重复副作用”不再成立，你会怎样调整？没有做过的实验如实说明，不能把教材数字说成自己的线上收益。
