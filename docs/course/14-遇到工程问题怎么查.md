# 不熟悉的故障，先用证据缩小范围

## 固定四步，而不是固定答案

写一个最小失败输入；列两个可同时解释现象的假设；设计一个能区分假设的观测；只改已经被证据定位的层。每次改完保留原失败输入作回归。多个假设都不符合时扩大观测，不把第一次猜测写成根因。

| 现象 | 假设A / 假设B | 最有区分力的第一条证据 | 回到课程 |
| --- | --- | --- | --- |
| 工具调用没有执行 | 模型没产tool_calls / dispatcher拒绝参数 | 原始模型结构与dispatcher拒绝日志 | L03/F02 |
| 同一文件读到旧内容 | 索引旧 / 当前工作区不是想象位置 | 内容hash与已解析工作区根 | L02/R01 |
| 补丁重复应用 | 操作键没复用 / 已提交但响应丢失 | 幂等记录、结果hash与响应时序 | L10/F05 |
| 测试绿但任务错 | 测试没收集 / 报告不是当前快照 | collected、test_set_hash、workspace_hash | L09/L12 |
| 状态越来越大 | reducer接全量 / 新消息本就重复 | 节点输入、返回增量、合并后三份快照 | F04 |
| RAG回答无根据 | 候选漏召回 / 证据被裁剪 | 检索候选与实际送模上下文对照 | R01/L16 |

| Java入口耗尽线程 | 下游慢 / 队列无界 | 活跃线程、队列长度与下游延迟分布 | J02/L21 |

## 一份像工程师写的故障记录

“相同请求第二次执行把文件改了两遍”只是现象。好的记录继续写：假设1是幂等键不同，假设2是数据库未保存第一次结果；先比较两次operation_id，若不同转查键生成，若相同再查事务提交与响应丢失。修复后分别测重复请求、键冲突和恢复窗口，不能只再跑正常路径。

还要记录不能确定的部分。没有抓到事件时序，就不能说‘一定是并发问题’；没有真正杀进程，就不能说持久恢复已证明。使用[故障复盘模板](templates/故障复盘.md)，AI只能评审你的证据，不能替你伪造观测。
